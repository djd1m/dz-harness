Изолируем показ.
Ставим skills.

Терминал · выполнить до запуска Codex
# Из корня dz-harness; основное дерево останется нетронутым
git worktree add ../dz-talk-demo HEAD
cd ../dz-talk-demo

# Установка skills без изменения пользовательских hooks
dz init --target codex \
  --select design-taste-frontend,package-story-page,presentation-storyteller \
  --project . --no-hooks --no-verify

dz list --skills-dir .agents/skills
codex
Говорим вслух: worktree — страховка показа; --no-hooks не меняет глобальную конфигурацию зрителя.

2 минуты. Не устанавливайте npm-пакет во время выступления: сделайте это заранее и начните с dz --version. Если worktree уже создан, просто войдите в него. После dz list покажите три каталога skills.

Live demo · шаг 2/3

Просим результат.
И доказательство.

Вставить в Codex
Изучи packages/@dzhechkov/harness-cli/package.json и README.md.
Используй установленные skills package-story-page,
design-taste-frontend и presentation-storyteller.

Создай два файла: out/live-demo/index.html — автономную
русскоязычную story-page о dz для нового разработчика —
и out/live-demo/verify.mjs — детерминированную проверку.
Ограничения страницы: без CDN и сборки, 5 экранов,
клавиатурная навигация, видимый CTA с точной командой для Codex.
Проверка обязана именованно проверять эти ограничения и выходить
с кодом 1, если найден внешний script src или stylesheet href.

До редактирования назови 4 критерия готовности.
После редактирования запусти проверку HTML и сообщи:
1) какие файлы созданы; 2) какую команду запускал;
3) её exit code; 4) что осталось непроверенным.

Не диктуем макет. Фиксируем аудиторию, артефакт, ограничения и evidence contract.

5 минут. Пока Codex работает, подсветите четыре части запроса: реальные источники в репозитории; явно названные skills; узкая форма результата; формат доказательства. Если прошло 90 секунд без файла — прервите и попросите показать текущий план и незавершённый артефакт. Не превращайте задержку в театральное «всё точно работает».

Live demo · шаг 3/3

Финал — это
квитанция

Проверяем проверку: green → red → green
# 1. Штатная страница — GREEN
node out/live-demo/verify.mjs

# 2. Пускаем «дым»: внешний script — нужен RED
cp out/live-demo/index.html /tmp/dz-live-demo-index.html
sed -i 's#</body>#<script src="https://example.com/demo.js"></script></body>#' out/live-demo/index.html
node out/live-demo/verify.mjs

# 3. Возвращаем байты — снова GREEN
cp /tmp/dz-live-demo-index.html out/live-demo/index.html
node out/live-demo/verify.mjs
git status --short

Смотрим не на красноречие

01файл реально существует 02gate зелёный на норме 03gate красный на нарушении 04после восстановления снова зелёный
Зелёная проверка ничего не стоит, пока вы не видели её красной.

2 минуты. Первый запуск обязан быть зелёным. Затем одной строкой добавьте внешний script: gate обязан назвать нарушение и вернуть ненулевой код. Восстановите точные байты и получите зелёный снова. Честно скажите: этот мини-gate проверяет форму и самодостаточность, но не визуальное качество на разных экранах.

Для существующего проекта

Сначала dz architecture и минимальный набор skills. Не устанавливайте весь каталог «на всякий случай».

Для повторяемой работы

Правило усиливают: рекомендация → skill → детерминированный gate → CI.

2 минуты. Соедините demo с большой картиной курса: каталог помогает найти способность, target доставляет её, проверки удерживают честность, память переносит реальные уроки между сессиями. Это путь от разовой удачи к системе.

Забрать с собой

Три правила на завтра

1

Храните способность

Не переобъясняйте процесс в каждом промпте — оформляйте повторяемое решение как skill.

2

Ставьте минимум

Выбирайте skills под текущую задачу и компилируйте под реальный target.

3

Требуйте квитанцию

Слово «готово» начинается после воспроизводимой команды проверки.

1 минута. Проговорите выводы медленно. Финальная формула: модель предлагает, harness ограничивает и снабжает, проверка решает, можно ли доверять результату.
