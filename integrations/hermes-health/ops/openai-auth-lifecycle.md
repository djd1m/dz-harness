# Жизненный цикл OpenAI OAuth в Hermes

Статус: эксплуатационное решение и план следующего этапа, 2026-11-09.
Автоматическая синхронизация и единый сервис обновления **не реализованы**.

## Что проверено на установленной версии

Hermes хранит OpenAI Codex OAuth в своём `auth.json`, в секции
`providers.openai-codex`, отдельно от Codex CLI. При обновлении токенов штатный
`_save_codex_tokens` синхронизирует связанные записи credential pool и сохраняет
независимые учётные записи. Других провайдеров заменять нельзя.

В установленном `hermes_cli/auth_codex.py` явно описана ротация refresh token
с обнаружением повторного использования. Файловый lock защищает обновление
одного auth store; копии в разных контейнерах и на хабе этим lock не связаны.
Это установленный риск схемы копирования, а не утверждение, что текущая
авторизация уже сломалась. HTTP200 endpoint usage доказывает принятие access
token в момент проверки, но не следующий refresh и не получение ответа модели.

## Принято сейчас

Разовая передача свежей авторизации выполнена по запросу владельца. До записи
сохранены закрытые резервные копии; права credential files0600. Изменён только
Codex OAuth, остальные providers и выбор active_provider сохранены. Авторизация
в постоянном Hermes home переживает restart. Изменения в writable layer
контейнера (например `/root/.codex/auth.json`) сами по себе **не переживают
recreate**: для CLI надо явно использовать постоянный CODEX_HOME при установке.

Не добавлять timer, который слепо разносит auth.json или запускает refresh во
всех потребителях. Не считать выбор самого нового mtime доказательством
актуальности refresh chain. Не откатывать старый refresh token автоматически:
после ротации он может быть уже использован.

## Варианты устойчивой эксплуатации

1. **Отдельная OAuth-сессия для каждого независимого refresh-процесса.**
   Тот же пользователь может авторизовать Hermes и CLI отдельно, если это
   поддержано провайдером и условиями его плана. Выделенные grants устраняют
   копирование одной цепочки refresh между процессами. Перед внедрением
   проверить штатный login на установленном Hermes, идентичность аккаунта без
   вывода персональных данных, сохранение grant и независимый refresh двух
   клиентов. Требуется участие владельца в login, передавать секрет в чат не надо.

2. **Единственный владелец общей refresh chain.**
   Отдельный доверенный credential broker сериализует refresh и атомарно
   сохраняет новую пару. Потребители получают только краткоживущий access token
   и не выполняют refresh сами. Понадобится поддерживаемый адаптер Hermes и
   отдельная проверка режима Codex CLI: нельзя предполагать, что штатный CLI
   позволяет запретить refresh и использовать внешний broker. Пока хабовый
   CLI продолжает самостоятельно обновлять ту же chain, единственного владельца
   нет. Простое общее подключение auth.json к контейнерам недостаточно.

Для текущих независимых Hermes/CLI предпочтителен первый вариант при успешной
проверке штатных login и правил аккаунта. Второй — отдельная инфраструктурная
функция, а не копирование файла. Не подменять OAuth подписки API-ключом с
отдельным биллингом без решения владельца.

## Приёмка следующего этапа

- Изолированный профиль/контейнер без карты, gateway и cron production.
- Успешный минимальный inference, а не только HTTP200 usage.
- Два параллельных клиента: refresh одного не ломает второй.
- Проверка expiry, revoke, недоступности провайдера, restart/recreate.
- Нет refresh token в логах, аргументах процессов, Git и модельном контексте.
- Отдельная блокировка, атомарная запись и fail-closed при сбое сохранения для
  broker-варианта; не повторять refresh после неоднозначного сетевого исхода
  бесконечно. Должен быть понятный путь повторного login.
- Переключать контейнеры по одному; не перезапускать медицинскую карту или
  другие cron-задания ради проверки.

Секретные резервные копии нужны для расследования/восстановления конфигурации,
но не гарантируют возможность отката OAuth. Отчёты должны содержать только
результат и момент проверки, без account ID, JWT, refresh token и их фрагментов.

## Проверка 2026-11-09 после переноса

В hermes-me и hermes-dz-health выполнен отдельный `hermes chat --safe-mode`
через provider openai-codex, model gpt-6.1-terra. Оба вернули ожидаемый AUTH_OK.
Режим исключал плагины и пользовательские правила, задача не требовала
инструментов. Это проверка inference в текущий момент; принудительный refresh
общего grant не вызывался, долговечность копированной chain не подтверждена.
