# Медицинские инструменты Hermes — кандидат 0.3

Нативный плагин предоставляет три инструмента чтения, предпросмотр, подготовку пакета и отдельные gateway-команды подтверждения; также навык `hermes-health:health-read`.
Добавление оригиналов выполняется только после явного подтверждения и включения writer оператором. Распознавание PDF, клиническая верификация и отправка вложений остаются отдельными функциями рабочего агента/CLI.

Каталог находится вне `packages/`: опубликованные npm tarballs и MIRROR-MANIFEST не меняются.
Это предложение отдельной интеграции для публичного зеркала, не опубликованный npm-пакет.
Существующий `adapter-hermes` можно использовать для переноса остальных навыков;
он не реализует регистрацию этих инструментов. Общее ядро изменено в source repo dz-harness-hub, PR125; опубликованные tarballs этого зеркала не редактируются.

## Проверенная конфигурация

Linux, Python 3.14 (unit-тесты также Python 3.12), Hermes 0.22.2, Node 22.23.4,
health-advisor 1.10.10-hermes.0 (кандидат), harness-cli 0.7.5, harness-core 0.5.4, better-sqlite3 11.10.0.
Другие сочетания требуют повторной интеграционной проверки. Нативный SQLite binding
должен быть собран под тот Node, который задан в HEALTH_NODE.

## Установка в тестовую среду

Скопируйте **этот каталог**, включая skills, в `$HERMES_HOME/plugins/hermes-health/`.
Используйте отдельный HERMES_HOME, тестовую карту и отдельного бота; токен production не копируйте.

```bash
export HEALTH_WORKSPACE=/absolute/path/to/test-medical
export HEALTH_NODE=/opt/health-node22/bin/node
export HEALTH_RUNTIME=/opt/health-advisor-runtime
hermes plugins doctor "$HERMES_HOME/plugins/hermes-health"
hermes plugins validate "$HERMES_HOME/plugins/hermes-health" --json
hermes plugins enable hermes-health
```

HEALTH_RUNTIME содержит node_modules/@dzhechkov/health-advisor,
node_modules/@dzhechkov/harness-cli и собранный node_modules/better-sqlite3.
Устанавливайте зависимости заранее: плагин не скачивает пакеты и не обновляет их.
После включения запустите новую сессию Hermes. При явных списках toolsets добавьте
`hermes_health` в конфигурацию соответствующего интерфейса и проверьте видимость пяти инструментов и трёх gateway-команд.

Настройки задаёт оператор через окружение процесса, они не принимаются как аргументы инструмента.
Директория workspace и её родительские каталоги должны находиться под управлением оператора.
Для отката отключите `hermes-health` и перезапустите соответствующий процесс; том карты сохраняется.

## Контракты

- `health_search(query, limit=5)` — полнотекстовый CLI-поиск только по `.health-brain`.
  Перед выдачей passages сверяется хеш текущего документа. Устаревший источник даёт ошибку.
  DB+WAL читаются дважды и должны совпасть; SQLite Backup API и CLI работают на приватной
  временной копии. При активном изменении индекса возвращается `index_busy_retry`.
- `health_source_get(entry_id=...)` либо `health_source_get(path=...)` — оригинал из manifest
  или документ разрешённого каталога. Для manifest обязательно совпадение размера и хеша.
  Текст ограничен 12000 символами; для бинарного оригинала возвращаются только метаданные.
- `health_validate()` — размеры и SHA-256 **перечисленных** записей manifest. Не заменяет
  полную `health-advisor intake-archive --verify`: не ищет неучтённые raw-файлы и не проверяет
  клиническую интерпретацию или достоверность самого manifest.

Все ответы содержат `ok`; ошибки — стабильный код без содержимого stderr.
`human_verification=not_established`: хеш никогда не превращает результат в проверенный человеком.
Даты и клинические статусы следует брать из самого документа/структурированного профиля.
Документный текст недоверенный: инструкции внутри документов не исполняются.

Лимиты: файл 32 MiB, manifest 8 MiB/10000 строк, суммарная проверка 512 MiB/20 секунд,
DB и WAL по 128 MiB, subprocess 25 секунд/2 MiB stdout+stderr, 10 поисковых результатов
по 6000 символов. Превышение даёт ошибку, не неполный успешный отчёт. Проверка времени
между файловыми чтениями не прерывает блокирующее чтение неисправного файлового устройства.
Поиск временно хранит до нескольких копий индекса, требуется запас RAM и локального tmp.
Конкурирующая враждебная замена родительского workspace и изменения ядра CLI вне закреплённого
окружения не входят в модель защиты; symlink в запрашиваемых путях запрещены.

## Проверки

```bash
python3 -m unittest discover -s integrations/hermes-health/tests -v
# В подготовленном изолированном health runtime, без сети и production volumes:
python3 /plugin/tests/integration_check.py
```

Интеграционный тест создаёт синтетический документ и индекс через настоящий CLI, находит источник,
сверяет SHA-256, проверяет отказ при изменении источника и неизменность исходного workspace.
Дополнительно запускаются настоящий `hermes plugins doctor` и `hermes plugins validate`.
Все фикстуры генерируются во временных каталогах. Медицинские данные и credentials не включены.

## Приёмка на приватной копии и рабочее включение

1. Подготовьте отдельную копию разрешённых каталогов карты и checkpointed SQLite через Backup API. Не подключайте рабочие секреты, архивы auth или production gateway. Для теста потребуется manifest и минимум три различных текущих источника в индексе.
2. Подключите копию read-only к тестовому контейнеру, отключите сеть, задайте HEALTH_WORKSPACE и выполните `python3 /plugin/tests/acceptance_check.py`. Проверка выводит только агрегированный результат. Поиск по doc_id подтверждает соответствие источника, но не оценивает качество семантического поиска.
3. В отдельном Hermes home выполните штатный enable, затем discovery и вызов handler через реестр. doctor сам по себе не доказывает успешную конфигурацию рабочего процесса.
4. Сохраните Compose и config.yaml рабочего агента в закрытый каталог резервных копий. Скопируйте закреплённую версию плагина в постоянный Hermes home; добавьте три HEALTH_* параметра в environment контейнера. Не заменяйте существующие env_file, модель, токены или тома.
5. Выполните штатный `hermes plugins enable hermes-health`. При отсутствии активных задач пересоздайте только целевой сервис Compose с `up -d --no-deps SERVICE`. Проверьте discovery, `health_validate` и connected в состоянии Mattermost. Прочие контейнеры не перезапускайте.
6. В новой сессии Mattermost попросите вызвать `health_validate`. Успешный API/registry smoke и статус connected не заменяют эту проверку.

Откат: штатно отключить плагин (`hermes plugins disable hermes-health`), удалить только три добавленных HEALTH_* параметра и пересоздать целевой сервис. Исходную конфигурацию восстанавливать целиком только при отсутствии последующих изменений; иначе переносить изменения выборочно. Каталог плагина и том карты удалять не требуется.


## Предпросмотр PDF/ZIP

`health_intake_preview(attachment, expect_sha256?)` принимает **basename из события вложения** (например, `doc_abc123_документ.pdf`), а не абсолютный путь, URL или Mattermost file_id. Оператор добавляет HEALTH_INBOX с точным путём к кэшу документов профиля; получить его можно через `gateway.platforms.base.get_document_cache_dir()` в том же Hermes окружении. Подкаталоги, symlink и специальные файлы запрещены. Требуется существующий валидный manifest карты.

Два ограниченных чтения сверяются, затем обработка идёт по зафиксированным байтам. Это обнаруживает наблюдаемое изменение загрузки, но не является гарантией атомарности конкурирующей записи. Независимо известный SHA-256 можно передать как expect_sha256; без него автоматически вычисленный хеш доказывает только соответствие снимка. Предпросмотр запускает настоящее intake-ядро в одноразовой временной карте, проверяет полученные источники и сравнивает их с рабочим manifest. Проверяются и реальные байты найденных дублей. Рабочая карта и inbox не изменяются.

Вход до 16 MiB; до 100 записей ZIP, 16 MiB на файл, 64 MiB распакованных данных. CLI — 25 секунд/2 MiB вывода; проверка результата и сравнение дублей имеют отдельные временные бюджеты до 20 секунд каждый. Это не единый 25-секундный deadline. Время файлового I/O зависит от исправности носителя. Временные данные удаляются, но secure erase не гарантируется.

PDF проверяется только по `%PDF-`/`%%EOF`, затем сохраняется без изменения байтов внутри технического ZIP. PDF внутри архива не проходит полноценный разбор. Нет OCR, проверки активного содержимого, шифрования PDF или медицинской интерпретации. Ошибки ядра возвращаются обезличенным runtime_failed: не следует называть любую такую ошибку повреждением архива.

Результат preview_only не разрешает commit. Дедупликация ограничена текущим manifest и актуальна на момент проверки. В многопользовательском сервисе нужен отдельный авторизованный inbox на пациента: basename не является контролем доступа. CLI получает локальный --file и не использует сетевой transport; отсутствие сети проверяется в тестовом контейнере. Сам Python subprocess не является OS network sandbox.

Дополнительные тесты в закреплённом runtime без сети:

```bash
PYTHONPATH=/opt/hermes HERMES_HOME=/tmp/preview-test-home python3 /plugin/tests/test_intake_preview.py -v
```

Перед широким использованием отправьте технический PDF через Mattermost в новой сессии и явно попросите `health_intake_preview`, без записи в карту. Наличие tools в реестре и проверка cache utility не заменяют эту проверку доставки.


## Подтверждаемое добавление (кандидат 0.3)

`health_intake_prepare(attachment=...)` фиксирует исходные байты и выдаёт ограниченную по времени квитанцию. Для PDF имена членов ZIP определяются полным SHA-256; переименование загрузки не создаёт новое содержание. Точный дубль возвращается без квитанции, смешанный ZIP отклоняется целиком.

Оператор задаёт `HEALTH_INTAKE_STATE` вне карты и Git. Каталог0700, файлы0600, persistent mount; сохраняйте его резервную копию, включая ключ HMAC. По умолчанию write отключён. Для реальной записи дополнительно требуется `HEALTH_INTAKE_WRITE_ENABLED=1` и ядро с capability manifest-cas/durable-journal/global-content-dedup/idempotent-sha256.

Пользователь отдельно отправляет `health-confirm <receipt_id>` через зарегистрированную gateway-команду; `health-cancel` отменяет, `health-status` сообщает состояние. Синтаксис Hermes — slash-команда. В Mattermost перед ней может потребоваться начальный пробел, чтобы клиент не перехватил неизвестный slash. Реальную доставку нужно принять отдельно; наличие handler не доказывает её. Ни одна из этих команд не является tool модели.

Подтверждение сверяет связанные ContextVars platform/profile/user/chat. Environment fallback, cron, чужой канал/пользователь не дают права на запись. Receipt HMAC защищает от незаметного изменения state, но процесс с тем же UID и shell может обойти эти проверки — это не изоляция от root/кодера.

Ядро сверяет ожидаемый SHA manifest под общей блокировкой. После успешного subprocess отдельно проверяются реальные источники и `--verify`. Неопределённый результат сохраняется как reconciliation_required без автоматического повтора. Повтор подтверждённой операции проверяет текущие оригиналы.

Ограничения: срок30мин,64 receipts,256MiB state; очистка пока административная. OCR, медицинская верификация, обновление индекса и git push не выполняются. Подробности: `features/hermes-health-confirmed-intake/11_operator_runbook.md`.

Validator предупреждает об использовании приватных ContextVars Hermes. Это сознательная зависимость от закреплённой версии0.22.2: публичный get_session_env допускает небезопасный для подтверждения environment fallback. После обновления Hermes требуется повторная проверка этого интерфейса; при его отсутствии подтверждение отказывает.
