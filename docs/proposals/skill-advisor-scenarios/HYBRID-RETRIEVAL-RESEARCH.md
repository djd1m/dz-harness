# Готовые компоненты гибридного поиска для советника DZ Harness

Дата: 2026-11-10. Первоначальное исследование. Эксперимент завершён: см. [результаты проверки](HYBRID-EXPERIMENT-RESULTS.md). Ниже сохранены предварительные оценки до измерений; по результатам предпочтён LanceDB, production не изменён.

## Решение, которое предлагается

Сначала сравнить **Orama JS и LanceDB Embedded** с существующим lexical baseline на одном утверждённом каталоге. Не переносить весь советник на новый framework. Первый кандидат для небольшого каталога и минимальной интеграции — Orama; кандидат с явно документированным TypeScript hybrid/RRF — LanceDB. Окончательный выбор сделать по измерениям, а не по звёздам.

LlamaIndex действительно решает эту задачу на Python: BM25Retriever + vector retriever + QueryFusionRetriever. Но **LlamaIndexTS архивирован**, README прямо говорит об отсутствии сопровождения. Python-проект продолжает развиваться. Новую Node.js-интеграцию на архивированном TS-пакете не начинать.

## Наш контекст

Текущий `integrations/skill-advisor-catalog/search.mjs` использует RU/EN stemmer, совпадения терминов и IDF-подобный вес. Это не полноценный BM25. Векторов нет; выдаётся до пяти кандидатов. Затем дешёвая модель выбирает утверждённые сценарии, а сервер выводит проверенные объяснения и ссылки на курсы. Навык skill-advisor не исполняется agent runtime на каждом запросе.

Рабочий каталог: 32 сценария / 12 пакетов по сохранённому аудиту. Нельзя считать отсутствующий сценарий ошибкой retrieval: отдельно измеряем покрытие каталога, нахождение существующих сценариев, качество выбора и отказа. Семантический поиск не создаст отсутствующие знания.

## Пять осей: предварительная архитектурная оценка

Шкала 1–5; выше лучше по всем осям. Последняя ось — **управляемость эксплуатации и рисков**, а не величина риска. Это суждения для нашего VPS/Node.js/малого каталога, не результаты нагрузочного теста и не security certification. Баллы могут измениться после проверки конкретных зависимостей.

- Fit: 1 — не подходит, 3 — подходит с новым стеком/сервисом, 5 — напрямую закрывает текущую задачу. User story: «нахожу пакет по свободной формулировке и точному имени».
- Freshness: 1 — прекращено сопровождение, 3 — активность есть, но release cadence требует внимания, 5 — свежие релизы и активность. User story: «могу обновляться без собственной поддержки заброшенного fork».
- Maturity: 1 — эксперимент, 3 — рабочая реализация с открытыми эксплуатационными вопросами, 5 — развитая документация и эксплуатационные механизмы. User story: «после рестарта рекомендации воспроизводимы».
- Adoption: оцениваем наблюдаемую популярность, не доказанное production adoption. Здесь 3 — 3–15 тыс. GitHub stars, 4 — 15–40 тыс., 5 — более 40 тыс. User story: «есть сообщество для поиска решений»; звёзды лишь слабый proxy.
- Assurance: 1 — неподдерживаемая зависимость, 3 — управляемая, но дополнительная runtime/native/service поверхность, 5 — проверенная минимальная поверхность с воспроизводимой поставкой. Ни одному кандидату 5 без аудита не присваивается. User story: «обновление можно проверить, откатить и не открыть лишний сетевой доступ».

Обоснование отличий: Orama не требует второго runtime/DB, но GitHub latest release старше остальных; LanceDB напрямую поддерживает нужный TS path, но требует проверки native поставки; Qdrant получает высокую maturity за развитый Query API и эксплуатационные документы, но ниже fit из-за отдельного сервиса; Python frameworks зрелые, однако для нашей задачи расширяют стек. Archived TS имеет независимое исключающее условие: среднее значение не может его отменить.

Веса пока не утверждены ADR, поэтому не выдаём произвольное среднее за окончательный рейтинг. Предлагаемый приоритет: качество подбора → простота эксплуатации → стоимость/задержка. Популярность не должна компенсировать непригодность или отсутствие поддержки.

## Что всё равно нужно сделать нам

Готовый engine не выбирает автоматически подходящую RU/EN embedding-модель и не гарантирует верность совета. Документные embeddings вычислять при сборке каталога, query embedding — на запросе; фиксировать model ID, размерность, hash текста, revision каталога. Не смешивать векторы разных моделей. Модель эмбеддингов и её стоимость выбрать отдельным коротким сравнением; наличие ключа для чат-модели не доказывает доступность embedding endpoint.

Схема: свободный вопрос → lexical + semantic retrieval → fusion → проверка ограничений/выбор дешёвой моделью → утверждённые объяснения и ссылки. Не заменять утверждённый renderer свободным генератором. RRF использует позиции результатов и не требует складывать несопоставимые BM25/cosine scores. Для Orama конкретный алгоритм fusion ещё проверить; RRF не приписываем ему без проверки.

Индекс хранит только утверждённые сценарии с revision/ID, обновляется атомарно. При сбое embeddings — явно зарегистрированный lexical fallback; при несовпадении revision не использовать устаревший индекс. Не выводить уверенное отсутствие пакета только потому, что retrieval не нашёл сценарий. Выбор engine не требует E2B или исполнения навыков на каждом запросе.

## Следующий эксперимент, до изменения production

1. Зафиксировать отдельный holdout: минимум 60 запросов — перефразировки RU/EN, точные имена, частичные задачи, несколько целей, отрицательные и неоднозначные случаи. Разметить допустимые scenario IDs и ожидаемый отказ; не подгонять каталог под holdout.
2. Одинаковый каталог и embeddings: текущий lexical, semantic-only, Orama hybrid, LanceDB hybrid. Добавить BM25-only каждого кандидата, чтобы отделить улучшение лексики от эффекта fusion. Одинаковые top-k и ограничения.
3. Измерить coverage отдельно; на покрытых запросах Recall@5 и MRR; затем end-to-end правильность комплекта, ложные рекомендации и обоснованные отказы. Отдельно точные IDs и многозадачные запросы.
4. Записать p50/p95, холодный старт, память, размер индекса, стоимость embedding/selector, повторяемость при одинаковых scores. Проверить отказ embedding API, restart, повреждение/устаревание индекса.
5. Критерий допуска: прирост retrieval на перефразировках без регрессии точных IDs и без роста ложных полных рекомендаций. Заранее зафиксировать численные бюджеты задержки/стоимости. Если оба подходят, выбрать меньшую операционную сложность.
6. Зафиксировать ADR выбора и версии; только после этого интеграция, review и кандидат на публикацию.

Исследование подтверждает наличие готовых компонентов. Оно пока не доказывает, что любой из них повышает качество нашего советника.
