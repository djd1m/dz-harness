## ddia-ch03-ku01 — Индексы: компромисс чтение/запись
*type: heuristic · pages: 99–100 · skill_worthiness: high*

**Problem:** Стоит ли добавлять индекс и по каким столбцам, если он ускоряет чтение, но замедляет запись?

**Content:** Ключевой компромисс подсистем хранения: индекс — производная структура от основных данных, которая ускоряет запросы на чтение, но замедляет запись, поскольку индекс приходится обновлять при каждой записи. Простое дописывание в конец файла (append-only) — простейшая и самая быстрая операция записи; любой индекс её замедляет. Поэтому БД не индексируют всё подряд по умолчанию — разработчик/DBA выбирает индексы вручную, исходя из типичных паттернов запросов приложения, чтобы выгода была максимальной, а накладные расходы не превышали необходимого. Ориентир по сложности: поиск без индекса (полное сканирование лог-файла) имеет сложность O(n) — при удвоении числа записей время поиска удваивается.

**Applicability:** Проектирование схемы индексов; решение о добавлении/удалении вторичных индексов; оценка стоимости записи при большом числе индексов.

**Limits:** Правило не даёт конкретных порогов — выбор индексов зависит от знания реальных паттернов запросов; для конкретной нагрузки нужно измерять.

## ddia-ch03-ku02 — Хеш-индекс (модель Bitcask)
*type: case-pattern · pages: 100–104 · skill_worthiness: high*

**Problem:** Когда простой append-only лог с хеш-индексом в памяти — правильный выбор подсистемы хранения?

**Content:** Стратегия: append-only лог-файл значений + хеш-карта в оперативной памяти, отображающая каждый ключ на смещение (offset) в файле. Запись = дописать пару в конец файла и обновить offset в хеш-карте; чтение = найти offset и прочитать значение (одна операция позиционирования на диске, а при попадании в кэш ФС — без I/O). Так работает Bitcask (движок Riak). Управление размером диска: лог разбивается на сегменты фиксированного размера, к ним применяется уплотнение (compaction — отбрасывание дублирующихся ключей, хранение лишь последнего значения) и слияние сегментов в фоне; неизменяемые сегменты позволяют читать параллельно, запись ведёт один поток. Нюансы реализации: двоичный формат (кодировать длину строки), отметки об удалении (tombstone) при слиянии, контрольные суммы для обнаружения недописанных записей, восстановление хеш-карт после сбоя (Bitcask хранит снимки хеш-карт на диске).

**Applicability:** Много операций записи на один ключ при небольшом числе уникальных ключей (пример: счётчик просмотров видео по URL); все ключи помещаются в RAM; значения могут превышать RAM.

**Limits:** Хеш-таблица должна целиком помещаться в оперативную память (много ключей — не подходит); запросы по диапазону неэффективны — каждый ключ ищется отдельно.

## ddia-ch03-ku03 — SSTable + LSM-дерево
*type: methodology · pages: 104–108 · skill_worthiness: high*

**Problem:** Как построить движок с высокой пропускной способностью по записи и поддержкой запросов по диапазону, когда ключи не помещаются в RAM?

**Content:** SSTable (sorted string table) — сегмент, где пары отсортированы по ключу, каждый ключ встречается один раз. Преимущества: (1) слияние сегментов алгоритмом сортировки слиянием (mergesort) эффективно даже если файлы больше RAM; (2) не нужен полный индекс всех ключей — достаточно разреженного индекса в памяти (один ключ на несколько КБ файла), т.к. диапазон между известными смещениями сканируется быстро; (3) блоки между записями индекса можно сжимать. Пайплайн (LSM): запись → в располагающееся в памяти сбалансированное дерево MemTable (красно-чёрное/AVL); при превышении порога (обычно несколько МБ) MemTable сбрасывается на диск новой SSTable; чтение = MemTable → новейший сегмент → более старые; фоновое слияние+уплотнение. Для защиты от потери MemTable при сбое ведётся отдельный append-only WAL, удаляемый после сброса MemTable. Оптимизации: фильтр Блума (Bloom filter) для отсечения чтений несуществующих ключей; стратегии уплотнения — size-tiered (уплотнение по слоям в соответствии с размером) и leveled (поуровневое). Так работают LevelDB, RocksDB, Cassandra, HBase, Lucene (термы→postings list); термин из статьи Google Bigtable, структура описана O'Neil и др. (LSM-Tree).

**Applicability:** Наборы данных больше RAM; нужны запросы по диапазону; высокая пропускная способность записи (последовательная запись); полнотекстовые индексы.

**Limits:** Поиск отсутствующих ключей медленный без фильтра Блума; уплотнение может влиять на латентность (см. KU про сравнение с B-деревьями).

## ddia-ch03-ku04 — B-дерево: структура и надёжность
*type: case-pattern · pages: 108–112 · skill_worthiness: high*

**Problem:** Как устроен стандартный индекс реляционных БД и как обеспечивается его отказоустойчивость при обновлении на месте?

**Content:** B-дерево (1970, Bayer/McCreight) разбивает БД на страницы фиксированного размера, обычно 4 КБ, читаемые/записываемые по одной. Страницы ссылаются друг на друга по адресу на диске, образуя дерево: корень → внутренние страницы (ключи-границы диапазонов + ссылки на дочерние) → страницы-листья со значениями. Коэффициент ветвления (branching factor) = число ссылок на странице, на практике несколько сотен. Дерево сбалансировано → глубина O(log n); обычно 3–4 уровня (4-уровневое дерево страниц по 4 КБ с ветвлением 500 хранит до 256 ТБ). Обновление: найти лист, изменить, записать обратно; вставка при переполнении → разбиение страницы на две полупустые + обновление родителя. Отказоустойчивость: журнал упреждающей записи (write-ahead log, WAL / redo log) — append-only файл, куда модификации пишутся ДО применения к страницам, используется для восстановления после сбоя (иначе риск бесхозной/orphan страницы). Конкурентный доступ защищается защёлками (latches). Усовершенствования: копирование-при-записи (LMDB), сокращённые ключи во внутренних узлах (выше ветвление), указатели между листьями (B+-дерево), фрактальные деревья.

**Applicability:** Стандарт индексов практически во всех реляционных и многих нереляционных БД; поиск по ключу и запросы по диапазону; сильная транзакционность.

**Limits:** Обновление на месте — «опасная» многостраничная операция при разбиении; листья на диске не обязательно последовательны, что ухудшает большие range-сканы; требует WAL и управления защёлками.

## ddia-ch03-ku05 — B-дерево против LSM-дерева
*type: tradeoff-table · pages: 113–115 · skill_worthiness: high*

**Problem:** Какой тип OLTP-движка выбрать — B-дерево (обновление на месте) или LSM (журналированный)?

**Content:** Общее правило: LSM-деревья обычно быстрее при ЗАПИСИ, B-деревья — при ЧТЕНИИ (чтение в LSM медленнее — надо просматривать несколько структур/SSTable на разных стадиях уплотнения). Достоинства LSM: (1) меньше усиление записи (write amplification — эффект, когда одна логическая запись порождает много физических за время жизни БД; критично для износа SSD) — B-дерево пишет каждый элемент минимум дважды (WAL + страница, плюс при разбиении) и переписывает всю страницу ради нескольких байт; (2) выше пропускная способность (последовательная запись компактных SSTable вместо перезаписи страниц), особенно на HDD; (3) лучше сжимаются, меньше фрагментация (нет незанятого места в страницах). Недостатки LSM: (1) фоновое уплотнение конкурирует за пропускную способность диска → всплески латентности на высоких процентилях (B-деревья предсказуемее); (2) при высоких объёмах записи уплотнение может не успевать → рост числа несоединённых сегментов, замедление чтений, риск исчерпания диска — нужен отдельный мониторинг. Плюс B-дерева: каждый ключ в одном месте → удобно навешивать блокировки диапазонов ключей для изоляции транзакций.

**Applicability:** Выбор движка под профиль нагрузки (запись- vs чтение-ориентированный); SSD с ограниченным ресурсом перезаписи; требования к предсказуемости латентности; сильная транзакционность.

**Limits:** Оценки неубедительны и сильно зависят от нюансов нагрузки — обязательно тестировать под конкретную рабочую нагрузку; нет простого универсального правила.

## ddia-ch03-ku06 — Хранение значений в индексе: heap / clustered / covering
*type: tradeoff-table · pages: 116–117 · skill_worthiness: medium*

**Problem:** Где хранить фактические данные строки относительно индекса, чтобы сбалансировать скорость чтения и стоимость записи?

**Content:** Три варианта размещения значения при поиске по индексу: (1) Неупорядоченный файл (heap file) — индекс хранит ссылку на строку в отдельном heap-файле; избегает дублирования при нескольких вторичных индексах (все ссылаются в одно место). Минус: при увеличении значения строку приходится перемещать и либо обновлять все индексы, либо оставлять указатель-переадресацию. (2) Кластеризованный индекс (clustered index) — строка хранится прямо в индексе; в InnoDB (MySQL) первичный ключ всегда кластеризован, вторичные ссылаются на PK; SQL Server допускает один кластеризованный индекс на таблицу. (3) Охватывающий индекс / индекс с включёнными столбцами (covering index) — компромисс: в индексе хранится часть столбцов, что позволяет отвечать на запрос из одного индекса («индекс охватывает запрос»). Общий принцип: кластеризованные и охватывающие индексы ускоряют чтение, но требуют больше места, повышают стоимость записи и усложняют обеспечение согласованности из-за дублирования.

**Applicability:** Проектирование первичных/вторичных индексов; оптимизация частых запросов; выбор covering index для устранения лишнего перехода к heap-файлу.

**Limits:** Любое дублирование данных увеличивает накладные расходы записи и требует усилий по согласованности; выгода от covering index зависит от конкретных запросов.

## ddia-ch03-ku07 — OLTP против OLAP
*type: tradeoff-table · pages: 121–122 · skill_worthiness: high*

**Problem:** Как отличить транзакционную нагрузку от аналитической и почему их разделяют на разные БД?

**Content:** OLTP (обработка транзакций в реальном времени): небольшое число записей на запрос, извлекаемых по ключу; запись — произвольный доступ с низкой задержкой на основе ввода пользователя; пользователи/заказчики через веб-приложение; отражает актуальное состояние; размер ГБ–ТБ; узкое место — время позиционирования на диске (seek). OLAP (аналитическая обработка): агрегирование по большому числу записей (COUNT/SUM/AVG); запись — групповой импорт (ETL) или поток событий; штатные аналитики для поддержки решений; отражает историю событий; размер ТБ–ПБ; узкое место — пропускная способность диска. Почему разделяют: аналитические запросы ресурсоёмки, сканируют большие части данных и вредят производительности критичных OLTP-транзакций; поэтому с конца 1980-х аналитику выносят в отдельный склад данных (data warehouse) — read-only копию данных из всех OLTP-систем, оптимизированную под аналитические паттерны. Термин OLAP — из статьи Codd 1993.

**Applicability:** Решение о выделении отдельного склада данных; выбор движка (строчный vs столбцовый); проектирование ETL; оптимизация под seek vs bandwidth.

**Limits:** Границы OLTP/OLAP не всегда чёткие; некоторые СУБД (MS SQL Server, SAP HANA) поддерживают оба режима, но внутренне расходятся на две подсистемы.

## ddia-ch03-ku08 — Схемы «звезда» и «снежинка» (dimensional modeling)
*type: definition · pages: 125–127 · skill_worthiness: medium*

**Problem:** Как моделировать данные в складе данных для аналитики?

**Content:** Схема «звезда» (star schema, dimensional modeling): в центре — таблица фактов (fact table), каждая строка = отдельное событие (продажа, просмотр страницы, клик) в конкретный момент; столбцы фактов — либо атрибуты-меры (цена, себестоимость), либо внешние ключи к таблицам измерений (dimension tables), отвечающим на «кто/что/где/когда/как/почему» события (товар, дата, магазин, кампания, покупатель). Даже дата обычно выносится в таблицу измерения (кодирует праздники, будни/выходные). Название — из визуализации: таблица фактов в центре, измерения-лучи вокруг. «Снежинка» (snowflake) — вариант, где измерения разбиты на подызмерения (напр. отдельные таблицы марок и категорий), более нормализована, но используется реже, т.к. со «звездой» аналитикам работать удобнее. Таблицы фактов часто очень широкие (>100, иногда сотни столбцов); таблицы измерений тоже широкие (все метаданные для анализа). Факты хранят как отдельные события ради гибкости анализа → таблица может достигать десятков петабайт (Apple, Walmart, eBay).

**Applicability:** Проектирование склада данных; моделирование под BI-запросы; выбор между star и snowflake.

**Limits:** Модель заточена под read-heavy аналитику, не под OLTP; широкие таблицы фактов растут очень быстро.

## ddia-ch03-ku09 — Столбцовое хранилище: сжатие и векторизация
*type: methodology · pages: 128–133 · skill_worthiness: high*

**Problem:** Как эффективно выполнять аналитические запросы, читающие миллионы строк, но лишь 4-5 из >100 столбцов?

**Content:** Идея столбцового хранилища: значения одного столбца хранятся рядом (каждый столбец — отдельный файл), поэтому запрос читает и разбирает только нужные столбцы, а не грузит все >100 атрибутов каждой строки. Требование: все файлы столбцов содержат строки в одинаковом порядке (k-й элемент каждого столбца = k-я строка). Сжатие: столбцы хорошо сжимаются из-за повторов; кодирование битовыми картами (bitmap encoding) — столбец с n различными значениями → n битовых карт (бит=1, если строка содержит значение); при большом n разреженные карты дополнительно сжимаются кодированием длин серий (run-length encoding). Запросы типа WHERE col IN (...) = побитовое ИЛИ карт; WHERE a AND b = побитовое И. Порядок сортировки: сортировать нужно целые строки (не столбцы по отдельности), первый ключ сортировки задаёт DBA под частые запросы (напр. date_key) — даёт длинные серии для RLE (миллиарды строк → килобайты); первый ключ сжимается лучше всех. C-Store/Vertica хранят данные в нескольких порядках сортировки (используя реплики). Векторизованная обработка (vectorized processing): порции сжатых столбцов помещаются в L1-кэш CPU и обрабатываются в плотном цикле с SIMD-инструкциями, минуя вызовы функций. Запись: обновление на месте невозможно (сжатые сортированные столбцы) → используется LSM-подход (MemTable в памяти + фоновое слияние с файлами столбцов, как в Vertica).

**Applicability:** Склады данных, аналитические запросы с агрегированием по многим строкам и немногим столбцам; узкое место — bandwidth диска и циклы CPU.

**Limits:** Усложняет запись (вставка в середину сортированной таблицы → переписать файлы столбцов); семейства столбцов Bigtable/Cassandra/HBase — НЕ столбцовые (внутри семейства строка хранится построчно, без сжатия столбцов).
