## ch10-ku01 — Sort-based vs in-memory hash aggregation for batch group-by
- **Type:** decision-framework · **Pages:** 454 · **Skill-worthiness:** high
- **Problem:** When aggregating/counting over a large dataset, decide whether to accumulate counts in an in-memory hash table or to sort records and count adjacent duplicates.
- **Content:** The choice hinges on the working set — the amount of random-access memory needed, which depends only on the number of DISTINCT keys, not total record count (a URL with a million hits is still one hash-table entry). Decision rule: (1) If distinct keys fit in RAM (Kleppmann notes small/medium sites keep all unique URLs+counters in roughly 1 GB), use an in-memory hash table — fast even on a laptop. (2) If the working set exceeds available memory, sort instead: sort chunks in memory, spill sorted runs to disk as segment files, then merge sorted segments. Sorting yields sequential disk access patterns (same principle as SSTables/LSM-trees in §3.1) and scales past memory. GNU Coreutils sort auto-spills large inputs to disk and parallelizes across CPU cores; the bottleneck becomes source-file read speed. MapReduce always sorts between map and reduce, which is why it scales but pays a materialization cost.
- **Applicability:** Choosing an aggregation strategy for log analysis, counting, GROUP BY over datasets that may or may not fit in RAM; understanding why MapReduce mandates a sort step.
- **Limits:** The 1 GB figure is illustrative for small/medium sites; high-cardinality keys can blow the in-memory option even on modest data. Sorting adds latency because it must read all input before emitting output.

## ch10-ku01 — Bounded-input assumption of batch processing and its latency cost
- **Type:** heuristic · **Pages:** 270, 505, 506 · **Skill-worthiness:** medium
- (Note: shares the id `ddia-ch10-ku01` with the aggregation unit above.)
- **Problem:** When is batch processing the right fit, and what limitation forces a move toward stream processing?
- **Content:** Batch processing assumes input is BOUNDED: its size is known and finite, so the process can tell when reading is complete. This assumption is load-bearing for sort-based operations central to MapReduce: the engine must read the ENTIRE input before producing any output, because the very last record read could carry the smallest key and thus become the first output record — so emitting output before the full input stream is consumed is meaningless. In reality data is often unbounded (arrives incrementally over time and never truly 'final'), so batch processors artificially slice it into fixed time windows (e.g., process each day's data at day-end, or each hour's at hour-end). The tradeoff: with daily batch runs, an input change is reflected in output only a day later — often too slow. Reducing that latency means running more frequently (e.g., every second) or abandoning fixed windows entirely and processing events as they occur, which is the motivation for stream processing.
- **Applicability:** Deciding between batch and streaming architectures; explaining why MapReduce sort/shuffle must fully materialize input; reasoning about end-to-end latency of daily/hourly batch pipelines.
- **Limits:** Applies to sort/shuffle-style batch jobs; not every batch operation strictly requires reading all input. The unbounded-data framing and stream alternative are developed fully in Chapter 11, not here.

## ch10-ku02 — MapReduce job execution model (map, shuffle, reduce)
- **Type:** methodology · **Pages:** 460–463 · **Skill-worthiness:** high
- **Problem:** How to structure a distributed batch computation using MapReduce and understand what the framework does versus what you must write.
- **Content:** A MapReduce job runs four conceptual stages mirroring a Unix pipeline. (1) Read input files and split into records (e.g. `\n` as record separator) — handled by the input-format parser. (2) Map: the mapper is called once per input record, extracts a key and value, may emit zero-to-many key-value pairs, and holds no state between records (each processed independently). (3) Sort: the framework hash-partitions mapper output by key so all pairs with the same key go to the same reducer, and sorts each partition — you never write this code. (4) Reduce: the reducer is called once per key with an iterator over all values for that key (which may not fit in memory) and emits any number of output records. You only write map and reduce callbacks. Parallelism comes from partitioning: input = an HDFS directory; each file/block is a mapper partition. The scheduler applies 'put the computation where the data is' — run the mapper on a machine holding a replica of that input block if it has spare CPU/RAM, minimizing network load. The process of partitioning by reducer, sorting, and copying map output to reducers is called the shuffle. Number of map tasks = number of input blocks; number of reduce tasks = chosen by the job author.
- **Applicability:** Designing MapReduce jobs; reasoning about data locality, partitioning, and where sorting happens; understanding Hadoop/MongoDB/CouchDB map-reduce APIs.
- **Limits:** A single job cannot express computations needing a second sort (e.g. top-N by count) — chain multiple jobs. Shuffle sort is unavoidable and can dominate cost.

## ch10-ku03 — Batch join algorithms: reduce-side vs map-side variants
- **Type:** tradeoff-table · **Pages:** 467, 468, 471, 472, 473, 494 · **Skill-worthiness:** high
- **Problem:** How to join two large datasets in a batch job and which join algorithm to pick given size, partitioning, and sort properties of the inputs.
- **Content:** MapReduce has no index; it does full scans, which is fine for analytics touching most records. Choices: (A) REDUCE-SIDE SORT-MERGE JOIN — mappers on both inputs emit the join key; framework sorts+partitions so all records for a key arrive adjacently at one reducer; use secondary sort so the DB/dimension record precedes the event records. Pro: no assumptions about inputs. Con: heavy sort + shuffle + possible multiple disk spills. (B) MAP-SIDE BROADCAST HASH JOIN — use when one input is small enough to fit in memory: every mapper on a partition of the large input loads the entire small input into an in-memory hash table (or an on-disk read-only index cached in the OS page cache) and probes it. No reduce/sort. Supported as Pig 'replicated join', Hive MapJoin, Cascading, Crunch, Impala. (C) MAP-SIDE PARTITIONED HASH JOIN (Hive: bucketed map join) — when both inputs are partitioned the same way (same key, same hash function, same number of partitions), do a broadcast hash join per partition independently; each mapper loads only one partition of the small side. Requires prior jobs to have produced matching partitioning. (D) MAP-SIDE MERGE JOIN — when inputs are partitioned AND sorted on the join key, mappers merge-scan both sides record-by-record with no in-memory requirement. Output structure differs: reduce-side output is partitioned+sorted by join key; map-side output is partitioned+sorted like the larger input.
- **Applicability:** Choosing a join strategy in Hadoop/Hive/Pig/Spark; understanding why the query optimizer needs metadata (partition count, sort keys) stored in HCatalog/Hive metastore.
- **Limits:** Broadcast/partitioned hash joins require assumptions (small side fits memory, or identical partitioning) that reduce-side joins do not; getting partitioning/sort wrong silently breaks map-side joins. This covers equi-joins; non-equi joins are out of scope.

## ch10-ku04 — Handling skew (hot keys) in batch joins and grouping
- **Type:** heuristic · **Pages:** 469, 470 · **Skill-worthiness:** high
- **Problem:** A small number of hot keys (celebrities, key objects) collect disproportionate records, so 'collect all records with one key in one place' overloads a single reducer and stalls the whole job.
- **Content:** Because a MapReduce job finishes only when its slowest reducer finishes, one linchpin key creates a straggler. Compensation techniques: (1) Pig skewed join — first samples the input to detect hot keys; at join time, records for a hot key are sent to one of SEVERAL reducers chosen at random (not the single hash-determined reducer), and the other join input's matching records are replicated to all those reducers. Spreads the hot key across reducers at the cost of replicating the other side. (2) Crunch sharded join — same idea but hot keys must be specified explicitly (no sampling). (3) Hive skew join — hot keys declared explicitly in table metadata; their records stored in separate files and joined via a map-side join. (4) Two-stage grouping for hot-key aggregation — stage 1: send records to random reducers so each aggregates a subset of the hot key into a compact partial; stage 2: combine partials per key into the final value.
- **Applicability:** Batch joins/aggregations over social-graph or power-law data with hot keys; diagnosing straggler reducers.
- **Limits:** All techniques trade extra parallelism for duplicated input data or an extra MapReduce stage; explicit-hot-key methods require you to know the hot keys in advance.

## ch10-ku05 — Why MapReduce is designed for frequent task preemption
- **Type:** heuristic · **Pages:** 480, 481, 482 · **Skill-worthiness:** medium
- **Problem:** Understanding the rationale behind MapReduce's aggressive disk writes and per-operation restart, versus MPP databases that keep data in memory and abort/retry whole queries on failure.
- **Content:** MPP DBs abort the whole query on a node failure and retry (acceptable because queries last seconds-to-minutes) and keep as much data in memory as possible. MapReduce instead tolerates per-task map/reduce failure by re-running just that operation, and writes intermediate data to disk — partly for fault tolerance, partly assuming datasets exceed memory. This suits long jobs where a full restart on one failure would be wasteful. The real driver is Google's mixed datacenters: online services and batch jobs share machines, resources are containerized with priorities, and low-priority batch tasks can be PREEMPTED anytime to free resources for higher-priority work. Numbers: at Google a one-hour MapReduce task has roughly a 5% chance of being preempted — over an order of magnitude higher than hardware/reboot failure rates. With that rate, a job of 100 tasks each running 10 minutes has a >50% chance at least one is preempted before completing. Hence per-operation recovery. This preemption model is less common in open-source schedulers: YARN CapacityScheduler supports preemption for fair-sharing, but (at time of writing) YARN, Mesos, and Kubernetes did not preempt to reclaim resources — so these MapReduce trade-offs matter less there.
- **Applicability:** Deciding whether MapReduce's disk-heavy, per-op-recovery design is worth its overhead in your cluster; comparing to dataflow engines and MPP DBs.
- **Limits:** In clusters where preemption is rare and failures infrequent, the materialization overhead is largely wasted — dataflow engines (Spark/Flink/Tez) are then faster. The 5% / 50% figures are Google-specific.

## ch10-ku06 — Full materialization (MapReduce) vs pipelined dataflow engines
- **Type:** tradeoff-table · **Pages:** 483–487 · **Skill-worthiness:** high
- **Problem:** Deciding between classic MapReduce chains that materialize every intermediate state to the distributed filesystem versus dataflow engines (Spark, Tez, Flink) that treat the whole workflow as one job.
- **Content:** MapReduce chains write each job's output to HDFS as intermediate state that the next job reads. Drawbacks of full materialization vs Unix-pipe-style streaming: (1) a job starts only after ALL tasks of predecessors finish, so one slow/skewed task delays the whole workflow, whereas piped processes start concurrently and consume output as produced; (2) mappers are often redundant — they merely re-read what a reducer just wrote to repartition/sort it; if reducer output is already partitioned+sorted appropriately, reducers could be chained directly; (3) storing intermediate state in HDFS means replicating temporary data across nodes — often overkill. Dataflow engines fix this: operators generalize map+reduce and can be composed flexibly (repartition-and-sort, partition-only for hash join, or broadcast). Advantages: sorting done only where needed (not by default between every map/reduce); no redundant map stages; the scheduler knows all dependencies so it can co-locate producer/consumer and pass data via shared memory buffers; intermediate state kept in memory or on local disk (less I/O than replicated HDFS writes); operators start as soon as inputs are ready; JVMs are reused instead of a new JVM per task. Fault tolerance differs: MapReduce re-reads durable HDFS input to restart a failed task; Spark/Flink/Tez RECOMPUTE lost intermediate state from lineage (Spark RDDs) or operator checkpoints (Flink) — which requires operators to be DETERMINISTIC (fix random seeds; avoid hash-iteration order, system clocks, external sources), else cascading recomputation forces restarting downstream operators too.
- **Applicability:** Choosing an execution engine for multi-stage batch pipelines (recommendation pipelines of 50-100 jobs); understanding why Pig/Hive/Cascading can retarget MapReduce→Tez/Spark without code changes.
- **Limits:** Recompute-on-failure is not always cheaper: if intermediate data is much smaller than source or computation is CPU-intensive, materializing intermediates to files is cheaper than recomputing. Operators that sort must still buffer all input before emitting.

## ch10-ku07 — Hadoop/MapReduce vs MPP databases (schema-on-read vs schema-on-write)
- **Type:** tradeoff-table · **Pages:** 478, 479, 480 · **Skill-worthiness:** medium
- **Problem:** Choosing between an MPP analytic database and a Hadoop-style distributed-filesystem + general compute stack for large-scale data processing.
- **Content:** MPP databases: monolithic, tightly integrated storage+query-planning+execution, tuned for parallel analytic SQL; require modeling the schema and query patterns up-front and importing into a proprietary storage format (schema-on-write). Excellent performance for the query types they're built for; SQL is expressive and works with BI tools (e.g. Tableau). Hadoop/MapReduce over a distributed filesystem: files are just byte sequences in any encoding/model (records, text, images, video, sensor data, sparse matrices, genome sequences). Key differences — (1) STORAGE DIVERSITY: dump raw data into HDFS first and figure out processing later (schema-on-read / 'data lake' / 'sushi principle: raw data is better than cooked'); interpretation is shifted from producer to consumer, enabling multiple views and faster centralized collection; MPP's up-front modeling slows ingestion. Hadoop often serves as the ETL layer feeding an MPP warehouse. (2) PROCESSING-MODEL DIVERSITY: not all processing fits SQL (ML, recommendation, relevance ranking, image analysis need arbitrary code); MapReduce lets engineers run their own code over huge datasets, and you can build SQL on top (Hive). Many processing models (SQL, MapReduce, others) share one cluster and the same HDFS files — no re-importing per tool. The ecosystem includes random-access OLTP (HBase) and analytic MPP (Impala) both on HDFS. As high-level declarative operators arrive in batch engines and MPP DBs become more programmable, the two categories are converging.
- **Applicability:** Architecture decisions for analytics platforms, data-lake vs data-warehouse strategy, deciding where schema modeling should happen in the pipeline.
- **Limits:** Schema-on-read pushes interpretation cost to every consumer and can yield messy data; MPP's up-front modeling gives cleaner, faster-to-query data when access patterns are known. Convergence means the distinction is blurring.

## ch10-ku08 — Batch graph processing: iterative MapReduce vs Pregel/BSP vs single machine
- **Type:** decision-framework · **Pages:** 488–491 · **Skill-worthiness:** medium
- **Problem:** Running whole-graph offline algorithms (PageRank, transitive closure, recommendations) where computation must repeat until a convergence condition.
- **Content:** Graph algorithms propagate information along edges, iterating until a stopping condition (no edges left to traverse, or metric change below a threshold). Plain MapReduce cannot do 'repeat until done' — it does one pass — so you wrap it in an external scheduler loop: run one step as a batch job, check the convergence condition, re-run if not converged. This is inefficient because MapReduce ignores the iterative nature: it re-reads the entire input and writes a whole new output each iteration even if only a small part of the graph changed. Better: the Pregel / bulk-synchronous-parallel (BSP) model (Apache Giraph, Spark GraphX, Flink Gelly). A vertex 'sends messages' to other vertices along edges; per iteration a function is called for each vertex with its incoming messages (like reduce), but — unlike MapReduce — the vertex KEEPS its state in memory across iterations, so it only processes new incoming messages; idle graph regions do no work. Resembles the actor model but with fixed-round timing guarantees and durable fault-tolerant vertex/message state. Fault tolerance = periodic checkpoint of all vertex state to durable storage; on failure roll back to the last checkpoint (or, if deterministic + message logging, selectively recover only the lost partition). DECISION: if the graph fits in one machine's memory, a single-machine (even single-threaded) algorithm usually beats a distributed batch job, because distributed graph algorithms incur heavy cross-machine message traffic (intermediate messages are often larger than the graph itself) since partitioning tightly-connected vertices well is hard and systems typically partition by arbitrary vertex ID. If it fits on one machine's disk, use a single-machine engine like GraphChi. Only when the graph exceeds a single machine is distributed Pregel warranted.
- **Applicability:** Choosing an approach for offline whole-graph analytics; deciding when distribution actually helps versus hurts for graph workloads.
- **Limits:** Pregel's per-iteration barrier waits for all messages to be copied over the network before the next iteration; distributed graph processing frequently loses to single-machine tools unless the graph genuinely exceeds one machine.

## ch11-ku01 — Классификация систем обмена сообщениями: два вопроса и реакция на перегрузку
- **Type:** decision-framework · **Pages:** 508 · **Skill-worthiness:** high
- **Problem:** Как выбрать/оценить систему обмена сообщениями (pub/sub) и что она делает, когда инициаторы отправляют быстрее, чем потребители успевают обрабатывать, или когда узел падает.
- **Content:** Две ключевые вопроса для классификации: (1) Что происходит при переполнении — три варианта: отбрасывание сообщений (drop), буферизация в очередь, или контроль обратного потока / backpressure (блокировка отправителя). Конвейеры Unix и TCP используют backpressure: небольшой буфер фиксированного размера, при заполнении отправитель блокируется. (2) Что при сбое/недоступности узла — потеряются ли сообщения; надёжность достигается записью на диск и/или репликацией ценой пропускной способности и задержки. При буферизации важно понимать поведение при росте очереди (выход за пределы памяти → сброс на диск → падение пропускной способности). Приемлемость потери сообщений зависит от приложения: для периодических метрик датчиков потеря одного измерения терпима, но при подсчёте событий (счётчики) каждое потерянное сообщение искажает результат.
- **Applicability:** Выбор брокера/транспорта для событийного конвейера; проектирование обработки перегрузки и сбоев в pub/sub.
- **Limits:** Три варианта реакции — концептуальная рамка; конкретные системы комбинируют их через настройку. Не покрывает семантику доставки exactly-once.

## ch11-ku02 — Брокер на основе журналирования (Kafka) vs традиционный брокер (AMQP/JMS)
- **Type:** tradeoff-table · **Pages:** 515, 516, 517, 551 · **Skill-worthiness:** high
- **Problem:** Когда выбирать лог-ориентированный брокер (Kafka/Kinesis/DistributedLog) против классического брокера сообщений (RabbitMQ/ActiveMQ, стандарты JMS/AMQP).
- **Content:** AMQP/JMS-модель: брокер доставляет отдельные сообщения потребителям, потребитель подтверждает обработку, после чего сообщение удаляется (деструктивная операция). Распределение нагрузки: одно сообщение — одному потребителю (хорошо для тяжёлой per-message обработки), но сочетание распределения нагрузки с повторной доставкой неизбежно нарушает порядок сообщений. Лог-модель: журнал секционирован; брокер назначает потребителю целые разделы, внутри раздела монотонно растущее смещение (offset) гарантирует порядок; чтение неразрушающее — старые сообщения можно перечитать (replay). Ограничения лога: число потребителей одной темы ≤ числу разделов; медленное сообщение блокирует следующие в том же разделе (head-of-line blocking). Правило выбора: AMQP/JMS — когда обработка ресурсоёмкая, нужен per-message параллелизм и порядок неважен; лог — при высокой пропускной способности, быстрой обработке, важности порядка и потребности повторно читать историю. Смещение потребителя аналогично регистрационному номеру транзакции при репликации с одним ведущим (брокер = ведущий, потребитель = ведомый).
- **Applicability:** Проектирование event-конвейера, выбор брокера, решение о необходимости replay и упорядоченности.
- **Limits:** Границы между CEP/аналитикой и брокерами размыты; выбор зависит от конкретных требований к порядку/параллелизму.

## ch11-ku03 — Синхронизация гетерогенных систем: двойная запись — антипаттерн, CDC — решение
- **Type:** case-pattern · **Pages:** 520–524 · **Skill-worthiness:** high
- **Problem:** Одни и те же данные живут в нескольких системах (OLTP БД, кэш, поисковый индекс, склад) и должны оставаться согласованными при обновлениях.
- **Content:** Двойная запись (приложение явно пишет в каждую систему) имеет два фундаментальных дефекта: (1) состояние гонки — два конкурентных клиента пишут X=A и X=B; в БД финально B, в индексе финально A (запросы чередуются в разном порядке), рассогласование без ошибки и без обнаружения без векторов версий; (2) частичный сбой — одна запись успешна, другая нет; гарантия атомарности требует дорогой атомарной фиксации (2PC). Решение — сделать одну систему единственным ведущим и извлекать поток изменений: Change Data Capture (CDC) — наблюдение за всеми записями в исходную БД и извлечение их как потока для репликации в производные системы (поисковый индекс, кэш, склад), которые становятся ведомыми. Реализация CDC: (а) триггеры БД (склонны к сбоям, накладны) или (б) синтаксический анализ журнала репликации/WAL (надёжнее; проблема — отслеживание изменений схемы). CDC асинхронен → страдает от задержки репликации. Инструменты: LinkedIn Databus, Facebook Wormhole, Bottled Water (PostgreSQL), Debezium/Maxwell (MySQL binlog), Mongoriver, GoldenGate (Oracle), Kafka Connect. Для восстановления состояния: начать с надёжного снимка, привязанного к позиции/смещению в журнале, затем применять изменения. Уплотнение журнала (log compaction) — фоновый процесс, оставляющий для каждого ключа только последнюю запись (nil = отметка об удалении); объём журнала зависит от текущего содержимого БД, а не от истории записей → журнал даёт полную копию БД без отдельного снимка.
- **Applicability:** Поддержание согласованности между БД и производными системами (индексы, кэши, склады); проектирование пайплайнов синхронизации данных.
- **Limits:** CDC асинхронен → возможна рассинхронизация чтения; парсинг журнала репликации хрупок при миграциях схемы; log compaction применим только когда обновление ключа полностью заменяет предыдущее значение.

## ch11-ku04 — Источники событий (event sourcing): команды vs события, отличие от CDC
- **Type:** methodology · **Pages:** 525–530 · **Skill-worthiness:** high
- **Problem:** Как моделировать хранение состояния приложения через неизменяемый журнал событий и чем это отличается от CDC на уровне БД.
- **Content:** Event sourcing хранит все изменения состояния приложения как журнал неизменяемых событий, дописываемых в конец (обновления/удаления запрещены). Отличие от CDC — уровень абстракции: CDC извлекает низкоуровневые изменения записей БД (парсинг журнала репликации), приложение не знает о захвате; event sourcing моделирует события на уровне действий пользователя (напр. «студент отказался от зачисления»), сохраняя намерение, а не результат. Следствие для уплотнения: событие CDC содержит всю новую версию записи → предыдущие для ключа можно отбросить (compaction возможен); событие в event sourcing последующие не перезаписывают предыдущие → нужна полная история, уплотнение невозможно (снимки — только оптимизация чтения). Различие команды и события: входящий запрос сначала команда — может быть отклонена при нарушении целостности; валидация (напр. проверка занятости имени/места) должна быть синхронной, часто сериализируемой транзакцией; после принятия команда становится неизменным событием (фактом), которое потребитель отклонить уже не может. Отмену моделируют новым компенсирующим событием, а не удалением. Математически: состояние = интеграл потока событий по времени, поток изменений = производная состояния; «истина — это журнал, БД — кэш подмножества журнала» (Pat Helland). Разделение записи (журнал) и чтения (производные представления) = CQRS; из одного журнала строят несколько read-оптимизированных представлений.
- **Applicability:** Проектирование доменной модели с аудируемой историей; системы, где важны намерение действия и восстановимость состояния; DDD.
- **Limits:** Неизменяемость ограничена: приложения с высокой долей обновлений/удалений → быстрый рост истории, фрагментация, дорогая сборка мусора; законы о приватности требуют реального удаления (Datomic excision, Fossil shunning), что противоречит модели.

## ch11-ku05 — Время события vs время обработки; техника трёх временных меток при недостоверных часах
- **Type:** definition · **Pages:** 539–542 · **Skill-worthiness:** high
- **Problem:** Как корректно привязывать потоковые события ко времени, когда обработка может задерживаться, а часы устройств недостоверны.
- **Content:** Время обработки (локальные системные часы процессора) простое, но при значительном отставании обработки даёт ошибки — напр. после перезапуска процессора накопленные события выглядят как аномальный всплеск запросов, хотя реальная частота не менялась (рис. 11.7). Правильно использовать время наступления события (timestamp, встроенный в событие). Причины задержек/переупорядочения: очереди, сетевые сбои, перезапуск потребителя, повторная обработка при восстановлении; событие B может достичь брокера раньше события A. При недостоверных часах устройства (мобильное приложение буферизует офлайн, шлёт через часы/дни) регистрируют ТРИ метки: (1) время события по часам устройства, (2) время отправки на сервер по часам устройства, (3) время получения сервером по часам сервера. Смещение часов = (3) − (2); применяя его к (1), оценивают истинное время события (при пренебрежимо малой сетевой задержке). Отставшие события (stragglers) после закрытия окна: либо игнорировать их (отслеживая долю отброшенных как метрику), либо публиковать поправку с отменой предыдущего вывода.
- **Applicability:** Потоковая аналитика с временными окнами; телеметрия с мобильных/офлайн-устройств; любые оконные агрегации по времени события.
- **Limits:** Оценка смещения предполагает, что часы устройства не менялись между событием и отправкой и что сетевая задержка мала относительно требуемой точности. Пакетная обработка страдает теми же проблемами, но менее заметно.

## ch11-ku06 — Типы временных окон: падающее, прыгающее, скользящее, сессионное
- **Type:** tradeoff-table · **Pages:** 542, 543 · **Skill-worthiness:** high
- **Problem:** Как определить временное окно для оконных агрегаций (подсчёт, среднее) в потоковой обработке.
- **Content:** «Падающее» (tumbling): фиксированная длина, каждое событие ровно в одном окне; реализация — округление метки события до границы (напр. 10:03:00–10:03:59). «Прыгающее» (hopping): фиксированная длина, окна перекрываются для сглаживания (напр. 5-мин окно с шагом 1 мин: 10:03:00–10:07:59, затем 10:04:00–10:08:59); реализуется объединением нескольких падающих окон. Скользящее (sliding): содержит все события в пределах интервала друг от друга (напр. любые два события в пределах 5 минут попадают в одно окно, чего не было бы у падающих/прыгающих с фиксированными границами); реализация — буфер, отсортированный по времени, с удалением истёкших событий. Окно сессии: без фиксированной длины, группирует события одного пользователя, близкие по времени; закрывается после периода неактивности (напр. 30 минут без событий); типично для анализа поведения на сайте.
- **Applicability:** Выбор типа окна для метрик, агрегаций и сессионной аналитики в потоковых процессорах (Flink, Spark Streaming, Kafka Streams).
- **Limits:** Требует решённого вопроса времени события (см. ku05); сессионные окна требуют состояния per-user.

## ch11-ku07 — Три типа объединений потоков и зависимость от времени (SCD)
- **Type:** tradeoff-table · **Pages:** 543–547 · **Skill-worthiness:** high
- **Problem:** Как реализовать join'ы в потоковой обработке, где новые события поступают в любой момент.
- **Content:** Три типа: (1) поток—поток (объединение окон): оба входа — потоки событий; оператор ищет связанные события в пределах окна (напр. поиск и клик по одному session ID в пределах часа); требует состояния — индекс всех событий за окно по ключу, при каждом событии проверяются оба индекса. (2) поток—таблица (обогащение): поток активности + журнал изменений БД, дающий локальную копию (в памяти хэш-таблица или индекс на диске); для каждого события — локальный запрос к копии (удалённые запросы медленны и перегружают БД). Копия поддерживается подпиской на CDC-поток изменений — концептуально join с бесконечным окном, где новые версии перезаписывают старые. (3) таблица—таблица (материализованное представление): оба входа — изменения БД; каждое изменение одной таблицы соединяется с текущим состоянием другой, результат — поток изменений матпредставления (пример: кэш ленты Twitter, join tweets и follows). Зависимость от времени: порядок событий важен и не гарантирован между разными секциями/потоками; join с меняющимся состоянием недетерминирован (повторный прогон даёт другой результат). Этот случай в литературе называют «slowly changing dimension» (SCD, медленно меняющееся измерение); решение — уникальный ID версии для каждой версии записи (напр. ID налоговой ставки на момент продажи), что делает join детерминированным, но исключает уплотнение журнала (нужно хранить все версии).
- **Applicability:** Проектирование join'ов и обогащения в потоковых пайплайнах; материализованные представления; корректная обработка исторических данных при изменяющихся справочниках.
- **Limits:** Требует управления состоянием в процессоре; детерминизм через версионирование ценой отказа от log compaction; порядок между секциями не гарантирован.

## ch11-ku08 — Отказоустойчивость и семантика «выполнение один раз» в потоках
- **Type:** methodology · **Pages:** 548–550 · **Skill-worthiness:** high
- **Problem:** Как обеспечить exactly-once (точнее, «кажется, что один раз») при сбоях, когда поток бесконечен и нельзя дождаться завершения задачи, чтобы сделать вывод видимым.
- **Content:** Пакетный подход (отбросить вывод неудачной задачи и перезапустить) неприменим напрямую к бесконечному потоку. Механизмы: (1) Микропакеты (Spark Streaming) — разбить поток на блоки ~1 сек и трактовать каждый как мини-пакет; компромисс: меньше пакет → больше накладных на планирование, больше → выше задержка; неявно даёт tumbling-окно размером с пакет. (2) Контрольные точки (Apache Flink) — периодические снимки состояния в надёжное хранилище (HDFS), активируемые барьерами в потоке; при сбое перезапуск с последней точки. Обе дают exactly-once ВНУТРИ процессора, но не защищают внешние побочные эффекты (запись в БД, письмо, сообщение брокеру) — они случаются дважды при перезапуске. (3) Подтверждение малых изменений (atomic commit): все побочные эффекты (сообщения операторам, записи в БД, изменения состояния, инкремент смещения потребителя) должны фиксироваться атомарно — всё или ничего; реализовано внутрисистемно (без гетерогенного XA) в Google Cloud Dataflow, VoltDB, планировалось в Kafka; затраты амортизируются пакетированием сообщений в одну транзакцию. (4) Идемпотентность: операция, дающая тот же результат при повторе (запись фикс. значения по ключу идемпотентна, инкремент счётчика — нет); неидемпотентную делают идемпотентной, сохраняя смещение (offset) последнего обработанного сообщения во внешней БД → повторное обновление не применяется. Требует: повтор воспроизводит те же сообщения в том же порядке (лог-брокер), детерминированной обработки, отсутствия конкурентной записи того же значения; при подозрении на зомби-узел нужен fencing. Восстановление состояния: локальное состояние + периодическая репликация (Flink — снимки в HDFS; Samza/Kafka Streams — изменения в compacted Kafka-тему; VoltDB — избыточная обработка на нескольких узлах); иногда состояние восстанавливается воспроизведением входных событий из окна или из compacted-журнала.
- **Applicability:** Проектирование exactly-once потоковых пайплайнов; защита от дублирования внешних эффектов; восстановление stateful-операторов после сбоя.
- **Limits:** «Один раз» — это «кажется, что один раз» (записи могут переобрабатываться, но видимый результат один); идемпотентность требует детерминизма и отсутствия конкурентных писателей; нет универсального компромисса локальное/удалённое хранение состояния — зависит от инфраструктуры (сеть vs диск).
