# Непрерывное обучение в Keysarium — Полное руководство

> **`/bto*` commands are NOT part of @dzhechkov/keysarium.** The BTO evaluator
> (Build-Benchmark-Test-Optimize) ships as a SEPARATE npm package. Install it first —
> `npx @dzhechkov/skills-bto init` — otherwise every `/bto…` command referenced below will
> not resolve in your project.


> Как данные, генерируемые в ходе продуктовых исследований, превращаются в улучшения системы.

## 1. Обзор цикла обучения

Keysarium реализует **замкнутый цикл обучения**, где каждое исследование не просто решает задачу, а делает систему лучше для будущих задач:

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  ИССЛЕДОВАНИЕ │────→│   REWARD     │────→│   HARVEST    │
│  /casarium    │     │  (авто)      │     │  /harvest    │
└──────────────┘     └──────────────┘     └──────┬───────┘
       ↑                                          │
       │              ┌──────────────┐            │
       │              │   DREAM      │            │
       │              │   /dream run │            │
       │              └──────┬───────┘            │
       │                     │                    │
       │              ┌──────┴───────┐     ┌──────┴───────┐
       │              │  LEARNING    │     │     BTO      │
       │              │  STATS       │     │  /bto-test   │
       │              └──────────────┘     │  /bto-optimize│
       │                                   └──────┬───────┘
       │                                          │
       │              ┌──────────────┐            │
       └──────────────│   BRAIN      │←───────────┘
                      │  EXPORT/     │
                      │  IMPORT      │
                      └──────────────┘
```

### Два типа обучения

| Тип | Что происходит | Автоматически? | Результат |
|-----|---------------|----------------|-----------|
| **Reward Learning** | Система запоминает, какие подходы получили одобрение пользователя | Да | Лучшие подходы приоритизируются в будущих фазах |
| **Knowledge Harvesting** | Из артефактов извлекаются переиспользуемые паттерны, правила, шаблоны | Нет (ручной запуск) | Новые правила, шаблоны, скиллы добавляются в систему |

## 2. Установка и первый запуск

### Шаг 1: Установка пакетов

**Основной пакет** (обязателен):
```bash
npx @dzhechkov/keysarium init
```

Это создаёт:
- `.claude/commands/` — 18 slash-команд (исследование, harvest, brain, dream, learning-stats)
- `.claude/skills/` — 7 скиллов (explore, goap-research, problem-solver, presentation, reverse-engineering, frontend-design, feature-adr)
- `.claude/rules/` — 16 правил
- `.claude/shards/` — 9 governance-шардов
- `lib/` — библиотечные протоколы
- `CLAUDE.md` — мастер-инструкция

**BTO пакет** (нужен для оценки и оптимизации скиллов):
```bash
npx @dzhechkov/skills-bto init
```

Добавляет:
- `.claude/commands/` — 6 команд (`/bto`, `/bto-build`, `/bto-benchmark`, `/bto-test`, `/bto-optimize`, `/verify-chain`)
- `.claude/skills/bto/` — скилл BTO (модули build, benchmark, test, optimize + references)

> **Нужен ли BTO?** Для проведения исследований (`/casarium`) — нет. Reward learning и harvest работают без BTO. Но **для замыкания цикла обучения** — да: без BTO невозможно объективно оценить качество скиллов, обнаружить слабые места и оптимизировать. Если вы хотите просто проводить исследования без улучшения системы — BTO можно не ставить. Если хотите **непрерывное обучение** — BTO обязателен.

### Шаг 2: Первый запуск

При первом `/casarium` система работает **без исторических данных** — это нормально:

```
memory_query() → пустой результат → "No historical patterns found, proceeding normally"
```

Директория `.keysarium/memory/` будет создана автоматически при первом checkpoint.

### Что НЕ нужно настраивать заранее

- `.keysarium/memory/config.json` — создаётся автоматически с дефолтами
- `.keysarium/memory/index.json` — создаётся при первом `memory_store()`
- `TOOLKIT_HARVEST.md` — создаётся при первом `/harvest`

## 3. Фаза 1: Исследование — генерация данных

### Запуск исследования

```
/casarium [текст кейса]
```

Пайплайн проходит 7 фаз (Phase 0 → Phase 5 + Packaging), на каждой создавая артефакты в `researches/<slug>/`.

### Что генерируется (для обучения)

На каждой фазе генерируются два типа данных:

**1. Артефакты фазы** (видимые файлы):
```
researches/<slug>/
├── 00_product_discovery.md    ← Phase 0
├── 01_case_brief.md           ← Phase 1
├── 02_research_findings.md    ← Phase 2
├── 02.5_trend_brief.md        ← Phase 2.5
├── 03_solution_strategy.md    ← Phase 3
├── 04_architecture.md         ← Phase 4
├── 05-08_*.md                 ← Phase 5
└── prototype/cjm-prototype.jsx
```

**2. Reward-записи** (невидимые, автоматические):
```
.keysarium/memory/<domain>/<slug>/
├── phase-0_2026-03-01T10-00-00.json
├── phase-1_2026-03-01T10-30-00.json
├── phase-2_2026-03-01T11-00-00.json
└── ...
```

### Ключевой момент: Checkpoint

После каждой фазы система показывает checkpoint и **ждёт вашего ответа**. Именно ваш ответ определяет reward:

| Ваш ответ | Reward | Что запоминает система |
|-----------|--------|----------------------|
| "ок" / "next" | 1.0 (excellent) | "Этот подход отлично работает" |
| "углуби секцию X" | 0.7 (good) | "Подход хороший, но нужна доработка в одном месте" |
| "переделай подход" | 0.3 (needs_work) | "Подход не оптимален, нужен другой" |
| "начни заново" | 0.0 (failed) | "Подход провалился" |

> **Важно**: Если сессия прервалась без ответа на checkpoint — запись НЕ сохраняется. Только явные ответы генерируют reward-данные.

## 4. Фаза 2: Reward Learning — автоматический сбор

### Как это работает

Reward Learning работает **полностью автоматически** — вам ничего не нужно делать.

**При начале каждой фазы** — `memory_query()`:
1. Система ищет похожие прошлые записи (тот же домен + та же фаза)
2. Сортирует по reward (лучшие сначала), потом по usage_count (проверенные сначала)
3. Загружает топ-10 записей + паттерны домена
4. Агент учитывает лучшие подходы из прошлого

**При checkpoint** — `memory_store()`:
1. Система классифицирует ваш ответ → reward score
2. Сохраняет запись со всем контекстом (какой скилл, какой домен, какой результат)
3. Обновляет индекс `.keysarium/memory/index.json`

### Жизненный цикл записей

```
HOT (0-30 дней)  →  WARM (30-90 дней)  →  COLD (90-180 дней)  →  PURGE (>180 дней)
 Полные записи       Полные, но            Сжатые, в              Удалены
 Приоритет в          депри-                _archive/
 поиске               оритизированы
```

### Что делать с Reward Learning?

**Ничего.** Это фоновый процесс. Просто:
1. Проводите исследования через `/casarium`
2. Давайте честную обратную связь на checkpoint-ах
3. Система сама учится

**Проверить статистику** можно командой:
```
/learning-stats                     ← всё
/learning-stats --domain banking    ← по домену
/learning-stats --phase 2           ← по фазе
```

### Когда Reward Learning начинает работать?

- **3+ записей в домене** — появляется bottleneck detection
- **4+ записей по фазе** — появляется trend detection
- **10+ записей** — паттерны достигают confidence 1.0

## 5. Фаза 3: Harvest — извлечение знаний

### Зачем нужен Harvest

Reward Learning запоминает "этот подход сработал/не сработал". А Harvest **извлекает конкретные переиспользуемые артефакты** из завершённого исследования: паттерны, правила, шаблоны, сниппеты.

### Когда запускать

**После завершения каждого исследования** (Phase 5 + Packaging done):

```
/harvest researches/<slug>/
```

Или для всех завершённых исследований:
```
/harvest all
```

### Как работает Harvest

Pipeline: **Extract (5 agents) → Classify (7 categories) → User Review → Gate (8 checks) → Integrate**

**5 параллельных экстракторов** сканируют проект через разные линзы:
1. Архитектурные паттерны
2. Исследовательские паттерны
3. Промпт-инжиниринг находки
4. Доменные специфики
5. Процессные улучшения

**7 категорий** артефактов:
| Категория | Куда размещается | Пример |
|-----------|-----------------|--------|
| skills | `.claude/skills/` | Новый скилл для специфичной задачи |
| commands | `.claude/commands/` | Новая slash-команда |
| hooks | `.claude/rules/` | Хук на определённое событие |
| rules | `.claude/rules/` | Новое правило (например, для нового домена) |
| templates | `.claude/skills/*/templates/` | Шаблон артефакта |
| patterns | `TOOLKIT_HARVEST.md` | Доменный паттерн |
| snippets | `TOOLKIT_HARVEST.md` | Переиспользуемый фрагмент |

### User Review — ваш контроль

После извлечения система показывает нумерованный список находок. Вы контролируете:
- `#3 пропусти` — не включать находку #3
- `#5 перенеси в rules` — изменить категорию
- `пропусти G3,G4 для #14` — пропустить определённые quality gates
- `ок` — принять всё

### Результат Harvest

- Новые артефакты размещены в правильных директориях
- `TOOLKIT_HARVEST.md` обновлён
- Harvest report сохранён

## 6. Фаза 4: BTO — оценка и оптимизация скиллов

### Зачем нужен BTO

Harvest извлекает знания. Но как оценить, достаточно ли хороши существующие скиллы? И как их улучшить? Для этого — **BTO (Build-Test-Optimize)**.

### Какой режим BTO использовать?

| Ситуация | Команда | Что делает |
|----------|---------|-----------|
| Хочу оценить существующий скилл | `/bto-test .claude/skills/<name>/` | Layer 0 → Layer 1 → Layer 2 (3 судьи) |
| Хочу оценить + оптимизировать | `/bto .claude/skills/<name>/` | BENCHMARK → TEST → OPTIMIZE (полный цикл) |
| Хочу только оптимизировать (уже знаю score) | `/bto-optimize .claude/skills/<name>/` | Эволюционная оптимизация (3 раунда) |
| Хочу создать новый скилл | `/bto-build "описание"` | Генерация скилла из описания |
| Хочу создать + сразу оценить + оптимизировать | `/bto "описание"` | BUILD → BENCHMARK → TEST → OPTIMIZE |
| Хочу только бенчмаркнуть | `/bto-benchmark .claude/skills/<name>/` | Детерминистический бенчмаркинг (B0-B3) |

### Рекомендуемый сценарий после Harvest

Если Harvest создал новый скилл или значительно изменил существующий:

```
1. /bto-benchmark .claude/skills/<name>/      ← Дешёвая проверка (детерминистическая)
   Если BENCHMARK_SCORE < 0.50 → BLOCK:
     Исправить структурные проблемы, не тратить бюджет на судей
   Если BENCHMARK_SCORE >= 0.50 → продолжить:

2. /bto-test .claude/skills/<name>/           ← Оценить качество (3 судьи)
   Если score < 7.0:

3. /bto-optimize .claude/skills/<name>/       ← Оптимизировать
   Если score >= 7.0:
     Скилл автоматически промотируется в Tier 2
```

### Почему Benchmark первый?

`/bto-benchmark` — это **детерминистическая** оценка из 4 слоёв:

| Слой | Что проверяет | LLM cost |
|------|--------------|----------|
| B0 — Golden Sample | Структурное сравнение с эталонами | **0** (diff) |
| B1 — Test Suite | Кросс-ссылки, терминология, специфичность | **0** (rule-based) |
| B2 — Consistency Probe | 3 haiku-агента интерпретируют артефакт, измеряют согласие | **Minimal** (haiku x 3) |
| B3 — Performance | Эффективность токенов, баланс секций, покрытие references | **0** (metrics) |

Формула: `BENCHMARK_SCORE = B0 * 0.30 + B1 * 0.35 + B2 * 0.15 + B3 * 0.20`

Если benchmark показывает BLOCK (< 0.50), нет смысла тратить бюджет на панель из 3 sonnet-судей в `/bto-test`. Сначала исправьте структурные проблемы.

### Trust Tiers: что за уровни доверия

| Tier | Label | Как получить |
|------|-------|-------------|
| 0 | Advisory | Скилл создан (только SKILL.md) |
| 1 | Structured | SKILL.md + references/ или modules/ |
| 2 | Validated | `/bto-test` Layer 2 score >= 7.0 |
| 3 | Verified | Score >= 8.5 + eval test suites |

**Цель**: довести каждый скилл минимум до Tier 2. Скиллы Tier 0 выдают предупреждение при загрузке.

### Что делает BTO с данными Harvest

BTO работает **с файлами скилла напрямую**. Он:
1. Читает `SKILL.md` и все reference-файлы
2. **BENCHMARK**: детерминистическая оценка (B0-B3) — golden samples, test suite, consistency probe, performance metrics
3. Если BENCHMARK_SCORE < 0.50 → BLOCK, не переходит к судьям
4. Прогоняет через 71 структурную проверку (Layer 0)
5. Отправляет на панель из 3 судей (Layer 2)
6. Если score < 8.0 — оптимизирует (мутации + кроссовер)
7. Модифицирует файлы скилла in-place

Никакого экспорта не нужно — BTO работает прямо с файлами в `.claude/skills/`.

## 7. Фаза 5: Dream Cycles — обнаружение паттернов

### Зачем нужны Dream Cycles

Reward Learning копит данные. Dream Cycles **анализируют накопленные данные** и находят нетривиальные паттерны:
- "Банковские кейсы систематически проваливаются на Phase 2"
- "TRIZ работает лучше Game Theory для ритейла"
- "Phase 1 качество улучшается — текущий подход работает"

### Когда запускать

```
/dream run        ← Запуск анализа
/dream insights   ← Посмотреть найденные инсайты
/dream status     ← Проверить триггеры (пора ли запускать?)
```

**Рекомендация**: запускать после каждых 5-10 завершённых checkpoint-ов, или когда `/dream status` показывает активный триггер.

### Результат

Инсайты сохраняются в `.keysarium/insights/` и **автоматически подгружаются** при следующем `/casarium`:
- Phase 0 получает рекомендации по time budget
- Phase 2 получает предупреждения о проблемных фазах
- Все фазы получают рекомендации по выбору скиллов

## 8. Фаза 6: Brain Export/Import — перенос знаний

### Зачем нужен Brain Export

Знания накоплены в одном проекте. Как перенести их в другой?

```
/brain-export all                           ← Полный экспорт в JSON
/brain-export --delta parent-brain.json     ← Дельта (только новое)
```

### Что экспортируется

| Секция | Содержимое | Actionable? |
|--------|-----------|-------------|
| `skills` | Метаданные скиллов, trust tiers, BTO scores | Контекст |
| `domain_patterns` | Обнаруженные паттерны (из reward tracker) | **Actionable** |
| `research_summaries` | Саммари завершённых исследований | Контекст |
| `harvest_patterns` | Извлечённые знания из TOOLKIT_HARVEST.md | **Actionable** |
| `pipeline_metrics` | Метрики пайплайна (время, фазы) | Контекст |
| `reward_data` | Агрегаты reward-ов, средние по фазам/доменам, most_reused_records | **Actionable** |

### Как импортировать

В другом проекте (после `npx @dzhechkov/keysarium init`):

```
/brain-import path/to/brain.json
```

Стратегия: **merge-not-overwrite** — импорт не затирает существующие данные, а дополняет.

### Нужно ли экспортировать отдельно или использовать напрямую?

**Короткий ответ**: Для одного проекта — используйте напрямую. Для переноса между проектами — экспортируйте.

| Сценарий | Действие |
|----------|---------|
| Работаю в одном проекте | Ничего экспортировать не нужно. Reward data, harvest, patterns — всё используется автоматически |
| Начинаю новый проект, хочу опыт из старого | `/brain-export all` в старом → `/brain-import` в новом |
| Делюсь опытом с командой | `/brain-export all` → передать файл коллеге → `/brain-import` |
| Инкрементальный перенос | `/brain-export --delta prev-brain.json` → импорт только дельты |

## 9. Куда деваются данные: карта потоков

### Автоматические данные (не требуют действий)

```
                           ЗАПИСЬ                      ЧТЕНИЕ
                           ──────                      ──────
Checkpoint ответы ──→ .keysarium/memory/{domain}/  ←── memory_query() в каждой фазе
                      {slug}/{phase}_{ts}.json

Агрегаты ────────→ .keysarium/memory/_stats/       ←── /learning-stats
                    reward-summary.json

Паттерны ────────→ .keysarium/memory/_patterns/    ←── memory_query() (enrichment)
                    domain-patterns.json

Индекс ──────────→ .keysarium/memory/index.json    ←── memory_query() (fast lookup)
```

### Ручные данные (требуют запуска команд)

```
                           ЗАПИСЬ                      ЧТЕНИЕ
                           ──────                      ──────
/harvest ────────→ .claude/skills/                 ←── Загрузка скиллов в фазах
                   .claude/rules/
                   TOOLKIT_HARVEST.md

/bto-test ───────→ Evaluation reports              ←── /bto-optimize (baseline)
                   Trust tier promotion

/bto-optimize ──→ Модифицированные файлы           ←── Следующие исследования
                   скиллов (in-place)

/dream run ─────→ .keysarium/insights/             ←── Phase 0 (auto-load)
                   dream-{date}.json

/brain-export ──→ keysarium-brain.json             ←── /brain-import (другой проект)
```

## 10. Контекстные данные vs Actionable данные

### Actionable данные — непосредственно улучшают работу системы

| Данные | Где | Как используются | Действие |
|--------|-----|-----------------|---------|
| Reward records (high score) | `.keysarium/memory/` | `memory_query()` загружает в начале фазы как best practices | Автоматически |
| Domain patterns | `_patterns/domain-patterns.json` | Подгружаются при `memory_query()`, применяются как advice | Автоматически |
| Harvest artifacts | `.claude/skills/`, `.claude/rules/` | Загружаются при чтении SKILL.md, shard-ов, правил | Автоматически |
| Dream insights | `.keysarium/insights/` | Загружаются в Phase 0, влияют на time budget и skill selection | Автоматически |
| BTO improvements | Файлы скилла (in-place) | Скилл стал лучше → следующая загрузка использует улучшенную версию | Автоматически |
| usage_count | В каждом reward record | Более переиспользуемые записи приоритизируются при сортировке | Автоматически |

### Контекстные данные — полезны для понимания, но не автоматизированы

| Данные | Где | Для чего |
|--------|-----|---------|
| Research summaries | В brain export | Понимание, какие кейсы проводились |
| Skill metadata | В brain export | Понимание, какие скиллы есть и их trust tier |
| Pipeline metrics | В brain export | Понимание, сколько времени тратится на фазы |
| Trend detection | В `/learning-stats` | Понимание, становятся ли результаты лучше/хуже |
| Witness chain | `.witness-chain.json` | Аудит, целостность артефактов |
| BTO evaluation reports | В директории оценки | Понимание сильных/слабых сторон скилла |

### Правило большого пальца

> **Если данные имеют прямое влияние на `memory_query()`, загрузку скиллов, или модификацию файлов — это Actionable.**
>
> **Если данные нужно читать и интерпретировать человеку — это Context.**

## 11. Как улучшать скиллы в npm-пакете

### Проблема

Скиллы установлены через `npx @dzhechkov/keysarium`. Как propagate improvements обратно в пакет?

### Рабочий процесс

```
┌─────────────────────────────────────────────────────────┐
│  Ваш проект (потребитель)                                │
│                                                          │
│  npx @dzhechkov/keysarium init                          │
│       ↓                                                  │
│  .claude/skills/<name>/SKILL.md  ← локальная копия      │
│       ↓                                                  │
│  /casarium → /harvest → /bto-benchmark → /bto-test → /bto-optimize │
│       ↓                                                  │
│  Улучшенный SKILL.md (локально)                          │
│       ↓                                                  │
│  Тестирование на реальных кейсах (ещё N casarium runs)   │
│       ↓                                                  │
│  Если score стабильно ≥ 7.0 на 3+ кейсах:               │
│       ↓                                                  │
│  Contribute back → PR в dz-harness-hub           │
└─────────────────────────────────────────────────────────┘
```

### Шаг за шагом

**1. Локальная оценка и оптимизация:**
```
/bto-benchmark .claude/skills/goap-research-ed25519/
# BENCHMARK_SCORE: 0.72 — PASS (структурно OK, можно к судьям)

/bto-test .claude/skills/goap-research-ed25519/
# Score: 6.5/10

/bto-optimize .claude/skills/goap-research-ed25519/
# Score: 6.5 → 7.2 (+0.7)
```

> Если `/bto-benchmark` показал BLOCK (< 0.50) — исправляйте структурные проблемы до запуска `/bto-test`. Это экономит бюджет: benchmark стоит ~0, а `/bto-test` Layer 2 = 3 sonnet-агента.

**2. Валидация на реальных кейсах:**
Проведите 2-3 исследования `/casarium` с оптимизированным скиллом. Проверьте, что:
- Reward scores не ухудшились
- `/learning-stats` показывает stable или improving trend
- Реальное качество артефактов устраивает

**3. Contribute back (если вы — мейнтейнер пакета):**
```bash
# В репозитории dz-harness-hub:
cp <your-project>/.claude/skills/<name>/ packages/@dzhechkov/keysarium/skills/<name>/
# + обновить trust tier в .claude/rules/trust-tiers.md
# + обновить SKILL.md frontmatter (bto_score, bto_date)
# + commit + publish
```

**4. Contribute back (если вы — пользователь пакета):**
```
/brain-export all
# Отправить brain.json мейнтейнеру
# или создать PR с изменёнными файлами скилла
```

### Что именно менять в скилле?

BTO оптимизация модифицирует файлы скилла **in-place**. Типичные улучшения:

| Файл | Что улучшается |
|------|---------------|
| `SKILL.md` | Инструкции, workflow, output format |
| `modules/*.md` | Шаги выполнения, anti-patterns, edge cases |
| `references/*.md` | Quality gates, rubrics, golden samples |
| `templates/*.md` | Шаблоны выходных артефактов |

### Чего НЕ нужно делать

- **Не экспортируйте reward data для улучшения скилла** — reward data влияет на выбор подхода в runtime, а не на содержимое скилла
- **Не копируйте `.keysarium/memory/` между проектами** — используйте `/brain-export` + `/brain-import`
- **Не модифицируйте core протоколы** (`lib/*.md`, `packages/@dzhechkov/keysarium-core/`) — если нужно изменить протокол, это архитектурное решение, не результат обучения

## 12. Полный цикл: пошаговый чеклист

### После установки (однократно)

- [ ] `npx @dzhechkov/keysarium init` — установить основной пакет
- [ ] `npx @dzhechkov/skills-bto init` — установить BTO (для оценки и оптимизации скиллов)
- [ ] Ознакомиться с `CLAUDE.md` — понять pipeline

### После каждого исследования

- [ ] Запустить `/casarium [кейс]`
- [ ] Давать честную обратную связь на каждом checkpoint (reward learning = авто)
- [ ] После завершения: `/harvest researches/<slug>/`
- [ ] Просмотреть harvest findings, принять/отклонить

### Каждые 3-5 исследований

- [ ] `/learning-stats` — проверить тренды
- [ ] `/dream run` — запустить анализ паттернов (или проверить `/dream status`)
- [ ] `/bto-benchmark` на скиллах с низким reward — быстрая дешёвая проверка
- [ ] Если benchmark PASS → `/bto-test` — полная оценка с судьями
- [ ] `/bto-optimize` если test score < 7.0 — оптимизировать

### При переносе в новый проект

- [ ] `/brain-export all` — экспорт знаний
- [ ] В новом проекте: `/brain-import brain.json` — импорт
- [ ] `/learning-stats` — убедиться, что данные импортировались

### При публикации улучшений в пакет

- [ ] Убедиться, что BTO score ≥ 7.0 для изменённых скиллов
- [ ] Провести 2-3 реальных исследования с улучшенным скиллом
- [ ] Скопировать файлы скилла в packages/ репозитория
- [ ] Обновить trust-tiers.md, SKILL.md frontmatter
- [ ] Commit + publish
