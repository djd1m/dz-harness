# Проверенные знания для clean-code-error-and-boundary-handling

## clean-code-ch07-p133-ku01 — Отделяйте ошибки от основного сценария исключениями

Тип: decision-framework

Проблема: Нужно не перемешивать алгоритм операции с проверкой сбоя после каждого вызова.

Содержание: При обнаружении сбоя выбрасывайте исключение вместо кода возврата или флага. Вызов тогда показывает сам алгоритм, а реакция на ошибку отделена и читается отдельно.

Применимость: Применяйте к последовательным операциям, где несколько вызовов могут завершиться ошибкой.

Ограничения: Исключение не устраняет обработку, а выносит её из нормального пути в отдельную ветвь.

## clean-code-ch07-p134-ku02 — Сначала очертите опасную работу try-catch-finally

Тип: methodology

Проблема: Надо задать границу операции, которая может оборваться, и понять состояние после ошибки.

Содержание: Сперва поместите код, способный выбросить исключение, в try-catch-finally. Catch обязан оставить программу целостной при любом результате try; эта рамка заранее проясняет ожидания пользователя.

Применимость: Используйте для ввода-вывода и другой работы, которую может прервать ошибка.

Ограничения: Сравнение с транзакцией означает обязанность catch сохранять целостность, а не автоматический откат любых изменений.

Источник: Чистый код: создание, анализ и рефакторинг; ISBN 978-5-49807-381-1; глава 7; физические страницы PDF 134–134.

## clean-code-ch07-p135-ku03 — Проверяйте исключение тестом и развивайте try

Тип: methodology

Проблема: Нужно по шагам реализовать операцию с ошибками, сохранив её транзакционную границу.

Содержание: Создайте тест, намеренно вызывающий ожидаемое исключение. Введите минимальный код, на котором он падает, затем перехватите реальный сбой и добавьте поведение для успеха; после этого сузьте catch до фактического типа и развивайте нормальный путь внутри try.

Применимость: Подходит TDD-разработке операции вроде чтения файла, когда неудачный сценарий можно воспроизвести.

Ограничения: Нужен проверяемый способ вызвать сбой; широкий catch не остаётся оправданным, если уже известен реальный тип.

## clean-code-ch07-p136-ku04 — В приложении взвешивайте каскад проверяемых исключений

Тип: decision-framework

Проблема: Требуется выбрать проверяемое или непроверяемое исключение в цепочке вызовов.

Содержание: В приложении учитывайте стоимость checked-исключения: если catch находится несколькими уровнями выше, каждый промежуточный метод вынужден добавить throws либо перехват. Изменение снизу разрастается в каскад правок, сборок и развёртываний и раскрывает деталь сбоя на всём пути; обычно это перевешивает выгоду.

Применимость: Используйте в прикладном коде с многослойными вызовами и удалённой обработкой ошибок.

Ограничения: Особо важная библиотека может оправдать проверяемое исключение, когда вызывающего надо обязать его обработать.

Источник: Чистый код: создание, анализ и рефакторинг; ISBN 978-5-49807-381-1; глава 7; физические страницы PDF 136–136.

## clean-code-ch07-p138-ku07 — Оберните внешнее API и переведите его ошибки

Применимость: Применяйте при интеграции с внешним API, когда его ошибки в приложении обрабатываются одинаково.

Ограничения: Общий переведённый тип годится лишь при одинаковой реакции клиента; разные способы обработки требуют разных типов.

## clean-code-ch07-p139-ku09 — Пусть штатное отсутствие данных обработает особый объект

Проблема: Нужно убрать catch из бизнес-логики, когда для отсутствия данных есть допустимое значение по умолчанию.

Применимость: Используйте, когда отсутствие записи или результата имеет определённое предметной областью штатное поведение.

Ограничения: Не применяйте, если отсутствие обязано оборвать операцию или требует разных действий клиента.

## clean-code-ch07-p140-ku10 — Не перекладывайте null на вызывающий код

Применимость: Применяйте к методам, где отсутствие можно выразить ошибкой или штатным альтернативным объектом.

Ограничения: Исключение или особый объект выбираются по тому, является отсутствие ошибкой либо ожидаемым сценарием.

## clean-code-ch07-p141-ku12 — Не передавайте null в аргументах

Тип: heuristic

Проблема: Надо уменьшить случайные ошибки от null в параметрах вызова.

Содержание: По возможности не передавайте null в свой код; исключением бывают сторонние API, без этого не работающие. Переданный null может привести к NullPointerException, когда метод обращается к аргументу.

Применимость: Используйте при проектировании контрактов вызова и ревью клиентского кода.

Ограничения: Цитируемая страница не предлагает полного способа обработки случайного null; она показывает, почему передавать его хуже, чем возвращать.

## clean-code-ch08-p144-ku02 — Не отдавайте общий контейнер клиенту, которому нужны запреты

Тип: decision-framework

Проблема: Внешний интерфейс широк, а клиентской архитектуре требуется запретить часть операций или значений.

Содержание: Не передавайте общий Map, когда клиент не должен очищать контейнер или класть в него значения неподходящего типа. Универсальность поставщика и требуемая пользователю специализация сталкиваются на границе; контролируемый прикладной контракт должен выразить нужные ограничения.

Ограничения: Универсальный контейнер остаётся мощным и гибким, поэтому ограничение выбирается требованиями конкретной архитектуры, а не неприятием Map.

Приведения типов и реализация останутся внутри фасада, поэтому изменение внешнего API не потребует массово менять клиентов.

Применимость: Подходит интеграциям с Map и другими сторонними интерфейсами, не входящими в публичный контракт приложения.

Ограничения: Не нужно оборачивать каждый Map: задача состоит в сдерживании распространения границы, а не в оболочке ради неё.

Ограничения: Такие тесты проверяют ваше понимание и сценарий применения, но не делают команду ответственной за тестирование всего стороннего пакета.

## clean-code-ch08-p147-ku04 — Сохраняйте открытые особенности API в тестах

Тип: case-pattern

Проблема: Эксперименты с библиотекой выявляют скрытые требования к настройке и последовательности вызовов.

Содержание: Запустите минимальный сценарий, прочитайте ошибку, найдите следующую необходимую настройку и повторите опыт. Когда способ заработал, оставьте простые модульные тесты с полученным знанием о поведении API, а применение библиотеки перенесите в специальный класс, чтобы граница не расползалась по продукту.

Применимость: Полезно для логирования и других пакетов, где результат зависит от скрытой начальной настройки или аргументов конструктора.

Ограничения: Странность поведения не обязательно означает ошибку библиотеки; тесты лишь закрепляют найденный способ её применения.

Ограничения: Тесты не гарантируют, что сторонний код всегда сохранит совместимость; выход каждой новой версии создаёт новый риск.

## clean-code-ch08-p150-ku07 — Снижайте стоимость изменений на внешней границе

Проблема: Продукт опирается на код вне контроля команды, и его эволюция может стать дорогой.
