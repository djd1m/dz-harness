# Проверенные знания для clean-code-object-data-ownership

## clean-code-ch06-p123-ku01 — Прячьте представление за предметными операциями

Тип: decision-framework

Проблема: Требуется дать клиенту доступ к сущности, не привязывая его к формату её данных.

Содержание: Открывайте операции предметного уровня вместо чтения и записи конкретных полей. У точки можно независимо читать координаты, но менять согласованную пару одним вызовом; так декартово хранение можно заменить полярным, не меняя клиентский код.

Применимость: Подходит объектам с изменяемым внутренним представлением либо с несколькими значениями, образующими общий инвариант.

Ограничения: Интерфейс, приватные поля и accessor-методы сами по себе не скрывают реализацию: абстракцию нужно спроектировать по смыслу.

## clean-code-ch06-p123-ku02 — Показывайте клиенту состояние, а не единицы хранения

Тип: heuristic

Проблема: API отдаёт низкоуровневые показатели и тем самым раскрывает формат данных.

Содержание: Возвращайте смысловую величину, необходимую пользователю, вместо частей её расчёта. Процент оставшегося топлива скрывает объём бака и число галлонов, тогда как отдельные getters этих значений выдают устройство данных.

Применимость: Используйте в доменных интерфейсах, когда клиенту нужно судить о состоянии, а не получать измерения реализации.

Ограничения: Нужно продумать представление данных; простая замена полей accessor-методами ничего не решает.

## clean-code-ch06-p124-ku03 — Определяйте объект и структуру данных по их контракту

Тип: definition

Проблема: Нужно различить объект и структуру данных по тому, как они предоставляют состояние и поведение.

Содержание: Объект скрывает данные за абстракциями и предоставляет функции, работающие с ними. Структура данных открывает значения и не имеет осмысленных функций. Эти контракты дополняют друг друга и фактически являются противоположностями.

Применимость: Используйте при выборе между скрытым состоянием с операциями и открытыми данными без существенного поведения.

Ограничения: Цитируемая страница определяет различие контрактов, но ещё не задаёт правило выбора по направлению будущих изменений.

## clean-code-ch06-p125-ku04 — Сверяйте модель с осью будущих изменений

Тип: decision-framework

Проблема: Требуется выбрать между полиморфными объектами и структурами с внешними процедурами.

Содержание: При частом добавлении операций к стабильным типам выбирайте структуры и процедуры: новая функция не меняет эти структуры. Если ожидаются новые типы при устойчивых операциях, берите объекты: новый класс не требует менять существующие функции. Обратная стоимость остаётся: новый тип требует правок процедур, а новая операция — классов объектов.

Применимость: Подходит частям системы с ясным направлением развития: например, новым фигурам или новым расчётам для прежних фигур.

Ограничения: Посетитель и двойная диспетчеризация несут свои затраты и обычно возвращают проект к процедурному виду; они не устраняют этот компромисс.

## clean-code-ch06-p126-ku05 — Не делайте объектность универсальным правилом

Тип: heuristic

Содержание: Не принимайте принцип «всё объект» без выбора. Для расширения поведения над прежними данными уместны простые структуры с процедурами; для добавления новых видов данных — объекты. Решайте это в конкретной части системы, а не по идеологическим причинам.

Применимость: Используйте в сложных системах, где подсистемы развиваются по разным осям.

Ограничения: Ни один вариант не объявлен лучшим всегда: у каждого есть обратная цена расширения.

## clean-code-ch06-p127-ku06 — Ограничивайте метод прямыми знакомыми по Деметре

Тип: definition

Проблема: Надо сузить круг объектов, с которыми метод вправе общаться, чтобы не раскрывать чужую внутреннюю структуру.

Содержание: Метод класса C вправе вызывать методы самого C, объектов, созданных внутри этого метода, переданных ему аргументов и объектов в полях экземпляра C. Не вызывайте методы у объектов, возвращённых этими разрешёнными вызовами: это уже обращение к чужаку, а не к непосредственному знакомому.

Применимость: Подходит методам, которые работают с объектами, скрывающими своё внутреннее устройство.

Ограничения: Эвристика относится к объектам с поведением; на обычные структуры данных без поведения она не распространяется тем же образом.

## clean-code-ch06-p127-ku07 — Проверяйте цепочки вызовов на утечку структуры

Тип: checklist

Проблема: Программа идёт через ряд возвращаемых объектов ради одного итогового значения.

Содержание: «Крушение поезда» узнаётся по последовательным вызовам у результатов вызовов. Временные переменные делают эту зависимость заметной, но главный вопрос остаётся: промежуточные сущности — объекты или структуры? Для объектов такая навигация выдаёт их устройство и нарушает Деметру; для структур без поведения она естественна.

Применимость: Применяйте к переходам наподобие context → options → временный каталог → путь и к иным вложенным цепочкам.

Ограничения: Любая цепочка не является нарушением автоматически: решение зависит от природы промежуточных сущностей.

## clean-code-ch06-p128-ku08 — Не соединяйте объект и структуру в гибрид

Тип: heuristic

Проблема: Класс сочетает значимые операции с открытыми данными либо с getters/setters, фактически открывающими состояние.

Содержание: Не объединяйте объектный контракт со структурой данных. Гибрид приходится менять и во внешних процедурах при новом типе, и в самом классе при новой операции; он не защищает ни расширение типов, ни расширение функций.

Применимость: Используйте при ревью классов с бизнес-методами и открытыми полями либо accessor-методами с полным доступом.

Ограничения: Некоторые инфраструктуры и стандарты требуют accessors даже для структур; от этого структура не становится объектом с поведением.

Источник: Чистый код: создание, анализ и рефакторинг; ISBN 978-5-49807-381-1; глава 6; физические страницы PDF 128–128.

## clean-code-ch06-p129-ku09 — Поручайте объекту нужное действие вместо навигации

Тип: methodology

Проблема: Клиенту нужен результат, но он извлекает его, проходя через внутренние объекты и смешивая уровни абстракции.

Содержание: Определите итоговое действие и передайте его объекту-владельцу. Вместо получения пути временного каталога, склейки строк, добавления расширения и создания потока дайте контексту операцию создать поток файла по имени. Владелец сохранит строение скрытым, а клиент перестанет путешествовать по чужим объектам.

Применимость: Подходит цепочкам доступа, после которых вручную собирают ресурс из путей, строк, расширений и инфраструктурных типов.

Ограничения: Отдельный getter допустим, только когда возвращает структуру данных, а не объект; у обоих getter-вариантов есть собственные неудобства.

Ограничения: Навигационные методы Active Record не делают её подходящим местом для бизнес-логики: она остаётся структурой данных.

Применимость: Подходит классам, соединяющим данные или операции с независимыми причинами эволюции.

## clean-code-ch10-p169-ku03 — Организуйте систему сетью малых однозначных классов

Тип: decision-framework

Проблема: Команда боится, что многочисленные специализированные классы скроют общую картину.

Содержание: Не сохраняйте разнородные обязанности в нескольких крупных классах лишь ради уменьшения числа классов. Сложность никуда не исчезает; сеть малых классов помогает быстро найти нужное и знать только локальную часть работы. Каждый класс удерживает одну ответственность и взаимодействует с другими ради поведения системы.

Применимость: Используйте в сложных системах, где многоцелевые классы вынуждают изучать детали, не относящиеся к задаче.

Ограничения: Это не уменьшает объём логики, а организует её в чётко определённые части.

## clean-code-ch10-p170-ku04 — Оценивайте границы класса по связности

Тип: heuristic

Проблема: Надо понять, составляют ли поля экземпляра и методы одно целое.

Содержание: Добивайтесь высокой связности: операции используют хотя бы часть общего состояния, а поля и методы поддерживают друг друга. Ситуация, когда каждый метод касается каждого поля, обычно недостижима и не нужна. Чем больше полей использует метод, тем сильнее он связан с классом.

Применимость: Используйте, чтобы оценить, насколько методы и переменные экземпляра взаимозависимы и существуют как единое целое.

Ограничения: Высокая связность не означает обязательного обращения каждого метода к каждому полю; это крайнее состояние обычно нереально.

Источник: Чистый код: создание, анализ и рефакторинг; ISBN 978-5-49807-381-1; глава 10; физические страницы PDF 170–170.

## clean-code-ch10-p171-ku05 — Выделяйте класс из функций с общим состоянием

Тип: methodology

Проблема: При дроблении большой функции несколько малых частей используют общий набор локальных значений.

Содержание: Чтобы не передавать все общие значения длинным списком параметров, сначала преобразуйте нужные локальные переменные в поля исходного класса и извлеките малую функцию. Затем оцените связность: если эти поля используются только отдельной группой функций, вынесите соответствующие поля и методы в новый, более связный класс.

Применимость: Подходит рефакторингу больших функций с множеством локальных значений и подзадачами, использующими разные подмножества.

Ограничения: Превращение локальных значений в поля может снизить связность исходного класса; это повод продолжить выделение, а не конечный дизайн.

Исходников может стать больше из-за понятных имён, объявлений и форматирования, хотя алгоритм и механика сохранятся.

Применимость: Используйте для монолитных процедур, смешивающих оркестрацию, представление результата и вычисления.
