# Step 8: Quality Engineering

### Native history through the installed CLI

For an explicitly native review, use the actual installed producer before dispatching any formal QE role:

```bash
dz qe-rounds --source native --action prepare --project "$REPO" --feature-dir "$FEATURE" --reviewers '[{"id":"qe-primary","family":"codex"}]' --json
```

Bind the actual selected families and use the returned full roster, nonce and revision in the existing QE receipt at `feature/.fa-state/review-convergence-qe-review.json`. An owner-approved family exception must use `owner-exception` and preserve its explicit approval. Call `dz qe-rounds --source native --action evaluate --project "$REPO" --feature-dir "$FEATURE" --json` after actual independent review; missing or incompatible installed core/helper capabilities are NOT ESTABLISHED. No project-local module search, helper override, automatic installation or fake bridge evidence is allowed.

Native history fixes the ceiling at three witnessed cycles, including partial and unresolved originating reviews. Multiple roles, fallback, repeated prepare/evaluate and restart share one cycle. Prepare may refresh artifacts before a review originates. After witnessing, a measured code/design change requires explicit `--action begin-repair` with the actual roster before another review; unchanged third-cycle completion may finish, while a fourth opening is refused. The ceiling applies to formal feature review as well as focused roles. Do not evade it by changing family, host, source or nonce. No-verdict attempts are reported separately. Native `--ceiling` is refused.

Omit `--action` for read-only native reporting; omitted `--source` retains the historical bridge reader. Locally bound native/bridge collisions refuse either selection with both locations rather than unioning or resetting. A reviewed legacy QE host cannot retrospectively initialize a zero history. Initial admission allows only the documented surviving-evidence matrix; parseable ideation state alone is permitted.

The helper runs at most four Git calls before locking (2s and 4 MiB per call), then rechecks bounded authoritative bytes, index, directory candidates and known artifacts in one short directory-lock transaction. Limits are 256 artifact paths, 2 MiB per artifact, 16 MiB aggregate artifacts, 256 KiB host/receipt/head, 2 MiB checkpoints, a separate 4 MiB index metadata fence, 8 MiB journal, 1024 events and 256 directory candidates. The 2s monotonic budget is checked before authoritative writes; lock stale/timeout are explicitly 30s/5s. Returned late I/O refuses, but synchronous I/O cannot be interrupted. This fenced observation does not serialize arbitrary external editors or prove reviewer authenticity or deletion of all writable evidence. Commit failures preserve paths and report possible partial writes; never delete authority or reconstruct zero to resume.

## Review convergence gate (Plain and native Workflow)

Review follows **initial review → host rework → focused verification → closure**, or explicit owner
escalation. A grade/GO label does not establish closure. Run the same installed Node gate before
planning (phase `ideation`) and before Step-8 completion/delivery (phase `qe`), including resume.

The host prepares a measured artifact snapshot BEFORE independent review. Resolve the executable
from this installed skill's `scripts/check-review-convergence.mjs`; do not use a scratch replacement.
For example, from the execution project, using the actual originating role/family:

```bash
node "$FEATURE_ADR_SKILL/scripts/check-review-convergence.mjs" prepare \
  --repo "$EXECUTION_PROJECT" --feature "features/$FEATURE_SLUG" --phase ideation \
  --reviewers '[{"id":"qcsd","family":"owner-exception"}]'
node "$FEATURE_ADR_SKILL/scripts/check-review-convergence.mjs" evaluate \
  --repo "$EXECUTION_PROJECT" --feature "features/$FEATURE_SLUG" --phase ideation
```

The ideation example above is illustrative; QCSD uses its three actual core role entries. For QE use `--phase qe` and the actual `qe-primary` reviewer, plus `qe-precision` when configured.
`family` is `codex`, `claude`, or an explicitly authorized `owner-exception`. Existing family/routing
policy remains binding; this receipt does not authorize an exception. Only the host calls `prepare`.
It retains originating reviewer roles and prior condition meanings in the existing feature checkpoint
`.fa-state/review-convergence-<phase>-host.json`; neither the latest report nor an empty request array
can replace that lineage. Do not edit/delete host lineage to obtain a clean bootstrap. A new nonce is
issued when measured bytes/path membership change; repeated preparation cannot remove conditions. Pending changed paths accumulate across every prepare, including path additions/deletions, until an established closure; failed/refused evaluations never clear them.

The snapshot measures requirements, every direct ADR, architecture, and other available design
inputs. QE also measures the plan, ideation report, every declared target, and host-discovered Git
changes/additions/deletions against `.fa-state/base-ref` (HEAD when absent). Receipt/checkpoint files,
QE report and generated `architecture/map.json` are outputs excluded to avoid circular hashes.
Explicit planned deletions carry a null digest. Traversal, symlinks and non-files refuse. The host
must include relevant unchanged dependencies in declared targets; hashing cannot discover semantic
dependencies. Parallel Workflow design may change after ideation review: that stale review pauses
before planning and needs focused review of the settled snapshot.

Each independent reviewer writes its OWN entry, preserving other reviewer entries and the actual
author handoff, in `.fa-state/review-convergence-<phase>-review.json`. A genuinely clean initial
review needs no invented condition or extra review. Its complete receipt shape is:

```json
{
  "schema": "fa-review-convergence-1", "phase": "ideation",
  "nonce": "<copy host snapshot nonce>", "revision": "<copy host snapshot revision>",
  "author": null,
  "reviews": [{
    "reviewer": "qcsd", "family": "owner-exception", "independent": true, "verdict": "clean",
    "conditions": [], "verifications": [],
    "newRisks": {"assessment": "none identified after complete scope review", "evidence": "<actual review evidence>", "conditions": []},
    "authorAssessmentChecked": false, "deltaVerification": null
  }]
}
```

`verdict` is `clean`, `conditional`, or `no-go`. Conditions have closed fields
`{id, owner, severity, classification, requirement, scope, evidence}`: stable unique ID, originating
role ID, BLOCKER/CRITICAL/HIGH/WARNING/SUGGESTION, structural/wording, exact acceptance meaning,
nonempty repo-relative scope paths, and original evidence. Carry every prior own condition unchanged
on every pass. Reviewer verifications have closed fields
`{id, revision, classification, evidence, implementationVerified}`. Only the originating independent
role can verify its own condition at the current revision; author/lead/scribe assertions cannot.

`implementationVerified` is phase-specific for both condition verifications and
`deltaVerification`. In phase `ideation`, structural `implementationVerified:true` means the
originating independent reviewer verified the corrected ADR, architecture and phase artifacts at
the current revision/nonce; it does not claim production code or implementation tests exist. In
phase `qe`, structural `implementationVerified:true` requires independent verification of the
actual implementation and relevant tests at the current revision/nonce. False or missing structural
verification remains blocking in both phases. Field names, boolean strength, originating ownership,
phase/nonce/manifest binding and legacy receipt compatibility are unchanged.

Rework requires the actual author object
`{addressed, changedScope, classification, delta, evidence, newRisks}`. Addressed IDs name prior
conditions; changedScope includes ALL host-measured changes and affected dependencies. Delta/evidence
explain the actual fix. Both author and reviewer `newRisks` require explicit assessment/evidence and a
conditions array, including an explicit none-identified assessment when empty. The reviewer must set
`authorAssessmentChecked:true` and supply independent
`deltaVerification:{classification,evidence,implementationVerified}`. Structural changes affect
behavior, contracts, safeguards, architecture or acceptance meaning and require phase-specific
structural verification as defined above. Wording changes affect expression only; the independent
reviewer checks that classification, so an author's wording label cannot weaken structural verification.

Focused scope is outstanding conditions plus actual changes and affected dependencies. New serious
risks always expand that scope. Retain ALL conditions and serious primary/precision findings until
own-reviewer verification; a token/round ceiling escalates unresolved risk, never approves it.

Gate exits: 0 with `prepared` (prepare only) or `closed` (evaluate only); 1 `unresolved`; 3
`not-established`. Inspect the structured reasons/unresolved IDs. Missing executable/report, malformed
or contradictory output, foreign/duplicate/omitted conditions, stale phase/nonce/manifest or unavailable
reviewer refuses. Native Workflow strictly checks stdout AND exit before planning and before
completion/delivery/success tags. Supported native/Mode-B/fallback/precision reviewers receive this
contract; the read-only Codex mode-A route cannot accept it and pauses for a supported independent
review. A scribe never creates reviewer evidence from grade. Historical resume without this contract
needs fresh evidence; resume rechecks bytes and every configured route, including unwitnessed precision.

Host prepare first reads the existing reviewer receipt, including valid partial own entries written
before an agent/transport failure. It preserves independently written conditions under their original
role/family before binding any actual fallback. This imports findings, never closure or author/scribe
claims. A stale receipt cannot originate new host conditions; known prior meanings remain immutable.
`pending-reviewer-receipt-needs-origin-review` pauses before native fallback dispatch when pending
evidence cannot be reconciled. Keep the original receipt and host lineage. Have its originating
reviewer repair malformed/foreign fields or refresh unknown stale own findings at the unchanged
host identity/current snapshot. Repeat prepare for the selected actual base-role families, complete
the returned full reviewer roster with actual own verification, then evaluate and resume the same
slug. No receipt/lineage deletion or relabeling is a recovery action. The existing QE checkpoint
validator rejects a paused non-QE result, so same-slug resume re-enters only that reviewer stage;
unrelated coder checkpoints remain eligible for reuse.

Bind the actual fallback family with host prepare BEFORE reviewer dispatch. An unused role may change family; once review evidence originated, its role/family and prior conditions remain required, and the new family receives a distinct `<base-id>:<family>` role. Reviewers read the returned full roster and never relabel old ownership.

On refusal, the host settles artifacts, calls prepare with the selected actual base-role families, supplies
the author handoff, requests focused own-condition verification, then evaluates and resumes the same
slug. This is host-driven repair, not an automatic repair loop. Existing Confirmation, amendment,
scope, testing, independent-family and budget gates remain conjunctive. This gate establishes receipt
consistency and current artifact binding, not semantic truth or authenticated reviewer identity.

For a same-slug QE resume blocked by historical serious findings, read-only mode A, or an
unwitnessed precision append, preserve the complete original checkpoint, findings and grades.
Prepare returns `checkpointDigest`: SHA-256 of `JSON.stringify` of the latest `qe` result in
`.fa-state/checkpoints.jsonl`. Each actual originating reviewer supplies optional closed-field
`checkpointVerification:{checkpointDigest,evidence,supported:true,route,findings,reportDigest}`
in its own review entry, in addition to the ordinary current-revision independent verification.
`route` is native/mode-b/fallback and evidence describes the actual supported focused review;
mode A, author/scribe flags, or the old grade cannot establish this proof. `findings` maps EVERY
original serious gap with `{digest,conditionId}`, where digest is SHA-256(JSON.stringify(gap))
and conditionId names that reviewer's preserved serious condition with its current structural
implementation verification. Both primary and precision origins must verify their own findings.
Use `reportDigest:null` normally; an unwitnessed precision append requires that originating
precision reviewer to verify the actual complete `08_qe_report.md` and supply its SHA-256.
The report must contain Primary QE pass, Precision QE pass, and Combined Step-8 grade sections.
Then evaluate with the same phase/repo/feature and re-invoke the same slug. Only a closed gate
with complete checkpoint binding can reconcile historical refusals on an actual resumed QE stage;
live findings, changed checkpoints/artifacts and a failed Confirmation gate still block delivery.
This procedure runs no coder or automatic repair loop, and retains the historical result for audit.

### 3. Code Review via Brutal Honesty Review (M+)

> Load: `references/agentic-qe/brutal-honesty-review.md`

Apply the **brutal-honesty-review** protocol from agentic-qe (Tier 2: Validated).

#### Mode Selection

Choose review mode based on context:

| Mode | When | Style |
|------|------|-------|
| **Linus** (technical precision) | Code has architectural/performance issues | "You're holding the lock for the entire I/O. Did you test under load?" |
| **Ramsay** (standards-driven quality) | Tests or quality is subpar | "15 tests, 14 happy path. Where's the edge cases?" |
| **Bach** (BS detection) | Architecture decisions seem cargo-cult | "Why are you using microservices for a single-user tool?" |

**Default mode**: Linus for code review, Ramsay for test review.
**Calibration**: Level 1 (Direct) — professional and actionable.

#### Review Structure (per finding)

```markdown
## What's Broken
[Surgical description — specific file, line, function]

## Why It's Wrong
[Technical explanation with evidence, not opinion]

## What Correct Looks Like
[Clear model of excellence — code example or pattern reference]

## How to Fix It
[Actionable steps, specific to this codebase]

## Why This Matters
[Impact if not fixed — security, performance, maintainability]
```

#### Review Dimensions (weighted)

| Dimension | Weight | Mode | Questions |
|-----------|--------|------|-----------|
| **Correctness** | 30% | Linus | Does it do what requirements say? Edge cases handled? |
| **Security** | 20% | Linus | Injection risks? Auth bypasses? Data exposure? |
| **Maintainability** | 20% | Ramsay | Readable? Follows patterns? Future-proof? |
| **Performance** | 15% | Linus | N+1 queries? Unnecessary allocations? Missing indexes? |
| **Consistency** | 15% | Ramsay | Matches codebase conventions? Naming consistent? |

#### Review Process

1. **Read every changed file** completely
2. **Check against requirements** — is anything missing or extra?
3. **Check against ADR decisions** — does code match chosen approach?
4. **Check against architecture** — do components match diagrams?
5. **Check against QCSD ideation risks** — are `{QUALITY_RISKS}` from Step 3.5 mitigated?
6. **Flag issues** with severity:
   - 🔴 **BLOCKER** — must fix before merge (Linus mode: "This is completely broken")
   - 🟡 **WARNING** — should fix, but not blocking (Ramsay mode: "This is RAW")
   - 🔵 **SUGGESTION** — nice to have improvement

### 3.1 ADR Fitness Checklist Gate (M+)

Before final grading, read every generated ADR in `features/<slug>/03_adr/NNN-*.md`.

Fail the ADR gate for any miss:

| Check | Required Evidence |
|-------|-------------------|
| Decision-shaped title | Title names one concrete decision, not a vague topic |
| One decision per ADR | No bundled independent decisions |
| Filename discipline | `03_adr/NNN-{decision-slug}.md`; slug is lowercase kebab-case, imperative, dateless, ticketless |
| Status vocabulary | `proposed`, `accepted`, `rejected`, `deprecated`, or `superseded` |
| Reversibility clause | Status states when/how to revisit or why it is irreversible |
| Neutral Context before Decision | Context states problem/forces without advocating the chosen solution |
| Drivers ranked or weighted | Decision Drivers are explicit and prioritized |
| Considered Options | Chosen and rejected options are present |
| Symmetric pros/cons | Each option has real strengths and weaknesses; no strawman loser |
| Rationale maps to drivers | Every rationale point names the driver it satisfies and why rejected options lost |
| Concrete/testable Decision | Exact names, versions, formats, paths, commands, APIs, or conventions |
| Negative consequences | Consequences include accepted downsides/risks, not only benefits |
| Follow-up discipline | Consequences link follow-up ADRs or state none; after-action review is scheduled |
| Confirmation stanza | Names verification method, monitoring, success metric, and owner |
| Confirmation-to-test link | The named load-bearing property has a real automated test/fitness check by file/name |
| No placeholders | No `TODO`, template hint text, raw prompt/generation scaffold, or empty tail sections |

Reject explainer-masquerading-as-ADR: if the document describes a problem space or technology landscape but has no concrete `Decision`, record a BLOCKER.

The Confirmation-to-test link is load-bearing. If absent, grade no better than C and record a blocker gap; for architecture dependency/layering/interface rules, recommend an ArchUnit or ArchUnitTS fitness function.

### 3b. Amendment Gate (P2 — amendments inherit the Confirmation discipline)

**Do not judge this yourself — RUN the check.** Resolution of every `AM-N` row to a real test is a
deterministic question, and a deterministic question must not live in prose (cost-of-detection ladder).
It used to live here, and `features/qe-scoped-review` shipped with five named amendment test ids of
which none existed, while its plan recorded `## Amendments: None`.

```bash
dz amendment-check --slug <feature-slug> --json      # or --feature-dir <abs path>
```

| Outcome | Exit | What it means for the gate |
|---|---|---|
| `pass` | 0 | every row resolves to a test found inside the file the row names |
| `skip` | 0 | no `## Amendments` section — an absence, stated, never a silent pass |
| `fail` | 1 | a HIGH gap: quote every reason verbatim into the QE report |
| `not-established` | 3 | the grammar matched nothing, or the inputs were unreadable — **never a pass** |

Empty stdout, a crash, or a missing `dz` is `not-established`, not a clean gate.

**What the command does NOT prove:** that a resolved test discriminates. Vacuity stays yours, in the
SAME `dz discrimination-check --test <f1,f2,...> --base HEAD --json` run as the ADR property test — an
amendment test that stays green at pre-feature base proves nothing about its amendment. A **safeguard**
amendment additionally needs its test to prove the safeguard FIRES on a real input: a structurally-dead
safeguard passes an existence check and never fires in production.

This closes the distance between "we caught the design flaw" (challenge-panel/QCSD) and "we proved the
fix works".

### 3c. I/O-on-pure-path + fixture-swap hunt (P5)

In the TEST diff, hunt for replacements of broken/unbound fixtures with healthy ones — the old fixture was
probably a **negative control** proving a path was I/O-free; each such swap requires a compensating
negative resource-down test. In the CODE diff, hunt for new I/O (DB/network/file) on previously-pure
paths — especially startup/lifespan/health: require a negative resource-down test (broken resource → the
path degrades per its declared contract: fail-open for advisory, explicit fail-fast for load-bearing).
Missing → HIGH gap.

### 5. Gap Detection Loop (M+)

After review findings are compiled, run a gap check:

```
ITERATION {N}:
  1. Check: Every FR-{N} from requirements → has passing test or verification
  2. Check: Every ADR decision → reflected in code
  2a. Check: Every ADR Confirmation load-bearing property → has a named automated test/fitness check
  3. Check: Every critical risk from QCSD → has mitigation in code
  4. Check: Every 🔴 BLOCKER → has fix plan

  If gaps found:
    → List gaps explicitly
    → Fix gaps (return to Step 7 for code changes if needed)
    → Re-run smoke tests
    → Increment iteration counter

  If no gaps:
    → Proceed to acceptance criteria validation

  Max iterations: 3. After 3 iterations, flag remaining gaps for user decision.
```

**Do NOT count the iterations yourself — ASK.** Before starting another rework round, run:

```bash
dz qe-rounds --slug <slug>
```

`0` under the ceiling, another round is within budget · `1` **STOP** — the ceiling is reached, the
remaining gaps go to the owner · `2` NOT ESTABLISHED, which is never "zero rounds".

It reads what `dz qe-bridge` already wrote and records nothing of its own, so it answers correctly
across restarts and for runs already past.

**Why this is a command and not a sentence you remember.** Until 2026-08-27 this rule existed ONLY as
the line above: `grep -rl 'ReviewScope|scopeId|findingId|lineage'` over harness-core and harness-cli
returned nothing, so there was no counter anywhere. Every restart of the agent forgot the sentence.
MEASURED cost on real data: one slug reached **38** graded rounds and 4 attempts with no verdict,
against a ceiling of 3. A rule at layer 4 of the cost-of-detection ladder fails silently — nobody
complains that the ceiling was missed, it is simply never reached.

This loop implements the "did we miss something?" recursive check from the original pipeline spec.

### 7.1 Findings ledger (machine-readable)

Prose is for people; `dz score`/`dz recap` need a machine-readable surface too (qe-findings-record,
ADR-001). Write BOTH of these into `08_qe_report.md`, in addition to the prose report above:

1. Exactly ONE line, in the PROSE body of the file (never inside a fenced code block, an indented
   code block, a `>` blockquote, or an HTML comment — the parser masks all four before it looks):
   `QE-VERDICT: <A|A-|A+|B|B+|B-|C|C+|C-|D>` — the letter grade you gave above, machine-parseable,
   ASCII hyphen for the sign (the parser also accepts U+2212 as the same sign; write ASCII). Two such
   lines make the report `ambiguous`, never "last wins" — write it once. A line that starts with
   `QE-VERDICT` but gets the grammar wrong (wrong dash, trailing prose, wrong case, no colon) is worse
   than writing nothing: the parser reports `invalid` and REFUSES to fall back to guessing a grade
   from prose — get the one line right rather than close.
2. A `## Findings ledger` section — this exact heading, occurring EXACTLY ONCE in the file, at the
   top level (never inside a fence/indented block/blockquote/comment either) — with a table directly
   under it, under this EXACT header (copy it verbatim):

```markdown
## Findings ledger

| Finding | Severity | Status | Round | Author | Title |
|---------|----------|--------|-------|--------|-------|
| F1 | HIGH | fixed | 1 | codex | escaping bug in the token scanner |
| F2 | MEDIUM | open | 1 | lead | style nit, not blocking |
```

A table found ANYWHERE else — before the heading, after the section ends at the next heading, with
no heading in the file, or with the heading duplicated — is REFUSED as `outside ledger section`,
never parsed as the real ledger; a second table found INSIDE the section is REFUSED as `duplicate
table`. Both refusals name how many of the rejected table's rows were ignored.

Closed dictionaries — a row using anything else is REFUSED by the parser, never coerced to the
nearest known value:
- **Severity**: `BLOCKER` `CRITICAL` `HIGH` `MEDIUM` `LOW` `INFO`
- **Status**: `confirmed` `fixed` `partial` `refuted` `named-limit` `open`
- **Round**: an integer ≥ 1 (which review round raised it)
- **Author**: `codex` `claude` `lead`
- **Finding**: a short id token with no spaces (`F1`, `R2-3`, …); **Title**: free text — a literal
  `|` inside Title must be escaped as `\|`, or wrapped in inline code (`` `a|b` ``), or it fragments
  the row into extra columns and the row is refused as malformed.

An empty (header-only) table is read as `hollow: true` — worse than no table at all, because it
claims a ledger exists and says nothing. If there are no findings, omit the section entirely rather
than writing an empty table.

### 7.2 Ledger row for this QE step (mandatory)

Plain mode (this SKILL, not the ultracode `Workflow`) has no in-process `appendRunCostRow` — without
this step the QE instrument's own pass leaves ZERO trace in the run-cost ledger (aqe-ledger-row,
owner audit 17.09, decision #3).

**Resume guard — check this FIRST, before writing anything.** If QE was RESTORED from a checkpoint
for THIS run (`features/<slug>/.fa-state/checkpoints.jsonl` already contains a line for stage `qe`
that matches this run) — the row for this review was already written by the run that actually did
it. Do **NOT** run the command below in that case; instead write exactly this line into
`08_qe_report.md`: `qe ledger row skipped — stage resumed`. Writing the row anyway would double-pay
the same review in the ledger (aqe-ledger-row fix-round-1/#3, Codex r1 HIGH #3 — plain mode had no
resume guard at all before this).

Otherwise — QE ran fresh in this pass — after `08_qe_report.md` is written and the grade is final, run:

```bash
dz feature-adr-record --kind ledger --stage qe --slug <slug> --row '<json>' --json
```

fix-round-1 (Codex r1 HIGH finding 4, ADR-001 D5): no `--auto` here. `--auto` is the trusted marker
of an AUTOMATED pipeline run and requires an experiment envelope that the manual path does not have;
this plain-mode row is written without it.

`<json>` carries the same fields the ultracode pipeline writes for this row: `reviewer` (the model
that reviewed, or `null` if unknown — never guessed), `reviewerFamily` (`claude`|`codex`|`null` when
the reviewer identity is not one of the two known families — never guessed as `claude`), `qeRole`
(`qe-code-reviewer` for a Claude reviewer; `codex-review`/`codex-exec` for a codex reviewer by scope
mode; `null` otherwise), `grade`, `gradeSource` (if known), `findings` (gap count), `findingsBySeverity`
(normalized `sev` -> count, unknown severities counted as `other`, never dropped), `findingsSource`
(`gaps` or `no-gaps-array`), `claimCheck` (if run), `crossFamily` (bool: reviewer family != coder
family — `null` when either family is unknown, since a same/cross-family verdict cannot be asserted
without both), `qeScope` (if the reviewer ran scoped, e.g. codex `mode`/`ref`/`files`). Insert the
writer's verdict (`{verdict:"written"|...}`) verbatim into `08_qe_report.md` so the record is
auditable from the artifact itself. NAMED LIMIT (layer 4 of the cost-of-detection ladder, said
honestly): this step is a skill instruction, not a code gate — nothing forces the agent to run it or
to check the resume guard first; only its PRESENCE in this module is deterministically pinned (grep
for the command above and for the resume-guard sentence).

### 8. QE Pattern Store (Direct Mode only)

When `{AGENTIC_QE_MODE}` = `direct` | `direct-extended`, after the gap loop is closed and the verdict is set:

```
mcp__agentic-qe__memory_store({
  key: "patterns/feature-adr/qe/{timestamp}",
  namespace: "learning",
  value: {
    pattern: "<one-sentence lesson from this QE run>",
    confidence: <honest 0-1 derived from the gap loop>,
    type: "qe-outcome",
    metadata: { tier: "{COMPLEXITY_TIER}", gaps_found: <N>, verdict: "<READY|NEEDS_FIXES|CONDITIONAL>" }
  },
  persist: true
})
```

Confidence must be honest — derived from the gap loop, never a fabricated 1.0
(e.g. zero gaps in one iteration ≈ 0.9; gaps remaining after 3 iterations ≤ 0.4).

Then persist the SAME lesson durably (the aqe kv store is ephemeral across MCP-server
restarts — observed live; the dz lexical store is the half that survives):

```
dz teach "<the same one-sentence lesson>" --reward <same confidence> --domain feature-adr \
  --type <success-pattern if verdict READY, else lesson-learned>
```

Non-blocking: if `dz` is not on PATH or the command fails, note it and proceed.
Non-blocking: a write failure is logged and the pipeline continues.
