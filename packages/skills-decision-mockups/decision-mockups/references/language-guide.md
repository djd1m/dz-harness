# Язык страницы решений

Все примеры ниже синтетические. Учебный сервис записи на занятия не представляет
работающий продукт; стоимость изменений задаётся в условии, а не измеряется по чужой работе.

## Для нетехнического адресата

1. Вводите бытовую картинку раньше нового термина; используйте одну аналогию на понятие.
2. Называйте действие и последствие для человека. «Нарушен принцип» не объясняет ущерб.
3. Внутренние имена оставляйте в скобках для инженера, который продолжит работу.
4. Пишите числа с единицей и источником. Учебные оценки помечайте как условия примера.
5. Каждая карточка отвечает: что не так → чем грозит → как чиним.
6. У каждой живой альтернативы есть цена, выигрыш и условие, при котором её стоит выбрать.

## Плохо → хорошо

### Дата занятия спрятана

- Плохо: «В карточках нет нормализованного temporal label».
- Хорошо: «Список похож на афишу без дат: часы указаны, а день виден только внутри занятия.
  Добавим день рядом со временем, чтобы ученик мог сравнить занятия без лишних переходов».

Смысл сохраняется без названия поля. Если имя полезно исполнителю, допишите `(lessonDay)`.

### Напоминание приходит поздно

- Плохо: «Надо сдвинуть scheduled notification на T−48h».
- Хорошо: «Письмо приходит утром в день занятия — как приглашение перед самым выходом.
  Предлагаем напоминать за два дня, чтобы ученик успел выделить время на дорогу».

Цена продолжает объяснение: два дня работы, при переносе занятия понадобится ещё одно письмо.
Утреннее письмо остаётся полезным, когда расписание часто меняется, а ехать недалеко.

### Материалы перечислены неясно

- Плохо: «Развести required и optional inventory в UI».
- Хорошо: «Список материалов похож на список покупок без пометок: непонятно, что обязательно.
  Разделим его на „принести с собой“ и „можно взять в мастерской“».

### Выбор способа оплаты

- Плохо: «Настроить settlement policy».
- Хорошо: «Оплата заранее помогает организатору купить материалы. Оплата на месте удобнее
  ученику, который ещё не уверен, что сможет прийти. Это два рабочих плана с разными рисками».

Не выдавайте удобство одной стороны за выигрыш для всех. Назовите трудозатраты и риск отмены
для обеих веток. Не рисуйте интерфейс, если решение касается только момента расчёта.

### Непроверенная находка

- Плохо: «Проблема точно воспроизводится у всех».
- Хорошо: «В условии примера ученик не видит день в списке. Проверок на реальных учениках
  не было; макет показывает предложенное изменение, а не результат такого исследования».

## Смена адресата

Для организатора объясняйте влияние на запись, посещение и подготовку материалов.
Для команды разработки можно вынести технические имена из скобок и сократить очевидные
аналогии. Сначала выясните адресата, не меняйте регистр самовольно.

Структура остаётся одинаковой: три строки находки, настоящие альтернативы, стоимость,
основание рекомендации, условие полезности другой ветки, честный статус проверки.
Экспорт по-прежнему должен быть понятен в свежем чате. Адаптация адресата не разрешает
прятать цену или превращать заранее решённый вопрос в голосование.

## Слова и доступность

Предпочитайте «запуск», «среда исполнения», «ключи доступа», «сборка», «публикация»
вместо технических калек. Словарь G15 в `check_page.py` ловит часть таких слов;
остальное проверяйте чтением вслух. Если специальное слово действительно нужно,
сначала объясните действие. Например: «помощник по расписанию („воркер“) отправляет письма».

Калька может совпасть с обычным словом. Для буквального медицинского контекста
`<!-- calque: слово относится к повреждению ткани -->` объясняет исключение на строке.
Качество причины остаётся предметом ревью; не используйте оговорку для сокрытия жаргона.

Разметка вариантов — кнопки с `aria-pressed`, поведение — один выбор в группе.
Не обещайте управление стрелками или полную radio-семантику, которых в пикере нет.
Дайте группе `aria-label` с вопросом, чтобы варианты не звучали без контекста.
