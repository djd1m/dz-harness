# Cloud.ru tools in Codex, Hermes, OpenCode and Pi

`cloudru-hub mcp-safe` is the common process boundary. It starts only the binary whose SHA-256 matches the package pin and the classification baseline. Its default profile advertises the 78 golden `allow` tools and rejects `ask`, `deny`, unknown tools and unsupported MCP methods before forwarding a call. Some planning tools may still write local plan files. Filesystem and shell access granted separately to an agent remain outside this MCP boundary.

Installers default to the smaller `inventory` toolset (11 tools). Select comma-separated groups with `--toolsets inventory,billing`; the available groups are `inventory`, `compute`, `kubernetes`, `data`, `network`, `storage`, and `billing`. `--toolsets all` exposes all 78 allow-classified tools. The proxy checks the chosen set on every `tools/call`, so a tool hidden from discovery cannot be invoked directly.

For the read-only billing tools, put `agreement_id` in the same owner-only credential file as `key_id`, `secret` and `project_id`, then select `--toolsets billing` or `inventory,billing`. The safe proxy passes `agreement_id` to the Go engine as `CLOUDRU_AGREEMENT_ID`; Codex installation inherits the credential-file path and billing environment variables. If the file is absent, an existing environment-only setup still works. An explicitly configured but missing or invalid file is an error. `billing_consumption` currently returns an agreement-wide aggregate. The Cloud.ru API documents project filtering, but this adapter has not implemented or live-verified that filter; do not label its total as a project-only charge.

The separate `--toolsets vm-deploy` profile allows one reviewed VM plan and remote commands on the VM returned by that plan. Put temporary credentials in `~/.config/cloudru-hub/credentials.json` (owner-only mode `0600`) as `{"key_id":"…","secret":"…","project_id":"UUID","region":"ru.AZ-2"}`. The proxy reads JSON directly and passes values to the pinned Go child as environment variables; it never runs shell `eval`. The region may also be a zone UUID. After `deploy_plan` returns a persisted plan, inspect its VM shape and RUB/month estimate, then run `cloudru-hub approve --plan-id <id> --max-monthly-rub <cap>`. This creates a ten-minute, one-use approval for the exact plan bytes and project. `deploy_apply` ignores the model's `confirmed` value and supplies it only after consuming that approval. Successful deployment opens a two-hour `vm_exec` session for that VM UUID and the plan's SSH login. A generated login password is removed from the MCP result because the engine uses its own SSH key. The deployment profile gives Codex and Hermes a 1200-second per-tool timeout, covering VM boot, SSH and API retries. A same-name VM blocks creation; inspect the returned UUID and live inventory before retrying with a different name. The profile does not expose `destroy`; inspect the VM ID and remove the test resource through a separate supervised cleanup step.

This local approval is an operator workflow, not a hard security boundary against an agent with unrestricted shell access as the same Unix user: such an agent could invoke `approve` or edit the local files itself. Use process/user isolation and cloud IAM limits if the deployment agent is untrusted. The cost number is an estimate, and the operator cap controls the reviewed plan, not Cloud.ru's final bill.

The launcher archive does **not bundle** the engine. A Linux/x64 npm install pulls `@dzhechkov/cloudru-vm-linux-x64@0.2.6` as an exact optional dependency. On other platforms, or when optional dependencies are disabled, set `CLOUDRU_VM_BIN` to a trusted copy whose hash matches `package.json.cloudruHub.binaryHashes`. Run `cloudru-hub self-test --json` first. A missing or changed binary makes `mcp-safe` refuse startup.

|---|---|---|
| Codex | `cloudru-hub install --target codex --dir /trusted/project --toolsets vm-deploy` writes `.codex/config.toml` with `required=true`, 12 enabled tools, an explicit 1200-second timeout and inherited paths for the pinned engine and credentials file | Trust the project; in a fresh session call local-only `status` before planning. The profile requests host `auto`, but `codex exec` with approval policy `never` blocked even `status` in the local probe; `--approve-for-me` allowed it. The proxy still requires a separate plan-bound approval for `deploy_apply` |
| OpenCode | `cloudru-hub install --target opencode --dir /trusted/project` writes `opencode.json` with a local server | `opencode mcp list`, then inspect tools in a session; installer refuses an existing `opencode.jsonc` to avoid conflicting configs |
| Pi | `cloudru-hub install --target pi --dir /trusted/project` writes `.pi/mcp.json` | Use a Pi release with built-in MCP, trust the project, run `pi mcp list`, then `/mcp` in a session; an older Pi may require an adapter |
| Hermes | With a hash-verified engine available, `cloudru-hub install --target hermes` adds a guarded entry to `$HERMES_HOME/config.yaml` with an explicit nonempty include list and `CLOUDRU_VM_BIN` path; `--hermes-home` selects a test directory | Run `hermes mcp test cloudru_hub`; complex YAML and existing Cloud.ru entries are refused for manual review |

Hermes needs model authentication separately from the Cloud.ru service-account file. On this server, `hermes model` → **OpenAI Codex** → import existing Codex CLI credentials configured the default Hermes profile without changing `~/.codex/auth.json`. Choose a model, then check `hermes auth status openai-codex` and make a short inference probe before attempting a cloud operation. Hermes keeps an independent copy of the imported OAuth session in its own auth store; subsequent token refreshes are not shared with Codex CLI. A successful model probe alone does not establish that the Cloud.ru MCP server has credentials or that a VM deployment passed.

Hermes sends periodic MCP tool-list keepalives. The pinned proxy answers repeat listings from its filtered in-process cache while the Go engine handles a long deployment. This prevents the keepalive from waiting behind a serial `deploy_apply` and losing that call's result on reconnect. The first listing still comes from the engine; restart the proxy after changing the pinned engine or classification.

Project configs contain an absolute path to this installed package. Regenerate them after moving the package or copying the project to another machine. Hermes filters inherited environment variables when starting an MCP server, so its installer first checks the local engine hash and writes the engine's absolute path into the server-specific `env`. The proxy hashes that file again on every start. Hermes installation refuses a missing or mismatched engine without changing YAML; regenerate the entry after moving the binary. The installers preserve unrelated simple configuration and refuse an existing Cloud.ru server instead of silently overwriting it. Codex refuses existing MCP declarations whose TOML semantics need review. Hermes inserts only into a plain mapping, keeps unrelated YAML text, and refuses anchors or unusual structure. A Hermes plugin's `pre_tool_call` hook is supplementary: plugin failures and some plugin dispatch paths do not provide a reliable enforcement boundary. The proxy enforces its policy even when plugins are disabled.

Host-side registration and read checks alone do not prove a live VM deployment. The package tests use a fake engine to show that an unapproved call never reaches the backend and a VM command cannot target an unrelated VM. Do not switch these host entries to raw `mcp` to recover write access. Codex and Hermes each completed the two live Snake scenarios; their HTTP checks and cleanup evidence are in the feature acceptance record.

This integration follows the current [Codex MCP configuration](https://developers.openai.com/codex/extend/mcp), [OpenCode MCP](https://opencode.ai/docs/mcp-servers), [Pi MCP](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/mcp.md) and locally inspected Hermes `mcp_servers` contract. Host versions and effective configuration should be recorded when testing a real installation.

## Ideas worth carrying forward from EVO

The [EVO CLI](https://github.com/shatim-ops/evo-cli) currently has a broader standalone Go CLI, more MCP operations, HTTP transport, selectable `--toolsets`, `--allow-project`, `doctor`, JSON output and dry-run/preview flows. Those are concrete advantages over this thin adapter. The most useful next work in our own Go engine is a shared operation registry for CLI and MCP, a measured toolset/profile switch to reduce context use, and an explanation of resource cost before changes. A `confirmed=true` argument supplied by a model is not evidence that a human approved a mutation; any write mode in our hub must enforce approval independently of that argument.
