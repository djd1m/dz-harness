# Гранулярность и изоляция микросервисов

## Решающий момент

Применяйте маршрут, когда нужно провести физическую границу сервиса, выбрать владельца данных и способ связи, проверить гранулярность или решить, допустима ли общая инфраструктура.

**NOT:** здесь не проектируют HTTP API, схему хранения или протокол консенсуса. Маршрут фиксирует архитектурные границы и компромиссы; детальную реализацию передавайте `api-design`, `database-review` и DDIA-навыкам.

## Протокол

1. **Назовите physical bounded context.** В одну независимо развёртываемую единицу входят поведение, схема и данные, которыми она владеет. Предпочтите локальное дублирование небольшой доменной логики общей библиотеке, связывающей релизы.
2. **Проверьте три сигнала размера.** Сервис должен иметь ясную цель, разумную транзакционную границу и не требовать непрерывной хореографии с соседями. Границу пересматривают итеративно, а не выводят из числа строк или классов.
3. **Назначьте источник истины.** Если потребителю нужна свежесть владельца, используйте его контракт; если допустима задержка, рассмотрите локальную реплику или кэш. Тип хранилища выбирайте по форме данных, требуемым свойствам и бюджету.
4. **Оставьте gateway тонким.** Разрешены маршрутизация и поперечные обязанности. Бизнес-оркестрация в gateway создаёт новый центр связанности.
5. **Совместите UI с владением.** Общий интерфейс проще, но связывает команды; microfrontend оправдан, когда его граница действительно следует границе backend-владельца.
6. **Выберите связь по ожиданию ответа.** Немедленный ответ означает синхронную зависимость; события или сообщения подходят для отложенной реакции. Нейтральный протокол снижает технологическую связь, а разнородность стеков должна иметь причину.
7. **Не лечите плохую границу сагой.** Сначала заново проверьте гранулярность. Если распределённая операция всё же нужна, назначьте посредника и компенсирующие действия для уже успешных частей.
8. **Зафиксируйте топологию данных.** Отдельная БД или схема на сервис — исходная позиция. Ограниченно общее хранилище допустимо для небольшой тесно связанной группы и должно быть оформлено как сознательное исключение.
9. **Отделите domain reuse от operational reuse.** Общие технические обязанности можно вынести в sidecar или service mesh, но назначьте владельца конфигурации и контролируйте дрейф версий.
10. **Проведите деградационный тест.** Ищите сервисы-песчинки без самостоятельной цели, чрезмерные межсервисные вызовы, широко разделяемую БД и общий доменный JAR/DLL. Сопоставьте выигрыш в масштабировании, автономии релиза и отказоустойчивости с сетевой задержкой, DevOps-нагрузкой и максимальной стоимостью стиля.

## Матрица критериев

| Наблюдение | Предпочтительное действие | Цена или предел |
|---|---|---|
| Нужна строго свежая запись владельца | Синхронный контракт владельца | Временная и runtime-связанность |
| Допустима ограниченная задержка | Локальная реплика либо кэш | Lag и отдельная политика согласования |
| Участники должны завершиться вместе | Пересмотреть границу; затем saga | Компенсации не равны ACID rollback |
| Несколько сервисов постоянно делят таблицы | Укрупнить границу или выделить узкое исключение | Слабее независимость изменения |
| Общая обязанность не относится к домену | Sidecar/service mesh | Ownership и configuration drift |
| UI меняется одной командой | Общий UI | Связывает cadence команд |
| UI следует автономным доменам | Microfrontends | Больше интеграционной сложности |
| Главный драйвер — низкая стоимость | Проверить более простой стиль | Микросервисы имеют наивысшую относительную стоимость |

В отрицательном примере книги все примерно 60 сервисов разделяли одну БД. Отдельная рекомендация
книги для обоснованного исключения — ограничивать общую БД или схему тесно связанной группой примерно
до пяти-шести сервисов. Это два разных утверждения, а не один числовой норматив для любой системы.

## Антипаттерны

- Резать сервисы по таблицам, классам или числу разработчиков без доменной цели.
- Давать gateway выполнять долгоживущий бизнес-процесс.
- Объявлять асинхронным обмен, в котором инициатор блокируется до ответа.
- Вводить saga до проверки, не раздроблена ли одна транзакционная область.
- Делить доменную библиотеку между сервисами и сохранять иллюзию независимых релизов.
- Покупать разнородность технологий без локального выигрыша.
- Считать отдельные контейнеры доказательством изоляции данных.

## Связанные ограничения

- `architecture-quantum-boundary` уточняет минимальную независимо развёртываемую единицу.
- `event-*` маршруты выбирают семантику payload, доставку и владельца процесса после фиксации сервисных границ.
- `pattern-composition-coupling` решает, где эксплуатационное reuse требует отдельного паттерна.
- `environment-topology-alignment` проверяет, поддерживает ли физическая среда обещанные свойства.

## Self-check

- [ ] У каждого сервиса одна объяснимая цель и владелец данных?
- [ ] Транзакционная граница и необходимость хореографии проверены?
- [ ] Для каждой связи названы freshness и reply expectations?
- [ ] Gateway свободен от доменной оркестрации?
- [ ] Исключения общей БД ограничены и записаны?
- [ ] Sidecar/mesh имеет владельца и контроль дрейфа?
- [ ] За автономию посчитана эксплуатационная цена?
