# Аудит заблуждений и цены распределения

## Когда применять и границы

Применяйте до переноса локального вызова, данных или транзакции через сеть и при ревью уже распределенного критического пути. Цель — проверить восемь базовых заблуждений, контрактные версии и отказ компенсации.

**NOT:** не оценивает PR/diff по общей риск-матрице (`risk-assessment`), не проводит продуктовый red team (`strategy-red-team`) или QE-сессию (`qcsd-ideation-swarm`), не проектирует REST/GraphQL (`api-design`, `graphql-schema`), не заменяет security audit и не запускает chaos experiment (`qe-chaos-resilience`).

## Протокол

1. **Зафиксируйте исходную и целевую топологии.** Перечислите локальные операции, которые станут удаленными, их данные, обязательные ответы и ожидаемую выгоду независимой поставки.
2. **Пройдите восемь заблуждений.** Для каждой связи проверьте: сеть может отказать; задержка не равна нулю; пропускная способность конечна; сеть не является безопасной; топология меняется; администраторов несколько; передача имеет денежную цену; оборудование и среда неоднородны.
3. **Спроектируйте реакцию на ненадежность.** Ограничьте ожидание синхронного вызова и поставьте автоматический предохранитель. Отдельно определите поведение при неизвестном результате: запрос мог выполниться, хотя ответ потерян. Тайм-аут и предохранитель ограничивают последствия, но не устраняют эту неопределенность; значения получают измерением среды.
4. **Измерьте задержку как распределение.** Получите среднее время полного цикла и значения 95–99-го процентилей для одного перехода. Затем умножьте задержки на число последовательных сервисов и сравните средний и хвостовой результаты с бюджетом. Примеры источника — 10 переходов по 100 мс дают 1000 мс; среднее 60 мс рядом с 95-м процентилем 400 мс показывает, почему числа нельзя переносить как нормативы другой среды.
5. **Сократите связанность по образцу.** Если потребителю нужна малая часть крупного ответа, рассмотрите специализированный контракт, field selector или специализированную конечную точку. Передавайте только требуемые данные, учитывая рост числа контрактов и их эволюцию.
6. **Защитите каждую конечную точку.** Инвентаризируйте внешние и межсервисные interfaces и учитывайте стоимость проверок в критическом пути. VPN, доверенный сегмент и брандмауэр не освобождают сервисную границу от защиты; детальную модель угроз передайте `security-audit`.
7. **Организуйте контур сетевых изменений.** Поддерживайте связь со всеми эксплуатационными ролями, способными менять маршруты и топологию. Один контакт не представляет распределенное владение сетью.
8. **Посчитайте полную цену.** Снимите емкость, пропускную способность, задержку и зоны безопасности исходной среды. Добавьте оборудование, серверы, gateways, firewalls, subnets и proxies, необходимые целевой топологии, и сравните цену с выгодой декомпозиции.
9. **Установите политику версий.** До несовместимого выпуска определите область управления, масштаб поддерживаемой части, число одновременно действующих версий и правило устаревания. Нумерация без этих решений не является политикой.
10. **Спроектируйте отказ компенсации.** Нарисуйте основной путь, компенсации уже выполненных шагов и отдельный recovery path на случай, когда компенсация сама полностью или частично отказывает.

## Матрица критериев

| Проверяемое предположение | Нужное свидетельство | Решение при провале |
|---|---|---|
| Сеть надежна | поведение при потере запроса и ответа | явная реакция вместо бесконечного ожидания |
| Задержка нулевая | среднее и длинный хвост полного цикла | сократить цепочку или пересмотреть границу |
| Пропускная способность бесконечна | объем и частота передачи | уменьшить payload и связанность по образцу |
| Сеть безопасна | инвентарь защищенных endpoints | защитить каждую границу и учесть цену |
| Топология постоянна | процесс уведомления об изменениях | координация и повторная проверка задержек |
| У сети один администратор | перечень эксплуатационных владельцев | поддерживать несколько каналов связи |
| Передача бесплатна | инфраструктурная и денежная смета | сравнить с выгодой независимости |
| Сеть однородна | проверенные комбинации фактической среды | сохранить остаточный риск совместимости |
| Версия управляется номером | область, масштаб, лимит, устаревание | определить политику до выпуска |
| Компенсация всегда сработает | recovery path для ее отказа | проектировать второй уровень восстановления |

## Антипаттерны

- Декомпозиция только ради обещаний масштаба или доступности.
- Оценка цепочки по одной средней задержке.
- Передача крупного общего DTO всем потребителям.
- Доверие внутренней сети как единственной границе безопасности.
- Один сетевой администратор как предполагаемый владелец всей топологии.
- Сравнение только задержки без денежной и инфраструктурной цены.
- Бесконтрольное накопление версий контракта.
- Компенсация без сценария ее собственного отказа.
- Выдавать этот preflight за chaos, security или API review.
