# Эластичное участие архитектора и командные полномочия

## Решающий момент

Применяйте маршрут, когда нужно откалибровать участие архитектора, разделить архитектурные рамки и внутренний дизайн, определить ownership checklist/DoD или назначить полномочия на выбор библиотеки без диктатуры и без исчезновения архитектора.

**NOT:** маршрут не планирует sprint, не проводит retrospective или incident response и не заменяет stakeholder analysis. Эти процессы передаются соответствующим `boundary_skills`; здесь настраиваются архитектурное участие и технические полномочия.

## Протокол

1. **Создайте двустороннюю рабочую систему.** Архитектор объясняет свойства, стиль и компонентные границы; разработчики возвращают сведения о реализуемости и изменениях. Архитектура корректируется по итерациям, а ответственность не смешивается: системная целостность остаётся у архитектора, внутренности компонента — у команды.
2. **Откалибруйте рамки.** Ослабляйте правило, которое без нужды выбирает библиотеку, класс или coding technique. Усиливайте его, если команда вынуждена заново решать системные границы и взаимодействия.
3. **Проверьте две крайности.** Диктатор задаёт псевдокод и локальный дизайн; кабинетный архитектор недоступен, не знает домен и не видит последствий для сопровождения и тестирования. Верните первому правильный уровень абстракции, второму — контакт и компетентность.
4. **Оцените пять осей elastic leadership.** Учитывайте знакомство группы, размер, суммарный опыт, сложность и длительность. Усиливайте участие для новой, крупной, начинающей команды, сложной задачи и долгой программы; регулярно пересчитывайте.
5. **Используйте балл только для разговора.** Симметричная эвристика по 20 баллов на ось помогает сравнить режимы, но не является измерительным прибором. В источнике второй сценарий арифметически даёт +20, хотя в таблице напечатано −20.
6. **Не добавляйте человека без независимого потока.** Ищите сервис, область или участок с малым пересечением кода. Рост merge conflicts и разрыв между доступной мощностью и выпуском — сигналы взаимного торможения, но не повод искусственно создавать сервис.
7. **Защитите несогласие.** Замечая паузу или сомнение, пригласите участника высказаться без публичного давления. Проверяйте аргумент по фактам даже после голосования; цель — безопасный аудит выбора, не обязательная победа меньшинства.
8. **Выберите форму контроля.** Последовательные зависимые шаги оформите процедурой. Независимые забываемые проверки — коротким checklist. Надёжно автоматизируемое условие перенесите в статический анализ, plugin или fitness function.
9. **Дайте исполнителям ownership.** Объясните конкретные ошибки, от которых защищает checklist, и составьте его совместно. Для code done проверьте локальные соглашения и часто забываемые дефекты; машинно доказуемые пункты удалите из ручной части.
10. **Учитесь на границах и релизах.** Стартовый набор тестов покрывает спецсимволы, минимум/максимум, экстремальные случаи и отсутствующие поля. Новые классы дефектов пополняют тесты. Release checklist охватывает конфигурацию, зависимости и миграции; после сбоя добавляйте проверку лишь после root-cause analysis.
11. **Разделите library authority.** Сначала проверьте дублирование и обоснование по обучению, деньгам и срокам. Локальное специализированное средство может выбрать разработчик; common library исследует команда и утверждает архитектор; framework целого слоя выбирает архитектор.
12. **Поддерживайте способность архитектора.** Ведите технологический radar, развивайте ограниченную глубину и доменное знание, практикуйтесь на неблокирующих задачах, code review и архитектурных kata. Подбирайте team topology по потоку ценности и когнитивной нагрузке.

## Матрица полномочий

| Контекст | Участие архитектора | Полномочие команды |
|---|---|---|
| Малая знакомая опытная команда, простой короткий проект | Координация и доступность по запросу | Широкий внутренний дизайн |
| Новая или крупная команда, много начинающих, сложная долгая работа | Более частое наставничество и рамки | Решения внутри явно заданных границ |
| Специализированная локальная библиотека | Проверка границы при необходимости | Разработчик решает |
| Общая библиотека | Проверяет reuse, cost и coupling; утверждает | Команда исследует варианты |
| Framework, формирующий слой | Владеет системным выбором | Команда даёт evidence о реализуемости |
| Независимые забываемые проверки | Совместно формирует checklist | Исполнители владеют применением |
| Строго зависимые шаги | Согласует procedure | Команда выполняет порядок |
| Машинно доказуемое условие | Задаёт архитектурный intent | Команда автоматизирует |

Числа размера — до пяти как малая команда и свыше 12 как большая — ориентиры источника, а не организационный закон. Вес любой из пяти осей может быть изменён для проекта.

## Антипаттерны

- Выбирать классы и локальные приёмы вместо задания системной рамки.
- Рисовать схему и исчезать до следующего квартала.
- Принимать оценку участия за точную KPI-формулу.
- Добавлять людей в один конфликтующий участок кода без нового потока.
- Давить на сомневающегося или считать голосование техническим доказательством.
- Превращать независимый checklist в неявную последовательную процедуру.
- Сохранять вручную пункт, который надёжно проверяет сборка.
- Добавлять release-пункт без причинной связи со сбоем.
- Давать framework-level решение локальному эксперименту без оценки радиуса влияния.

## Связанные ограничения

- `architecture-quantum-boundary` и топологические маршруты задают рамки, которые архитектор объясняет команде.
- `decision-governance-last-moment` определяет формальный approval там, где командного полномочия недостаточно.
- `architecture-risk-storming` даёт безопасную структуру технического несогласия.
- `constraint-negotiation-availability` помогает архитектору обсуждать дорогие правила совместным языком.

## Self-check

- [ ] Архитектор и команда обмениваются решениями в обе стороны?
- [ ] Рамки останавливаются до внутреннего дизайна компонента?
- [ ] Пять осей оценены и будут пересмотрены?
- [ ] Для нового участника найден независимый поток?
- [ ] Сомнение можно высказать безопасно и проверить по фактам?
- [ ] Procedure, checklist и automation не перепутаны?
- [ ] Library authority соответствует радиусу влияния?
- [ ] Практика архитектора не блокирует пользовательский поток?
