# Исполняемая функция пригодности для архитектурного ограничения

## Когда применять и границы

Применяйте, когда архитектурное правило или свойство постепенно размывается и его можно связать с объективным сигналом, регулярной проверкой и заранее определенной реакцией.

**NOT:** не выбирает OTel, Prometheus, Grafana, dashboard, SLO или alerts (`observability`), не проводит chaos experiment (`qe-chaos-resilience`) и не пишет ADR (`architecture-decision-records`). Здесь выбирается архитектурный guardrail и его смысл.

## Протокол

1. **Назовите защищаемую цель.** Свяжите правило с бизнес-результатом и архитектурным свойством. Проверьте, действительно ли выбор влияет на структуру, интерфейсы, зависимости или значимые качества; название технологии ничего не доказывает.
2. **Сформулируйте правило.** Укажите допустимые источники обращения, цель, запрещенные обходы и обоснование. Для субъективного условия оставьте честную ручную проверку вместо ложной автоматизации.
3. **Выберите наблюдаемый сигнал по риску.** Числовому состоянию соответствует метрика, поведению во времени — монитор, изменению — обработчик события, статической структуре — тест, устойчивости к выбранному отказу — контролируемый эксперимент. Среднее дополняйте хвостом или максимумом, если редкое тяжелое отклонение важно.
4. **Откалибруйте вычисление и порог.** Для графа потока одной функции используйте `CC = E - N + 2`, а при `P` компонентах связности — `CC = E - N + 2P`. Для обычного продуктового кода значение меньше 10 рассматривайте как распространенную верхнюю границу, стремясь к значению меньше 5; оправданную алгоритмическую сложность разбирайте отдельно. Для пакетной структуры вычисляйте `D = |A + I - 1|`; пример `ideal = 0.0`, `tolerance = 0.5` является проектно-зависимым и требует калибровки.
5. **Выберите сильнейший подходящий механизм.** Запрещайте циклы графа зависимостей, проверяйте расстояние пакетов, закрепляйте разрешенное направление слоев или контролируйте эксплуатационный риск выбранным сигналом. Для Java в KU приведены JDepend и ArchUnit, для .NET — NetArchTest; это примеры, а не обязательный стек.
6. **Встройте проверку в контур изменения.** Подключите статическое правило к сборке, а эксплуатационное — к рабочему контуру. Согласуйте условие отказа, допустимое значение и действие при нарушении: вернуть реализацию, изменить практику либо пересмотреть исходное решение.
7. **Проверяйте жизнеспособность правила.** На обзорах сопоставляйте его с текущим бизнесом, технологиями, тестированием и выпуском. Сигнал должен отличать деградацию системы от устаревшей модели; одиночный proxy не доказывает полное свойство.

## Матрица критериев

| Риск | Сигнал / проверка | Ограничение интерпретации |
|---|---|---|
| Скрытая хвостовая задержка | среднее плюс хвост или максимум | выброс не объясняет причину |
| Сложное ветвление | `CC = E - N + 2P` | CC не различает предметную и случайную сложность |
| Циклы компонентов | ориентированный граф без возврата | не ловит все нежелательные однонаправленные связи |
| Дисбаланс абстрактности и нестабильности | `D = |A + I - 1|` | расстояние требует контекстной оценки |
| Нарушение границ слоев | executable dependency rule | правило не доказывает правильность самих слоев |
| Неизвестный отказ | контролируемая инъекция выбранного сбоя | подтверждается только исследованный сценарий |
| Деградация изменяемости | покрытие вместе с качеством тестов, выпуском и дефектами | процессные показатели зависят от команды |

## Антипаттерны

- Проверка без объяснения защищаемого свойства.
- Удобный одиночный proxy вместо риска пользователя.
- Перенос порога `0.5`, `<10` или другого ориентира без калибровки.
- Механический рефакторинг по CC без классификации источника сложности.
- Автоматический verdict там, где условие субъективно.
- Метрика без согласованной реакции на отклонение.
- Однократный аудит кода без проверки тестирования и выпуска.
- Скрытый обход guardrail ради локального срока.
