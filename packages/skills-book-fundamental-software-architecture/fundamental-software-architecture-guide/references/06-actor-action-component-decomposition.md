# Компонентная декомпозиция по акторам, действиям и рабочим процессам

## Когда применять и границы

Применяйте к новой или растущей системе, когда известны основные истории, акторы либо благоприятный рабочий процесс, но логические компоненты и владельцы поведения еще не определены.

**NOT:** маршрут не рисует Mermaid/PlantUML/C4 (`c4-architecture`), не выбирает общий backend pattern (`backend-patterns`) и не проводит обычный SOLID-рефакторинг (`solid`). Он заканчивается логическими обязанностями, а не физическими сервисами.

## Протокол

1. **Выберите начальную линзу.** Если доминирует один понятный путь обработки, начните с его этапов. Если различия проходят между несколькими ролями, используйте actor/action. Система тоже является актором автоматических действий.
2. **Создайте кандидатов без ложной точности.** Для workflow пройдите от первого действия до результата; для каждого этапа предложите функциональный блок и объедините повторяющиеся способности. Для actor/action выпишите только основные действия и сгруппируйте общую ответственность. Не создавайте компонент на каждый шаг.
3. **Сравните исходные гипотезы.** При доступности обоих источников сопоставьте наборы по ясности ролей и числу взаимодействий. Выберите более полезный старт, но не выдавайте его за финальную структуру.
4. **Назначьте истории одному владельцу.** Соотнесите поведение с ролью компонента. Если одинаковая способность нужна нескольким блокам и естественного владельца нет, выделите новый компонент; инициаторы лишь обращаются к нему.
5. **Проверьте связность роли.** Сформулируйте одно короткое назначение и перечислите обязанности. Длинные перечисления и независимые цели — сигнал разделения. После разделения перепишите роли и проверьте, стали ли они яснее.
6. **Наложите архитектурные свойства.** Для обязанностей сравните масштабируемость, надежность, доступность, отказоустойчивость, адаптируемость и гибкость. Различающиеся профили могут оправдать новую границу, но меньший размер сам по себе ничего не улучшает.
7. **Выявите временную связанность.** Для сквозных сценариев запишите обязательный порядок активации и границы транзакции. Эти отношения могут отсутствовать в статическом графе, поэтому сверяйте документацию и ошибки.
8. **Уберите чужие решения из перегруженного владельца.** Оставьте компоненту знания, необходимые его роли, а правила соседних обязанностей передайте естественным владельцам. После переноса пересчитайте направления связей: число зависимостей может не уменьшиться, даже если ответственность стала локальнее.
9. **Сравните несколько декомпозиций.** Для каждого варианта перечислите ясность ролей, число связей, различия свойств и цену будущих изменений. Выберите вариант с приемлемыми недостатками и повторяйте цикл при новых требованиях.

## Матрица критериев

| Ситуация | Стартовый прием | Последующая проверка |
|---|---|---|
| Один главный благоприятный путь | workflow decomposition | не создавать блок для каждого шага |
| Несколько отчетливых ролей | actor/action | включить систему как актора |
| Поведение нужно нескольким компонентам | найти естественного владельца | новый блок только при самостоятельной ответственности |
| Роль описывается длинным перечнем | кандидат на разделение | роли после разделения должны стать яснее |
| Обязанности требуют разных свойств | разделить профили эксплуатации | цена новых взаимодействий приемлема |
| Порядок операций обязателен | временная связанность | сделать порядок и транзакционную границу явными |
| Оркестратор знает внутренние правила соседей | нарушение локальности знаний | передать решение владельцу правила |
| Несколько правдоподобных границ | least-worst comparison | выбрать по бизнес-задаче и пересматривать |

## Антипаттерны

- Компонент на каждый этап процесса или каждое действие актора.
- Попытка смоделировать все редкие сценарии в первом проходе.
- Назначение одной истории нескольким владельцам и дублирование поведения.
- Разделение только ради меньшего размера.
- Игнорирование временного порядка, потому что его нет в графе импортов.
- Посредник, который сохраняет все знания о правилах соседей.
- Поиск единственной «правильной» декомпозиции без сравнения потерь.
- Замораживание исходных кандидатов после появления новых требований.
