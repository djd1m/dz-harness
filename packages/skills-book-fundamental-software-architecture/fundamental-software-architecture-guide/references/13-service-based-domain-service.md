# Service-based: крупные предметные сервисы и топология данных

## Решающий момент

Применяйте маршрут, когда нужны независимо поставляемые крупные бизнес-области без мелкой микросервисной нарезки и требуется согласовать service granularity, интерфейс, шлюз и владение данными.

**NOT:** маршрут не проектирует REST/GraphQL ресурсы, схему или миграцию БД и не выбирает детальную модель данных. Он определяет архитектурные границы и топологию; профильные артефакты передаются навыкам из `boundary_skills`.

## Протокол

1. **Выделите крупные предметные сервисы.** Начните с клиента и больших бизнес-областей. Сервис должен выражать область, а не одну техническую операцию. При общей монолитной БД ориентир книги — не более 12 предметных сервисов; это сигнал для анализа, не жёсткая норма.
2. **Проверьте внутреннюю гранулярность.** Внутри сервиса выберите технические слои или предметные подобласти. Оставление полного рабочего потока в одной границе допускает обычный ACID commit/rollback; дробление шагов уменьшает локальный радиус изменения, но добавляет BASE и компенсации.
3. **Выберите гранулярность интерфейса отдельно.** Сравните один клиентский модуль, интерфейс для группы областей и интерфейс перед каждым сервисом. Двигайтесь к более мелкой форме только при разных требованиях к масштабу или изоляции сбоев.
4. **Добавляйте API gateway по функции.** Обоснуйте его внешним доступом, общими метриками, аудитом, безопасностью, discovery или балансировкой. Не вводите центральную зависимость только ради симметрии схемы.
5. **Поднимайтесь по лестнице изоляции данных.** Общая физическая БД → базы групп областей → БД на сервис. Переходите выше, только если данные выделяемой области не нужны соседям постоянно; иначе новые сетевые чтения уничтожат автономность.
6. **Локализуйте влияние общей схемы.** Если используется общая БД, разделите entity/SQL libraries по областям и подключайте сервису только нужные пакеты. Общий пакет защищайте отдельным контролем изменений.
7. **Сделайте независимость проверяемой.** Ищите изменение одного сервиса, требующее правки другого, считайте межсервисные вызовы и обосновывайте исключения. Если возможно, верните координацию клиенту или шлюзу.
8. **Оцените кванты и экономику масштаба.** Общий UI или БД могут собрать систему в один квант. Реплицируйте только реально нагруженную область; крупный сервис масштабирует вместе с собой ненужные функции.
9. **Используйте форму как промежуточную осознанно.** После выделения крупных областей наблюдайте частоту изменений, нагрузку и потребность независимого выпуска. Делите только там, где измеренная цена крупной границы превышает цену дополнительной распределённости.

## Матрица решения

| Критерий | Предпочтение | Цена / стоп-сигнал |
|---|---|---|
| Умеренное число крупных DDD-областей | Крупные domain services | Рост числа сервисов и взаимных вызовов требует пересмотра границ |
| Один предметный процесс требует общей транзакции | Держать шаги в одном сервисе | Более широкое повторное тестирование и развертывание |
| Шагам нужны независимые release/scale/failure | Рассмотреть более мелкие сервисы | BASE, компенсации и удалённая координация |
| Клиентские части имеют одинаковые свойства | Один UI/групповой интерфейс | Общая точка поставки и сбоя |
| Различаются масштаб или изоляция | Более мелкий UI и целевой gateway | Дополнительные deployable units и центральная зависимость |
| Данные часто нужны многим областям | Общая или групповая БД | Координация схемы |
| Данные автономны | БД предметного сервиса | Не допускайте цепочки удалённых чтений |
| Границы ещё неясны | Service-based как промежуточная форма | Не дробить стабильные области без наблюдаемой цены |

## Антипаттерны

- Называть сервисом единичную техническую операцию.
- Копировать микросервисную гранулярность без требования к независимости.
- Делить БД, а затем восстанавливать совместное чтение синхронными вызовами.
- Подключать все сервисы к одному пакету полной модели данных.
- Добавлять шлюз ради картинки, не называя его функцию.
- Считать ориентир 12 автоматическим запретом или целью.
- Обещать независимые кванты при общей обязательной БД или UI.

## Связанные маршруты

- `style-topology-fit`: подтверждает, что крупное предметное распределение соответствует драйверам.
- `distributed-fallacy-audit`: проверяет цену сети до физического разделения.
- `modular-monolith-mediator`: альтернатива, когда отдельная поставка областей ещё не нужна.
- `microservice-granularity-isolation`: следующий выбор для обоснованно мелких автономных границ.
- `environment-topology-alignment`: проверяет, согласованы ли deployment, данные, команды и интеграции с выбранной формой.

## Self-check

- [ ] Сервисы выражают крупные бизнес-области?
- [ ] Внутренняя гранулярность и interface granularity решены отдельно?
- [ ] Для gateway названа конкретная функция?
- [ ] Data topology не создаёт новые критические remote reads?
- [ ] Межсервисные вызовы и влияние общей схемы измеримы?
- [ ] Общие точки кванта и цена репликации названы?
- [ ] Дальнейшее дробление опирается на наблюдаемую цену?
