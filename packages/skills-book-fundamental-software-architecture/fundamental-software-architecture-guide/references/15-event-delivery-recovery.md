# События: доставка, окна потери и восстановление

## Решающий момент

Применяйте маршрут, когда асинхронный поток должен переживать сбой издателя, брокера, потребителя или БД, сохранять локальный порядок и возвращать дефектные сообщения после автоматического либо ручного ремонта.

**NOT:** не выбирайте здесь OTel/Prometheus, не запускайте chaos experiment и не ведите incident timeline. Маршрут проектирует delivery/recovery semantics; реализация проверок и эксплуатационных инструментов передаётся `boundary_skills`.

## Протокол

1. **Нарисуйте полный путь сообщения.** Отметьте издателя, брокер, потребителя, побочные эффекты и конечную БД. Для каждого перехода назовите устойчивое место хранения и владельца подтверждения.
2. **Закройте три окна потери.** Проверьте сбой между отправкой и устойчивым приёмом, падение после чтения до завершения обработки и отказ записи в БД. Надёжность не сквозная, пока не закрыты все три.
3. **Свяжите гарантии.** На входе используйте сохраняемую очередь и дождитесь подтверждения физической записи брокером. На выдаче удерживайте элемент до client ACK. Запись в БД выполняйте ACID-транзакцией; после commit удаляйте сообщение через LPS, если платформа его поддерживает.
4. **Спроектируйте повторную доставку.** Повтор возможен после сбоя, поэтому потребитель должен выдерживать повторный эффект. Если LPS или ACID недоступны, зафиксируйте, что нужен другой согласованный протокол — данный маршрут его не придумывает.
5. **Отделите ремонт от основного потока.** При ошибке отправьте исходные данные и диагностику workflow delegate. Он пытается исправить автоматически, иначе передаёт материал оператору; исправленный вариант возвращается в исходный канал как новая попытка.
6. **Сохраните порядок локально.** Для ordered context извлеките ключ агрегата, удерживайте последующие элементы этого ключа в FIFO и продолжайте обрабатывать другие ключи. После ремонта выпустите накопленное последовательно.
7. **Выберите долговечность канала по модели брокера.** Для AMQP учитывайте exchange и очереди подписчиков, для Jakarta topic — durable subscription, для Kafka — потоковый журнал. Не переносите гарантии одной модели на другую по названию технологии.
8. **Если нужен request–reply, признайте синхронную зависимость.** Две очереди не делают обмен полностью асинхронным, если источник ждёт ответ. Для большого потока используйте общую очередь и CID; для редких обменов допустима временная reply queue, если её создание не перегружает брокер.
9. **Наблюдайте связанность, не объявляя её оправданной.** Для статической связи инвентаризируйте контракты и реально читаемые поля. Для динамической — журналируйте источник, адресат и протокол либо регистрируйте карту вызовов. Неожиданный вызов выносите на архитектурный разбор.

## Матрица решения

| Риск / потребность | Механизм | Ограничение |
|---|---|---|
| Потеря до устойчивого приёма | Persistent queue + synchronous broker ACK | Повышает publish latency |
| Падение потребителя после чтения | Client ACK, элемент остаётся закреплённым | Возможна повторная доставка |
| Сбой записи в БД | ACID commit + LPS перед удалением | При отсутствии поддержки нужен другой протокол |
| Дефект сообщения, поток нельзя останавливать | Workflow delegate и repair loop | Возврат меняет порядок и требует лимита попыток |
| Порядок важен внутри агрегата | FIFO hold по ordering key | Долгий ремонт накапливает очередь этого ключа |
| Много request–reply обменов | Общая reply queue + CID selector | Ошибка CID оставляет ответ невостребованным |
| Редкий простой request–reply | Temporary reply queue + `reply-to` | Создание/удаление очередей плохо масштабируется |
| Нужно увидеть фактические связи | Contract inventory + call logs/traces | Неполные данные занижают связанность |

## Антипаттерны

- Проверять только доступность брокера и объявлять delivery надёжной.
- Удалять сообщение при чтении до подтверждённого эффекта.
- Глобально останавливать очередь из-за ошибки одного агрегата.
- Бесконечно возвращать неисправимое сообщение без отдельного состояния ремонта.
- Считать request–reply через очереди динамически развязанным.
- Переносить AMQP/JMS guarantees на Kafka без отдельного решения.
- Делать вывод об оправданности зависимости только по её наличию в trace.
