# Граница архитектурного кванта и ограниченного контекста

## Когда применять и границы

Применяйте, когда нужно определить область независимой поставки и единый набор эксплуатационных свойств, понять, объединяет ли части общая БД или обязательный ответ, и локализовать разные смыслы предметной модели.

**NOT:** не рисует C4 (`c4-architecture`), не проектирует Kubernetes deployment (`kubernetes`), не ревьюит схему (`database-review`) и не выбирает data model (`ddia-data-model-selection`). Результат — обоснованная граница кванта, а не ее инструментальная реализация.

## Протокол

1. **Наметьте деловую цель кандидата.** Граница должна обслуживать отчетливую цель, а не просто совпадать с процессом или именем сервиса.
2. **Проверьте независимую поставку.** Кандидат должен развертываться без обязательной совместной поставки остальных частей. Формально отдельный сервис еще не образует квант.
3. **Включите обязательные ресурсы.** Поместите внутрь каждый компонент и хранилище, без которого часть не работает. Общая обязательная БД может объединить несколько сервисов в одну область свойств.
4. **Локализуйте предметный смысл.** Разделяйте модель по задачам. Если одна сущность означает разное в разных процессах, держите отдельные представления внутри ограниченных контекстов и согласуйте различия на интеграционной границе.
5. **Разложите связанность на четыре слоя.** Семантическая задана самой задачей; реализационная — выбранной формой решения; статическая — общими компонентами и данными; динамическая — вызовами во время работы. Не пытайтесь убрать естественную семантическую зависимость техническим приемом.
6. **Проверьте runtime-ожидание.** Обязательный синхронный ответ передает задержку и отказ соседу. Если превышение скорости производителя бывает коротким, результат допускает задержку, а средний вход не выше устойчивого выхода, очередь может буферизовать всплеск. В исходном примере приемник обрабатывает один платеж каждые 500 мс; очередь не создает дополнительную пропускную способность.
7. **Включите платформу в границу свойств.** Для контейнеров учитывайте свойства оркестратора; для функций, баз и других управляемых блоков — заявленные возможности каждого блока, безопасность и доступность провайдера. Обещание платформы требует проверки.
8. **Назначьте свойства полученному кванту.** Не распространяйте автоматически один профиль на всю систему. Если внешние статические или динамические зависимости не позволяют части сохранять свой профиль, пересмотрите границу.

## Матрица критериев

| Проверка | Признак самостоятельного кванта | Признак общей области |
|---|---|---|
| Поставка | часть выпускается отдельно | требуется совместный deployment |
| Деловая цель | одна отчетливая цель | случайная техническая группа |
| Статическая зависимость | мало внешней реализации | общий обязательный компонент или БД |
| Динамическая зависимость | задержка результата допустима либо вызов не обязателен | инициатор блокируется до ответа |
| Предметная модель | локальный смысл внутри bounded context | корпоративная сущность вынуждает общий выпуск |
| Нагрузка | краткий всплеск можно буферизовать | средний вход постоянно выше выхода |
| Платформа | свойства управляемого блока проверены | обещание провайдера принято без проверки |

## Антипаттерны

- Считать каждый сервис отдельным архитектурным квантом.
- Оставлять общую обязательную БД за нарисованной границей.
- Выводить runtime-связанность только из статической диаграммы.
- Создавать одну универсальную предметную сущность для разных смыслов.
- Использовать очередь как замену устойчивой пропускной способности.
- Считать облачную конфигурацию внешней по отношению к архитектурным свойствам.
- Назначать один набор свойств всей системе по умолчанию.
