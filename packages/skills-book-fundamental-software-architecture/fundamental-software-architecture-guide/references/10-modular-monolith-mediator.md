# Модульный монолит: границы, медиатор и данные

## Решающий момент

Применяйте маршрут, когда система должна оставаться одной единицей поставки, но команде нужно выбрать предметные модули, способ их упаковки, межмодульное взаимодействие и владение данными.

**NOT:** не используйте его для общего обзора backend-паттернов, ревью схемы или миграции БД и детального выбора модели данных — передайте такие задачи навыкам из `boundary_skills`. Если независимое развертывание уже обязательно, сначала вернитесь к `style-topology-fit`.

## Протокол

1. **Подтвердите форму поставки.** Зафиксируйте одну единицу развертывания и проверьте, что бюджет, сроки и приоритетные свойства допускают монолитную область масштабирования и отказа. Откажитесь от кандидата, если ведущими являются высокая адаптируемость, отказоустойчивость или независимое масштабирование частей.
2. **Проведите предметные границы.** Разделите верхний уровень по бизнес-областям или подобластям. Представление, правила и доступ к данным держите внутри соответствующего модуля; техническую роль отражайте ниже предметной ответственности.
3. **Выберите упаковку кода.** Общий репозиторий с предметными каталогами подходит заметно взаимодействующим модулям. Отдельные JAR/DLL и репозитории оправданы для крупных слабо связанных областей со специализированным владением.
4. **Сначала пытайтесь убрать межмодульный вызов.** Перепроверьте границы. Для редкой простой связи оставьте узкий публичный контракт; для потока через несколько модулей выделите медиатор, который хранит порядок шагов и обращается к их контрактам.
5. **Выберите владение данными после границ поведения.** Начните с общей БД как естественного кандидата одной программы. Выделяйте модульное хранилище только для самостоятельной функции с контекстными данными, не требующими постоянной координации с соседями.
6. **Совместите владение команд с декомпозицией.** Нанесите фактических владельцев на карту модулей. Частый проход типового изменения через несколько команд — сигнал переразметить границы или ответственность.
7. **Сделайте границы исполняемыми.** В каждой сборке проверяйте допустимые верхнеуровневые пространства имён, направления ссылок и запрещённые пары. Порог связанности выбирайте по baseline системы; книжное значение `5` — только пример сигнала.
8. **Проверяйте деградацию формы.** Ищите каскадные регрессии, замедлившиеся поставки, общий код как обход границы, долгий запуск и постоянные вызовы между модулями. Устойчивый паттерн требует изменения границ, а не нового исключения.

## Матрица решения

| Вопрос | Выбор | Цена и стоп-сигнал |
|---|---|---|
| Верхний принцип структуры | Предметные модули внутри одного deployable unit | Технические UI/business/data каталоги наверху возвращают слоистый монолит |
| Упаковка исходников | Общий repo при частом взаимодействии | Нужны статические запреты; иначе общий код размоет границы |
| Упаковка исходников | Отдельные JAR/DLL при слабой связи и отдельном владении | Частые взаимные вызовы создают JAR/DLL dependency nightmare |
| Межмодульный поток | Узкий прямой контракт для редкого простого вызова | Распространение прямых ссылок связывает реализации |
| Межмодульный поток | Медиатор для многошаговой координации | Медиатор может стать перегруженным центром и общей зависимостью |
| Данные | Общая БД, если совместное чтение убирает лишнюю координацию | Схема остаётся общей точкой влияния |
| Данные | БД модуля при самостоятельной функции и данных | Разделение без автономности создаст новые обращения |
| Пригодность стиля | Невысокая стоимость, неопределённая траектория, локальные предметные изменения | Высокая эластичность и независимая устойчивость частей требуют другого стиля |

## Антипаттерны

- Считать одну сборку доказательством модульности.
- Делить верхний уровень по технологиям, а не по бизнес-ответственности.
- Выносить каждый модуль в отдельный артефакт при тесном рабочем потоке.
- Давать всем модулям прямой доступ к внутренним API соседей.
- Создавать отдельные БД только ради визуальной симметрии модулей.
- Принимать любой единичный вызов или превышение порога за автоматический приказ к разделению.

## Связанные маршруты

- `style-topology-fit`: сначала подтверждает, что монолитная форма соответствует драйверам.
- `fitness-function-guardrail`: превращает выбранные направления зависимостей в автоматические проверки.
- `service-based-domain-service`: следующий шаг, когда крупным предметным областям нужна отдельная поставка.
- `microservice-granularity-isolation`: применяется лишь после обоснования физической изоляции мелких границ.
- `architect-elastic-participation`: калибрует полномочия владельцев; не меняет предметную границу вместо этого маршрута.

## Self-check

- [ ] Единая поставка подтверждена драйверами, а не привычкой?
- [ ] Верхние каталоги и пространства имён предметные?
- [ ] Для каждого межмодульного вызова выбран узкий контракт либо медиатор?
- [ ] Топология данных следует автономности, а не копирует форму схемы?
- [ ] Границы имеют владельцев и исполняемую проверку?
- [ ] Сигналы деградации оценены как устойчивый паттерн, не единичный случай?
