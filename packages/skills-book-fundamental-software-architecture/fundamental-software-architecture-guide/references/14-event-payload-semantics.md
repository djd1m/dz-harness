# События: семантика и форма полезной нагрузки

## Решающий момент

Применяйте маршрут, когда нужно решить, публикуется ли факт или адресное поручение, какие бизнес-исходы заслуживают отдельных событий и что положить в payload: ключ, снимок или дельту.

**NOT:** не проектируйте здесь REST/GraphQL ресурсы, transport schema или observability stack. Маршрут определяет бизнес-смысл и архитектурную цену контракта; доставку и координацию передаёт routes 15–16.

## Протокол

1. **Классифицируйте намерение.** Если вызывающая сторона ожидает определённый результат, знает адресата и управляет шагами, это запрос или сообщение. Если описывается уже случившийся факт без предписанной реакции, это событие. Брокер не превращает команду в событие.
2. **Выберите адресацию по смыслу.** Факт обычно публикуется один-ко-многим; адресное поручение — точка-точка. Издатель факта не должен знать число подписчиков или их алгоритмы.
3. **Разведите отзывчивость и полное время.** Раннее подтверждение допустимо только при обещании будущего результата и способе сообщить отклонение. Асинхронность сокращает ожидание пользователя, но почти не ускоряет саму работу.
4. **Проверьте границу кванта.** Обязательное ожидание ответа связывает доступность и масштабирование сторон. Если бизнес допускает отложенный результат, команда и отдельное событие подтверждения могут убрать обязательное ожидание.
5. **Назовите бизнес-исходы.** Выпускайте отдельный производный факт, когда результат меняет круг подписчиков или действие. Если адресаты и работа одинаковы, оставьте единый тип с результатом.
6. **Выберите payload для каждого event type.** Снимок данных повышает автономность и производительность потребителя; ключ уменьшает контракт и трафик, но требует чтения авторитетного состояния. Промежуточный вариант должен содержать ровно нужный контекст.
7. **Добавьте контекст изменения.** Для update-события проверьте, нужны ли изменённое поле и значения до/после: новое состояние БД уже не восстанавливает эту дельту.
8. **Проверьте хрупкость насыщенного события.** Оцените устаревание копии, порядок версий, жёсткость схемы, формат и обратную совместимость. Частичное использование большого контракта всё равно связывает потребителей с его выпуском.
9. **Контролируйте гранулярность.** Укрупняйте полевые уведомления в один содержательный бизнес-результат. Не создавайте событие на каждую техническую деталь и не возвращайтесь к огромному снимку всей сущности.

## Матрица решения

| Критерий | Выбор | Цена |
|---|---|---|
| Прошлый факт, реакция не предписана | Event + pub/sub | Сложнее увидеть общий результат и порядок реакций |
| Требуемое действие, известен получатель/ответ | Message/request + point-to-point | Более сильная динамическая связанность |
| Потребитель не может читать данные или критичны scale/performance | Data-rich payload | Версии, stale copies, stamp coupling и трафик |
| Важны актуальность, компактность и простота контракта | Key payload | Дополнительные чтения, нагрузка на БД, нарушение изоляции |
| Реакция зависит от дельты | Key + changed fields или before/after | Больше чувствительных данных и размер сообщения |
| Разные исходы имеют разных подписчиков | Отдельные outcome events | Риск «роя мошек» при техническом дроблении |
| Адресаты и обработка почти одинаковы | Один event с результатом | Потребители фильтруют результат сами |
| Поля меняются одной атомарной целью | Один business-result event | Не включать неиспользуемый полный снимок |

## Антипаттерны

- Называть команду событием только из-за асинхронного транспорта.
- Обещать ускорение бизнес-работы по времени раннего ACK.
- Публиковать весь объект без анализа потребителей.
- Передавать только ключ, когда решение зависит от исчезнувшей дельты.
- Делать каждое поле отдельным событием.
- Считать версионирование устранением статической связанности.
- Блокироваться на ответе через очередь и утверждать, что кванты разделены.
