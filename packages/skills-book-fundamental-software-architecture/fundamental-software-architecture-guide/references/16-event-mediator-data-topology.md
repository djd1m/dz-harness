# EDA: хореография, медиатор и топология данных

## Решающий момент

Применяйте маршрут, когда событийный процесс уже выбран и нужно решить, кто знает последовательность шагов, как маршрутизировать нескольким потребителям и где обработчики владеют данными.

**NOT:** не проектируйте здесь API, schema/migration, модель согласованности или observability stack.
Маршрут выбирает choreography/orchestration **событийного потока приложения** и архитектурную
топологию данных. Планирование ReAct, chain/graph, planner-executor и tool workflow ИИ-агента
принадлежит `aiagents-orchestration-and-planning`; остальные детали передаются навыкам из
`boundary_skills`.

## Протокол

1. **Опишите инициирующий факт и производные результаты.** В хореографии первичный обработчик выполняет ограниченную задачу и публикует результат; независимые подписчики продолжают цепочку. Зафиксируйте, как определить завершение и текущее состояние процесса.
2. **Начинайте с хореографии для короткого предсказуемого потока.** Она поддерживает параллелизм, отдельное масштабирование и добавление реакций, но распределяет знание состояния и усложняет восстановление.
3. **Выделяйте медиатор по необходимости управления.** Если один участник уже координирует много шагов, нужен status query, retry с известной позиции или единое решение граничных случаев, вынесите локального оркестратора. Делите медиаторы по предметным группам.
4. **Используйте гибрид для стабильного каркаса с редкими ветвями.** Основной маршрут остаётся у медиатора, динамические реакции развиваются событиями. Учитывайте две модели наблюдения.
5. **Подберите механизм медиатора по сложности.** Кодовый router подходит простому процессу; BPEL — многим динамическим ветвям и структурированным ошибкам; BPM — длительным операциям с ручным подтверждением.
6. **Выберите topic или адресные очереди по потребителям.** Topic подходит общей схеме и подключению новых реакций без знания издателем адресатов. Отдельные очереди нужны разным payload, lag, backpressure, масштабу, доступу или адресному контролю.
7. **Инвентаризируйте данные до выбора БД.** Для каждого обработчика назовите данные, нужные до результата, и их владельца. Для каждого варианта посчитайте локальные чтения, синхронные вызовы, общие точки отказа, области масштаба и радиус изменения схемы.
8. **Сравните три топологии хранения.** Общая БД убирает межсервисные чтения, но создаёт один ресурс и квант. Предметные БД локализуют область, если междоменных вызовов мало. БД на обработчик оправдана, когда подавляющее большинство работы использует локальные данные.
9. **Проверьте риски соответствия EDA.** Смоделируйте неожиданные производные события, найдите потребителей меняющихся контрактов, синхронные обращения и требование знать полное завершение. Большой объём таких обращений или обязательный централизованный status — сигнал пересмотреть форму.
10. **Посчитайте реальные кванты.** Объедините обработчики с одной БД и пары, где инициатор не может продолжить без ответа. Количество сервисов само по себе не определяет число квантов.
11. **Согласуйте командное владение.** Трудный алгоритм изолируйте у команды сложной подсистемы, общие брокеры и эксплуатационные сервисы — у platform team; предметная команда должна владеть всеми техническими артефактами своей области.

## Матрица решения

| Сигнал | Выбор | Цена |
|---|---|---|
| Короткий поток, независимые реакции | Хореография | Общий прогресс, ошибки и завершение распределены |
| Много шагов, status/retry/edge cases | Локальный медиатор | Центральная связанность, throughput и отказ |
| Стабильный основной путь, редкие ветви | Гибрид | Нужны две модели управления и наблюдения |
| Одинаковый payload, новые подписчики | Topic | Широкий доступ и слабее индивидуальный контроль |
| Разные данные, lag, scale или access | Отдельные очереди | Издатель знает адресатов и публикует несколько раз |
| Много совместных чтений | Общая БД | Общая точка отказа, масштаба и изменения схемы |
| Данные в основном внутри области | Предметная БД | Междоменные sync reads связывают области заново |
| Почти все данные локальны обработчику | БД на обработчик | Стоимость множества БД и опасность sync call chains |

## Антипаттерны

- Использовать хореографию, когда обязателен единый status и управляемый retry.
- Делать один медиатор координатором всех предметных процессов.
- Выбирать универсальный orchestration engine для процессов любой сложности.
- Делить данные до инвентаря чтений и владельцев.
- Объявлять обработчики автономными при критических синхронных запросах к соседям.
- Считать число сервисов числом архитектурных квантов.
- Строить topic/queue выбор как универсальное правило без access, lag и payload criteria.

## Связанные маршруты

- `event-payload-semantics`: определяет факт, команду и payload до маршрутизации.
- `event-delivery-recovery`: проектирует ACK, repair и loss windows после выбора каналов.
- `service-based-domain-service`: альтернатива крупной предметной координации без полной EDA.
- `microservice-granularity-isolation`: уточняет физическую автономность обработчиков и данных.
- `environment-topology-alignment`: сверяет брокеры, deployment и команды с выбранной формой.
