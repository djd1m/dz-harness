# ADR: синтетическая проверка единственного владельца rotating OAuth grant

Статус: план эксперимента, 2026-11-09. Решение о внедрении не принято.
Основание: `integrations/hermes-health/ops/openai-auth-lifecycle.md` и ночной план `features/hermes-night-acceptance/00_status.md`.

## Контекст и вопрос

Несколько Hermes и Codex CLI получили копии одной OAuth refresh chain. Установленный Hermes защищает запись своего `auth.json` файловым lock и обновляет связанные записи credential pool, но lock отдельных копий не координирует refresh между контейнерами и хабом. Провайдер может ротировать refresh token и распознавать повторное использование. Успешный inference после копирования подтверждает текущий access token, но не безопасный следующий refresh. Требуется проверить поведение схемы с одним владельцем chain **без реального провайдера, секрета или изменения Hermes**.

## Альтернативы

| Вариант | Свойства и ограничения |
| --- | --- |
| A. Независимый OAuth grant для каждого процесса, полученный штатным login | Предпочтительный путь для действующих независимых Hermes/CLI при подтверждении поддержки провайдером и условий плана. Нет общего refresh token; требуется участие владельца и отдельная интеграционная проверка каждого клиента. Синтетическая модель не подтверждает поддержку такого login. |
| B. Один refresh-owner, выдающий потребителям только access token | Устраняет конкурирующий refresh при условии, что **все** потребители действительно отключили собственный refresh. Нужны долговременное состояние, сериализация, обработка неоднозначного исхода и поддерживаемый адаптер Hermes. Режим Codex CLI требует отдельного исследования. Это предмет ограниченного эксперимента. |
| C. Продолжить копировать `auth.json` либо общий файл с lock/таймером | Не обеспечивает единственного владельца при автономном refresh разных процессов; mtime не доказывает актуальность chain. Отклонено. |

## Решение для этой итерации

Создать **только автономный offline lab**: `night_oauth_lab.py` и `tests/test_night_oauth_lab.py` в экспериментальной области вне production интеграции. Python stdlib, fake provider, вымышленные токены и управляемые часы. Никаких сетевых запросов, реальных `auth.json`, OAuth login, Docker, медицинской карты, PHI, cron, production Hermes, API key или изменения работающих credential stores. Никакой передачи refresh token клиентам даже в тестовом публичном интерфейсе.

Прототип демонстрирует семантику владельца, а не готовый credential broker. Один owner хранит единственную версию chain в приватном тестовом state file; несколько синтетических потребителей вызывают `get_access()` и получают только access token и срок действия. Fake provider принимает refresh token, ротирует его при успехе, делает прежний непригодным, умеет симулировать revoke, недоступность, timeout до применения и потерю ответа после применения. Отдельный контрольный пример двух независимых копий grant должен воспроизвести конфликт; далее owner показывает устранение конкурирующего refresh.

### Минимальный контракт и инварианты

1. Клиентский интерфейс не принимает и не возвращает refresh token, не предоставляет метод refresh. Срок действия проверяется owner с заданным запасом; просроченный access token не выдаётся.
2. Для одного grant в каждый момент есть не более одного вызова refresh provider. Сериализация действует и между процессами lab, использующими один state path: lock-файл на той же локальной файловой системе плюс повторное чтение состояния под lock. Lock на сетевой FS не заявлен. Генерация состояния монотонна; запоздалый результат не перезаписывает более новую генерацию.
3. До сетевого вызова owner долговременно записывает состояние `refreshing/uncertain` (намерение). Запись через временный файл в том же каталоге, `fsync` файла, `os.replace`, `fsync` каталога; приватные права. Пока состояние не сохранено, provider не вызывается.
4. Получив новую пару, owner сначала долговременно фиксирует её и лишь затем выдаёт access token. Если ответ потерян, процесс погиб после начала refresh, либо запись результата не удалась, состояние остаётся/становится `uncertain` и owner закрывает выдачу; старый refresh token не повторяется автоматически. Даже если сбой был до фактической отправки, после durable intent применяется консервативный переход в `uncertain`.
5. `uncertain` и `revoked` требуют явного нового login/reset в будущей эксплуатации. В lab допускается только явная загрузка **нового вымышленного grant** для следующего сценария. Автоматический откат к backup или бесконечный retry запрещён. При обычной недоступности до подтверждённой отправки можно вернуть детерминированную временную ошибку; при неясной стадии — `uncertain`.
6. Ошибки и журнал тестов содержат только коды состояния/счётчики, без token, account ID и их фрагментов. Fake token values остаются внутри тестового процесса/временного каталога; тестовый путь не совпадает с домашними каталогами Hermes/Codex.

### Состояния

`ready` → при истечении срока и успешной durable записи намерения `refreshing` → после provider success и durable записи новой пары `ready` с generation +1. После ambiguous response, crash или сбоя записи результата — `uncertain`; после явного revoke — `revoked`. Из `uncertain`/`revoked` выдача запрещена до явного нового grant. При рестарте незавершённое `refreshing` считается `uncertain`. Состояние `ready` со свежим access token не скрывает ошибку refresh, если уже зафиксирован `uncertain`.

## Реализация по шагам для lead

1. Написать fake provider и owner в `night_oauth_lab.py`; предусмотреть инъекции clock, pause/barrier и точки отказа записи/краша. Публичную поверхность сделать узкой: создание с fake grant, `get_access`, явное revoke/reset для тестов, чтение только безопасного статуса. Не имитировать Hermes adapter или Codex CLI API.
2. Использовать временный каталог и отдельный lock-файл для независимых процессов. State file содержит только синтетические значения. Проверять целостность/версию формата, не восстанавливать chain догадкой из mtime. При повреждённом файле fail closed.
3. Реализовать `tests/test_night_oauth_lab.py` на unittest/stdlib, без сети и Docker, с контролируемыми barrier/event, clock и fault injection. Не опираться на sleep как доказательство гонки. Запускать тесты из checkout в чистом временном окружении.
4. Независимый QE проверяет инварианты и результаты, отдельно отмечает непокрытые окна. Отчёт содержит только синтетические исходы, коды отказа и команды тестов.

## Приёмочные сценарии

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Две копии без owner | После ротации одной копией refresh второй отклоняется fake provider; риск воспроизводим. |
| Одновременный запрос 2+ клиентов и 2+ процессов на истёкший token | Ровно один provider refresh; все успешные ответы содержат одну новую access generation, refresh token не появляется у клиентов. |
| Ещё действующий token и переход через expiry | До порога refresh не вызывается; после порога свежий token выдаётся только после durable commit; expired token не возвращается при отказе. |
| Crash до intent, после intent/до вызова, после provider commit/до ответа, после ответа/до durable state | До intent нет вызова и состояние пригодно; все незавершённые случаи после intent при restart дают `uncertain`, без автоматического повторения старого refresh. |
| Timeout с известным отказом до отправки и неоднозначный timeout после применения | Первый допускает ограниченный повтор по явному вызову; второй блокирует chain и не вызывает refresh повторно. Fake provider считает вызовы. |
| Ошибка записи intent, результата и fsync/replace | До durable intent provider не вызывается; после успешной ротации и неуспешного durable результата access не выдаётся, восстановление не использует старую chain. |
| Revoke и потеря доступности provider | Revoke блокирует выдачу и refresh; временная недоступность возвращает безопасную ошибку, не раздавая просроченный token. |
| Повреждение state, рестарт и логирование | Fail closed; нет токенов в исключениях, сообщениях и отчёте; права временного state ограничены. |

## Граница вывода и дальнейшее решение

PASS означает только, что синтетическая модель выдержала заданные interleaving и fault injection. Он не доказывает свойства реального провайдера, сетевого хранилища, Hermes или Codex CLI. **Не подключать owner к Hermes без поддерживаемого адаптера, который полностью исключает локальный refresh и безопасно получает access token.** Для Codex CLI это отдельный вопрос: нельзя предполагать возможность отключить его refresh или направить его на broker. Пока хотя бы один клиент самостоятельно обновляет тот же grant, единый owner не существует. Эксплуатационный выбор между независимыми grant и полноценным broker принимать отдельно после проверки штатного login, правил провайдера, адаптера и восстановления в изолированной среде.

## Уточнение после challenge

Принята модель process crash + инъекция syscall failures, не физический power
loss. Durable pending marker создаётся ДО refresh; пока он существует, выдача
запрещена. Ошибка replace/dir-fsync результата оставляет marker, включая crash
до обработки исключения. Marker удаляется только после commit новой пары.
Ошибка fsync каталога ПОСЛЕ удаления marker — отдельное ограничение: вызов
возвращает durability_unknown, но новый процесс может увидеть committed ready;
не обещаем persisted uncertain при неисправности самого носителя. Новая chain
уже сохранена; повтор прежнего refresh этим не допускается.

NotSent не имеет специального retry: любой exception provider после intent
закрывает chain. Reset/revoke mutation API не добавляются в toy; новый fake
initial grant требует нового private directory. Provider revoke моделируется
на его стороне. Lock inode никогда не удаляется, state path и предки без
symlinks, flock на отдельном fd каждой операции. Параллельные reset операции
вне scope, поскольку такого API нет. Состояние strict/bounded JSON; expiry
проверяется и перед выдачей. Проверки реального wall-clock rewind вне scope.
