## Решение

**CONDITIONAL GO для разработки автономного offline toy после уточнений ниже; NO-GO для заявления, что текущая спецификация уже доказывает crash durability или готовность broker.** Граница «fake provider, временные синтетические state, без Hermes adapter» правильно ограничена. Основные недочёты — неполная crash-модель, противоречие retry после intent и неопределённость lock identity. Они устранимы в плане, не требуют доступа к реальным credentials.

## Блокирующие дефекты спецификации

### C1 — Atomic replace не равен durable commit; post-replace ошибка допускает видимый ready

Пункт 4 обещает: при ошибке записи результата состояние «остаётся/становится uncertain». Контрпример: новый ready записан во временный файл, file fsync успешен, replace успешен, directory fsync возвращает ошибку. На работающей ОС другие процессы уже видят новый ready. Если процесс погибает до компенсирующей записи uncertain, следующий owner может выдать access. Простое исключение из `atomic_write` не обеспечивает обещанный persisted uncertain. Если диск вообще недоступен для записи, обещание записать uncertain невыполнимо.

Нужно определить точный контракт: видимость ready и доказанная устойчивость после power loss — разные вещи. Допустимы два явно выбранных варианта: (а) усиленная state/journal схема с доказанными границами восстановления; (б) для toy ограниченная модель process crash и явное `durability_unknown`, без обещания, что filesystem fault всегда оставляет persisted uncertain. Одного флага в памяти недостаточно для второго процесса. Если требуется строгий запрет выдачи при неуспешном final directory fsync, план должен объяснить, как другие owner узнают об этом при падении писателя. Не считать повторную запись uncertain гарантированным решением той же ошибки носителя.

Тест: injected failure после replace и до/во время directory fsync; затем новый процесс читает state без помощи памяти первого. Проверить выбранный документированный результат. Отдельно сценарий, где компенсирующая запись тоже не работает.

### C2 — Не определена модель crash и неверно универсальное ожидание uncertain

Таблица говорит «все незавершённые случаи после intent при restart дают uncertain». Но crash после durable result commit и до ответа клиенту корректно оставляет ready generation+1. Crash после replace до directory fsync не моделирует реальную потерю питания простым SIGKILL: dirty page cache живёт в kernel, restart может прочесть новый state. Fake exception от fsync тоже не моделирует множество допустимых post-power-loss состояний.

Нужно разделить: process termination; simulated syscall error; host power-loss/storage durability. Для lab обещать первые две модели; третью — только абстрактной моделью допустимых состояний, не «доказано на диске». Отметить commit point; после durable result commit потеря ответа не требует уничтожать новую chain. Ambiguous provider result до durable successor — uncertain.

Тесты: crash после durable intent; после provider mutation; после ответа до replace; после replace до dir fsync; после dir fsync до client response. Последний должен вернуть ту же committed generation при следующем get_access, без второго refresh. Тестовый event срабатывает именно на границе, не по sleep.

### C3 — Retry до отправки противоречит консервативному durable intent

Пункты 4–5 одновременно говорят «после durable intent консервативно uncertain даже до отправки» и «при известной недоступности до отправки допускается повтор». Provider вызывается только после intent; значит таблица допускает возвращение к ready в том же окне, где инвариант его запрещает.

Нужно выбрать точную политику. Проще для toy: любой сбой после durable intent → uncertain, исключение только preflight ДО intent, которое не вызывает provider. Если нужен safe retry после intent, вводится типизированное доказательство `NotSent`/«provider не мог применить mutation», отдельный durable переход, а crash до сохранения этого перехода всё равно uncertain. Нельзя определять «не отправлено» по общему Timeout/OSError.

Тесты: одинаковый TimeoutError до и после provider commit не должен вызывать эвристический retry. Раздельные preflight отказ и подтверждённый NotSent с явной семантикой; crash до/после сохранения reset intent.

### C4 — Lock-файл назван, lock identity и охват транзакции не заданы

«Один state path» не равно один lock: относительный/абсолютный путь, symlink родителя, разные lock names и unlink/recreate lock inode дают два владельца. Если lock снимается на время provider call, второй процесс может принять refreshing за abandoned или начать другой refresh; сравнение generation после ответа не отменяет два вызова провайдера. Если один общий fd с flock переиспользуют threads, повторное захватывание не доказывает внутрипроцессную сериализацию.

Для toy зафиксировать Linux/local FS или иной конкретный механизм. Стабильный lock inode, который никогда не unlink/replace на обычном release; единый canonical state identity; внутрипроцессный mutex для shared owner/fd (либо доказанный эквивалент). Lock охватывает reread→intent→provider→commit. Lock acquisition timeout возвращает busy и не ломает чужой lock. Не добавлять stale-lock stealing по mtime/TTL: paused owner остаётся жив. Если нужны leases, потребуется fencing на provider, которого план не содержит.

Тесты: два threads одного owner; два owner objects одного процесса; два subprocesses; каждый со своим fd и общий fd; aliases одного пути; paused holder дольше timeout; третий contender; crash holder и recovery. Во всех сценариях provider хранит общую историю и измеряет максимум одновременно активных refresh, а не сумму локальных counters. Попытка unlink/recreate lock должна запрещаться/обнаруживаться либо честно выводиться за модель adversarial same-user writer.

### C5 — Fake provider может сделать multiprocess proof ложным

План не объясняет, как состояние fake provider общее между процессами. Независимые копии provider после fork/spawn не моделируют одну rotating chain: каждый может успешно принять старый token, а локальный counter каждого равен единице. Повторное создание provider после crash также может «восстановить» уже потраченный token и скрыть дефект.

Нужен один авторитетный fake provider в отдельном процессе с локальным IPC либо иной общей синхронизированной моделью; никаких сетевых запросов. Mutation и журнал provider переживают смерть owner в пределах теста. Сам provider атомарно проверяет/ротирует chain. Отрицательный контроль обязан реально показать два independent owner конкурируют за одну chain; счётчик max_inflight и успешных rotations проверяется родителем теста.

## Важные уточнения безопасности локального toy

### C6 — Symlinks и права не исчерпываются chmod(state,0600)

Приватный tempfile в directory, доступной для подмены, может быть заменён между lstat/open/replace. Symlink lock может разбить identity или привести к работе вне sandbox. Existing state с широкими правами не исправляется обещанием приватного нового temp. Directory fsync должен открывать ожидаемый directory, а не подменённый pathname.

Минимум toy: создать собственный приватный temporary root 0700; не принимать произвольные production path; определить запрет symlinks для root/state/lock/temp и проверку regular files/ownership/permissions, насколько заявляется поддержка. Atomic temp с эксклюзивным созданием 0600; стабильный lock 0600. Указать, что атаки другого процесса того же UID, способного менять приватный root, не входят в security proof, если не реализована directory-fd/openat/O_NOFOLLOW дисциплина. Простое `resolve` + `lstat` не является общей защитой TOCTOU.

Тесты: permissive umask; pre-existing 0644 state/lock; state/lock symlink наружу; symlink родитель; dangling symlink; temp name collision; directory вместо state; FIFO вместо state (не зависнуть); замена path между проверкой и open через hook. За пределами собственного temp root ничего не читается/пишется: sentinel содержимое и metadata неизменны.

### C7 — Reset/revoke должны сериализоваться с refresh и иметь grant identity

Generation сама по себе недостаточна: reset с generation=0 может создать ABA, late result старого grant перезапишет новый. Новый synthetic grant должен иметь отдельный immutable grant_epoch/id, не account ID; либо global generation никогда не сбрасывается. Все admin transitions используют тот же lock и reread. Revoke/reset не должны обслуживаться параллельно held refresh без явной политики. «Explicit revoke» — test control, не доказательство provider revocation текущего access token.

Тесты: delayed refresh + reset/revoke; после reset старый ответ не восстанавливает прежний grant. Повторный reset с тем же fake seed не возвращает revoked chain в ready. Статус выдаёт безопасный generation/epoch без tokens.

### C8 — Свежесть и format validation требуют точных границ

Clock injection полезна, но access может истечь во время медленного commit; проверка только до refresh недостаточна. Не заданы `expires_at == now + margin`, non-finite clock/expiry, отрицательный срок, неизвестная schema/status, duplicate JSON keys и ready без нужных полей. Не валидировать state только по успешному json.load.

Тесты: fake clock пересекает expiry между provider response и client return; точная граница safety margin; malformed/unknown schema, bool вместо generation, отрицательная/non-finite expiry; missing successor token. Expired token не выдаётся. Модель часов для persistent expiry и monotonic elapsed time должна быть документирована; wall-clock rewind не является доказанно безопасным случаем без политики.

### C9 — Отсутствие токенов в output нужно проверять, а не предполагать

Стандартные unittest assertions на state dict способны вывести token значения; exception fake provider/JSON parser тоже может содержать input. Синтетический token всё равно должен оставаться вне отчёта по условию плана. Уникальные вымышленные sentinel values и capture stdout/stderr/logging/exception repr позволяют проверить отсутствие всей строки и запрещённых фрагментов. Публичный get_access по определению возвращает access token клиенту: запрет логирования не надо путать с запретом этого тестового результата. Состояние и temp-файлы не прикладывать к отчёту.

## Минимальный набор gates перед утверждением PASS lab

1. Зафиксированы crash model, commit point и единая политика NotSent; тесты проверяют все границы file fsync / replace / directory fsync. Не утверждается power-loss гарантия по SIGKILL.
2. Отрицательный контроль двух копий действительно использует один provider. Shared provider переживает crash owner; счётчик concurrency измеряется централизованно.
3. Доказаны same-object threads, independent objects, independent processes, alias paths и recovery после смерти holder. Нет stale lock stealing и unlink-on-release.
4. Проверены post-replace failure и невозможность записать uncertain, а не только ошибка до temp write. Документирована граница, которую выбранная схема не может гарантировать.
5. Проверены permissions/symlink controls и strict state schema в приватном temp root.
6. Reset/revoke сериализованы; late completion не переписывает новый grant. Success после durable commit не превращается в ненужный повтор refresh.
7. Gate командой unittest завершается без skip необходимых сценариев; у каждого race test есть deterministic barrier и negative/mutation control. Отчёт перечисляет фактически выполненные тесты, platform и непокрытые модели отказа.
8. Артефакт явно назван offline toy. Нет production adapter, копирования auth, реального login, cron, Docker, ключей, PHI, HTTP listener или реального провайдера. PASS не даёт разрешение подключать Hermes/Codex.

## Предложение автору плана

Исправить спецификацию до реализации: начать с process-crash + syscall-failure модели и единого локального fake provider; буквально описать recovery state на каждой границе. Строгую durable неопределённость после failed final directory fsync либо решить отдельным протоколом и доказательством, либо честно исключить из гарантии toy. Это наиболее важная поправка: существующая формулировка смешивает atomic visibility, commit durability и способность сохранить маркер на неисправном носителе.
