# ADR-002 (предложение): синтетический offline writer для recognized restore

**Статус: proposed future; не принят, не реализован.** Этот контракт описывает следующий эксперимент после независимой приёмки read-only verifier из ADR-001. Он не разрешает production restore, не снимает DRP blocker и не меняет текущий verifier, его план или QE. Цель эксперимента — получить читаемые core `recognized` text/artifact на **новом изолированном target** под новыми ID, сохранив исходное свидетельство неизменным.

## Вход и право на действие

Writer принимает только закрытый синтетический export профиля ADR-001, внешний trusted descriptor и исходный HMAC key. Перед **любой** записью в target он заново выполняет полную проверку B1–B4, а не доверяет прежнему JSON-отчёту (`executable:false`). Нужны `valid=true`, только `saved_unverified`/`artifact_observed=true`, однозначное соответствие core операции и старой receipt, точные исходные artifact bytes, source manifest/raw bytes, tuple, engine и HMAC. Отсутствующий key, integrity refusal, другой state, orphan, extra object либо несогласованные эпохи — отказ до intent. Эти входы не доказывают происхождение backup, общий исторический freeze или человеческое согласие.

Отдельное **новое явное действие оператора**: после показа ограниченного summary оператор указывает exact digest проверенного inventory, target identity и batch ID в команде `apply`; writer записывает это действие, время, версию инструмента и digest плана в intent как *новое операторское распоряжение*. Одного `valid=true` недостаточно. Локальная synthetic запись команды не является криптографическим доказательством личности оператора и не заменяет будущую проверяемую authority/attestation для production. Старые gateway receipts никогда не копируются, не исправляются под новую identity и не регистрируются как новые рабочие receipts; старый TTL не обновляется.

## Namespace и неизменяемый план

Target заранее создан offline, private `0700`, принадлежит effective UID, имеет новый `realpath/dev/ino`, не вложен в export, descriptor, key или intent source и не alias с ними; ancestors и все компоненты проверяются через dir-fd/no-follow и `fstat`. Export остаётся read-only. Target содержит лишь заранее сверенные `sources/manifest.json` и `sources/raw/**` с **точными историческими bytes** и пустой recognized namespace. Для первого эксперимента writer отказывает target с чужой операцией, receipt, индексом, staging или прежним batch; один batch занимает весь target. Source manifest/raw после preflight повторно сверяются перед каждым save и при readback. Одновременный или same-UID hostile writer вне доказанной модели; отдельный эксклюзивный target lock защищает только соблюдающих его участников, поэтому fixture без других writers является обязательной предпосылкой.

Один canonical JSON envelope `intent.json` в private каталоге **того же filesystem, что target**, содержит закрытую схему и как минимум `schema`, `batch_id`, `snapshot_id`, `inventory_sha256`, digest trusted descriptor, исходную workspace identity из проверенного tuple, `target={realpath,dev,ino}`, digest точных target source manifest/raw, полный отсортированный взаимно однозначный mapping `old_id → new_id`, ожидаемые SHA-256/размер artifact и source, engine, operator action, generation, per-item state и batch state. Canonical encoding: UTF-8, фиксированный порядок полей, compact JSON, LF в конце; SHA-256 плана считается по явно указанным неизменяемым полям, без собственного digest. Никаких key, MAC или текста в envelope. Изменение immutable полей при любом reopen — refusal; envelope другого target inode, включая скопированный sealed batch, — refusal.

`new_id = "rc-" + first_32_lower_hex(SHA256("hermes-restore-op-v1\0" || canonical(snapshot_id, inventory_sha256, batch_id, target realpath/dev/ino, old_id)))`. Canonical здесь — length-prefixed UTF-8 каждого поля в указанном порядке; строковые decimal `dev/ino` имеют canonical форму core. Все ID вычисляются **до intent**, удовлетворяют core grammar, попарно различны, не равны старым ID и отсутствуют в target; любое столкновение отказывает весь batch, без salt/retry. Повтор открытия того же intent использует сохранённый mapping, а не пересчитывает новый batch. Новый core tuple закономерно содержит новый `operation_id` и target identity; исходные metadata/receipt остаются отдельным immutable свидетельством и не выдаются за новый tuple.

## B5: durable intent → apply → reconcile → seal

Переход состояния — atomic replace **одного** envelope: создать temporary file `0600` с `O_EXCL|O_NOFOLLOW`, записать и `fsync(file)`, `rename` поверх intent, `fsync(parent directory)`. Перед первым save должны быть durable `batch=planned`, полный mapping и все `item=planned`. Два независимых файла intent/mapping не образуют транзакцию. Initial creation также fsync-ит каталог; target claim проверяется под эксклюзивным lock и при каждом reopen. Неподтверждённый результат rename/fsync означает `unknown`, а не разрешение продолжить.

Для каждого item writer сначала durable переводит `planned → attempting`, **затем** вызывает неизменённый core `saveUnverifiedRecognition` с новым ID, исходными точными UTF-8 text bytes, исходными `entry_id/source_sha256/source_bytes` и engine. Это единственный момент создания нового core artifact. Core сам fsync-ит staging files, staging directory и parent после rename; его ответ не является batch seal. После save writer вызывает core `readUnverifiedRecognition(includeText=true)`, сверяет новый tuple, target identity, source binding, точные bytes/digests, label `unverified`, `human_verification:not_established`, `index_status:not_requested` и отсутствие индекса/receipt. Лишь затем durable переводит item `attempting → observed` с exact readback digests. Никакая ошибка после durable `attempting`, включая core `absent_at_read_time`, не вызывает автоматический повтор save или выдачу другого ID.

При restart обязателен отдельный явный операторский `reconcile` того же batch: заново проверить export, trusted descriptor/key, target identity/source и envelope; осмотреть каждый mapped ID через core read и фактическое дерево. Для `observed` требуется полное повторное совпадение. Для `attempting` валидный present может быть переведён в `observed` только после полного readback; absent, staging/incomplete, corrupt, source drift или иной ambiguity дают `held` и требуют разбора оператором, **без blind retry**. Для `planned` отсутствие допустимо лишь потому, что durable `attempting` предшествует любому вызову save; продолжение требует нового явного operator apply/reconcile и повторной проверки lock/identity. Нельзя считать простой `status=absent` доказательством отсутствия ранее начатой записи. Конфликт ID или чужой batch — постоянный отказ до отдельного решения, не cleanup/overwrite.

После `observed` для **всех** items writer повторяет полный readback и сверку источников, формирует seal с digest immutable plan, inventory, mapping, target identity и отсортированных exact readback digests. `batch=sealed` и seal являются следующей атомарной durable версией **того же envelope**; seal проверяется при каждом reopen. Crash после последнего readback и до durable seal оставляет unsealed batch; crash/ошибка вокруг seal rename/fsync остаётся unknown до повторной проверки envelope и всех artifacts. Seal утверждает только согласованность синтетического offline batch на момент чтения, не power-loss атомарность между двумя stores, не gateway receipt, не активацию. Partial/held/unsealed batch ни к чему не подключается; rollback означает оставить target и старые bytes для разбора, без автоматического удаления.

## Минимальная матрица fault injection

| Точка отказа | Обязательное наблюдение при restart |
| --- | --- |
| До initial intent file fsync/rename; после rename до directory fsync | Нет доверенного intent либо `unknown`; core save ещё не вызывался. Нужен новый operator action, без вывода «committed» по наличию имени. |
| После durable intent, до `attempting` | Все `planned`, target пуст; только явное продолжение с тем же mapping. |
| После durable `attempting`, до/во время core staging и после core rename/parent fsync | `attempting` остаётся; present и точный readback допускают reconcile; absent/staging/ambiguous дают held, без повторного save. |
| После core readback, до durable `observed`; после rename `observed` до fsync каталога | Reconcile проверяет bytes заново; неопределённость записи envelope не интерпретируется как успех. |
| Между items; после последнего readback до seal | Partial или полный unsealed batch остаётся изолирован; никакого нового ID, receipt, индекса или activation. |
| Во время seal replace/fsync; после durable seal | Повторно проверяются seal, все mapped artifacts и target identity; stale/tampered/copied seal отказывается. |
| Два concurrent claims; mapping/target/source tamper | Ровно один lock/claim либо отказ обоим при ambiguity; никаких target writes после отказа. |

## Предпосылки и решение о следующем шаге

**GO только к реализации synthetic writer experiment** после закрытой independent QE текущего verifier, подтверждённой compatibility с установленным core форматом, отдельной design/QE проверки этой B5 спецификации, проверяемого offline target без writers и fault injection всех строк таблицы. Минимальный эксперимент: один batch из 1–2 реальных синтетических adapter→core операций на скопированном export и новом inode; проверка exact bytes/source и нового core read, сохранности старого дерева, запрета receipt replay и всех crash transitions. **NO-GO** при любом непроверенном prerequisite, ambiguous state, невозможности durable fsync/lock или чужой записи. Даже успешный эксперимент не является полной миграцией и не разрешает production: для неё отдельно нужны общий freeze всех stores/writers, доверенное происхождение backup и authority оператора, политика подключения gateway, независимая приёмка и решение DRP blocker.
