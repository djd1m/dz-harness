# Независимая проверка будущего writer: B5

2026-11-10. Проверен только дизайн `002-proposed-offline-writer.md` на версии
`429aa6f`. Код writer не создавался; принятый verifier и его QE не изменялись.

**HOLD на реализацию до уточнения протокола ниже. GO на доработку спецификации.**
Новые ID, отдельный target, один envelope, durable `attempting` до core save,
запрет повторного save после неопределённого исхода и отсутствие activation
выбраны правильно. Оставшиеся пробелы касаются доказательства долговечности,
переоткрытия состояния и исключения смешанного target.

## Блокирующие уточнения

### W1 — начальное создание и принятие envelope после неопределённого fsync

После crash по одному имени `intent.json` невозможно установить, вернулся ли
предыдущий `fsync(parent)` успешно. Само поле generation также не доказывает
этот факт. Фраза «unknown до повторной проверки» должна задавать действие,
которое снимает неопределённость, а не только проверку JSON.

Нужен явный протокол: при каждом reopen получить lock, проверить namespace,
полный envelope и его связи с независимо перепроверенными входами; при явном
operator reconcile принять найденную допустимую версию через новый успешный
барьер долговечности file+parent. До этого никаких core save. Если envelope
отсутствует, повреждён, неоднозначен либо остались временные файлы, действует
отдельная таблица отказов; отсутствие имени не разрешает автоматически создать
другой batch. Начальное создание не должно заменять существующий intent даже
при совпадающем batch без процедуры reopen.

Для состояния `planned` безопасность продолжения основывается на инварианте:
предыдущий процесс не мог вызвать save без успешно завершённого fsync версии
`attempting`. Это допущение о порядке и гарантиях filesystem надо зафиксировать;
успешное чтение имени не заменяет fsync. Ошибка перехода немедленно прекращает
запись, в том числе не допускает продолжения из сохранённого в памяти состояния.

### W2 — присутствие восстановленного core artifact не доказывает долговечность

Crash core после rename операции, но до fsync каталога operations оставляет
возможный `present_unverified`. Предложение позволяет reconcile перевести такой
`attempting` в `observed` и затем sealed на основании readback. Однако core read
не fsync-ит дерево. Принятый core прямо отличает наблюдаемое присутствие от
исторического durable commit.

Выбрать один конкретный вариант: консервативно удерживать recovered
`attempting+present` без seal либо отдельным разрешённым recovery-протоколом
восстановить долговечность уже существующей операции. Во втором случае после
точной валидации требуются fsync обоих core файлов, каталога операции и цепочки
созданных recognized-каталогов до устойчивого родителя; никакой перезаписи
байтов или повторного core save. Ошибка любого барьера оставляет held/unknown.
Затем повторный readback и durable envelope. Это новая гарантия текущего
операторского действия, а не утверждение, что прежний core commit был durable.

Тест обязательно различает `SIGKILL` и моделируемый отказ fsync: успешный запуск
после убийства процесса на той же машине не доказывает устойчивость к потере питания.

### W3 — target sources, право владения и граница копирования

«Заранее создан» и совпадение SHA не определяют, кто подготовил target, завершено
ли копирование и fsync-нуты ли его файлы и каталоги. До intent нужен точный
source-only inventory target и его digest, проверка закрытости, типов, режима,
владельца, single-link файлов, отсутствия ссылок и пересечения roots. Все source
байты должны совпадать с перепроверенным export. Наличие неизвестного объекта
отказывает; каталог recognized должен иметь один явно заданный начальный вид
(отсутствует либо точно определённые пустые каталоги).

Определить copy-ready barrier: либо подготовщик передаёт проверяемую квитанцию
конкретного протокола копирования, либо writer сам делает fsync уже проверенных
target source files/directories и target parent перед durable intent. Сам
неподписанный marker или SHA не доказывает прежний fsync. Зафиксировать target
`realpath/dev/ino` до и после подготовки и под lock; shared filesystem/mount
должен поддерживать выбранные fsync/rename/flock гарантии.

Для первого эксперимента достаточно приватного synthetic target без других
writers. Это владение из предпосылки и проверок namespace, не криптографическое
доказательство эксклюзивности против same-UID процесса.

### W4 — полная матрица состояний и однозначные команды

Нужна закрытая таблица разрешённых переходов batch/item, включая `held`, и
раздельная семантика команд. Сейчас формулировка `apply/reconcile` допускает
разные прочтения того, может ли reconcile начинать save ещё не начатых items.
Минимально: reconcile только наблюдает/восстанавливает подтверждённые состояния;
новый явный apply после durable принятия envelope запускает лишь `planned`.

| Состояние item | Наблюдение | Требуемое решение |
| --- | --- | --- |
| planned | absent, без staging | Может остаться planned; новый apply допустим только после W1 и проверок target. |
| planned | present, staging или corruption | held: нарушение инварианта, не автоматическое принятие чужой операции. |
| attempting | точный present | Только W2, затем observed; без нового save. |
| attempting | absent, staging, drift, corruption | held, без retry и нового ID. |
| observed | точный present | Повторная проверка; сохранить observed. |
| observed | любое несовпадение | held, без восстановления через save. |
| sealed | точные envelope/seal/все items | Идемпотентная проверка; никаких новых saves. |
| sealed | несовпадение | Отказ/held с сохранением исходного свидетельства; не автоматическое переписывание seal. |

Уточнить, можно ли sealed envelope вообще переписывать в held либо отказ
существует только в результате команды. Для held отсутствует автоматический
переход обратно в planned. Ошибка одного item останавливает весь batch; остальные
planned не запускаются. Зафиксировать допустимые batch/item combinations.

### W5 — точная схема, lock/claim и атомарность перехода

До кода нужны полные exact-field схемы intent, operator action, item observation
и seal: типы, лимиты, canonical byte encoding, неизменяемая проекция и её digest.
«Как минимум» не задаёт закрытый контракт. Для length prefix mapping определить
число байтов/порядок байтов либо точную текстовую грамматику длины. generation
растёт ровно на один; он не является защитой от hostile rollback сам по себе.
При reopen immutable projection сравнивается с заново выведенным планом и
явно выбранным batch, а не только с самоподписанным SHA внутри envelope.

Задать точное расположение intent и стабильного lock-файла: отдельный private
control root на том же filesystem, без вложенности/alias с export, target,
descriptor и key. Lock удерживается на весь apply/reconcile; сам lock inode
никогда не заменяется и не удаляется. Существующие claim, temporary envelope и
служебные каталоги core должны иметь явную политику проверки; произвольный
cleanup запрещён. Новосозданные control parents должны также пройти fsync.

Проверка чужих объектов должна учитывать штатный core `.recognized-write`,
создаваемый save, иначе собственная операция может нарушить исходную политику
«только sources и recognized». После каждого перехода ошибки rename/fsync
останавливают процесс без попытки записать «успех» другим способом.

Для минимального batch потребовать одну согласованную old workspace identity
у всех операций либо явно сделать её полем каждого item: verifier сам по себе
не обещает одну глобальную историческую identity. Чтение core не возвращает
весь tuple; ожидаемый новый tuple нужно самостоятельно собрать и сравнить его
request fingerprint плюс exact readback bytes и остальные bindings.

## Новое распоряжение оператора и историческое согласие

Разграничение в proposal корректно: локальная запись команды — новое
распоряжение для synthetic эксперимента, не подписанное согласие и не доказательство
личности. Само по себе отсутствие подписи здесь не блокер. Однако команда apply
должна явно связывать **digest полного показанного плана**, batch ID, inventory
digest и target identity; запись одного inventory digest недостаточно явно
связывает mapping и версию семантики инструмента. Reconcile также должен иметь
свою новую запись действия, сохраняя первоначальную запись без подмены.

Запрет импортировать старые gateway receipts остаётся обязательным. Не называть
новый JSON authrecord аттестацией, если у него нет отдельной схемы проверки
подписи/authority. Это будущий production-контракт, а не требование добавить
подпись в данный synthetic эксперимент.

## Условия следующего GO

Достаточно дополнить спецификацию W1–W5 и явно определить запись нового действия.
Затем возможен GO на отдельную реализацию synthetic writer с проверкой каждого
барьера: initial intent file/rename/parent fsync; attempting file/rename/parent;
core stage/rename/parent; восстановление долговечности present; observed;
итоговый readback; seal file/rename/parent. На каждом переходе проверить
process crash и ошибку системного вызова, отсутствие blind retry, неизменность
mapping, единственность lock claim и сохранность исходного export.

Открытие copied sealed batch на другом inode, подмена source/copy-ready данных,
planned+present, чужой batch и неизвестные временные объекты должны отказывать.
Успешный readback должен сохранять exact UTF-8 bytes и source binding под новым
ID, `unverified`, `human_verification:not_established`, `index_status:not_requested`.

Ни текущий HOLD, ни будущее synthetic GO не меняют уже принятую read-only
реализацию, не разрешают production restore и не снимают DRP blocker.
