## Замечания

| ID | Важность | Подтверждение и требуемое исправление |
| --- | --- | --- |
| QE-1 | Блокирует приёмку строгих схем | В `semantic` проверяется набор полей строки manifest, но не значения `media_type`, `ingested_at`, `archive_id` и `source.*`. В синтетической строке одновременно установлены `media_type={}`, `ingested_at=false`, `archive_id=17` и все `source.*=[]`; после `fixtures.seal` получено `valid:true`. Нужна явная валидация значений выбранного экспортного профиля и соответствующие отрицательные тесты. |
| QE-2 | Блокирует приёмку строгих схем | В receipt заменено только `payload.workspace.dev=11.0`, оставлено `sidecar.workspace.dev=11`; после повторных HMAC и inventory получено `valid:true`. Обычное равенство Python смешивает int/float. Проверять схему и строгие типы обоих workspace до сравнения; добавить случай bool при подходящем значении идентичности. |
| QE-3 | Блокирует приёмку строгих схем | `inventory.entries[0].mode` заменён с integer `448` на float `448.0`; после обновления внешнего inventory digest получено `valid:true`. По архитектуре mode — integer. Требовать `type(mode) is int` для обоих типов записей. |
| QE-4 | Блокирует приёмку ограничений ресурсов | `open_abs` открывает `child`, но при отказе `_dir_ok` или проверки файла до присваивания `fd=child` закрывает только родительский fd. Десять вызовов `verify` для snapshot с режимом `0755` увеличили число `/proc/self/fd` ровно на 10. Нужна гарантированная очистка child на каждом пути отказа; повторные вызовы не должны увеличивать число fd. |
| QE-5 | Несоответствие диагностическому контракту | Удаление отдельного синтетического key-файла даёт `input_invalid`. ADR требует отдельный отказ отсутствующего ключа без fallback. Текущий отказ безопасен, но неотличим от общих ошибок входа; нужен фиксированный отдельный код. |
| QE-6 | Требование к документации | README проверенной версии написан по-английски; пользователь требует документы на русском. Перевести, сохранив технические идентификаторы и границы. |

Воспроизведение QE-1–QE-3: каждый пример начинается с нового
`fixtures.make(Path(tempdir))`; изменения JSON записываются через `fixtures.put`.
Для QE-1 вызвать `fixtures.seal(snapshot, descriptor, key)`.
Для QE-2 вызвать `fixtures.resign(receipt_path)`, затем `fixtures.seal`.
Для QE-3 изменить только mode в inventory и переписать
`descriptor.inventory_sha256=fixtures.sha(inventory_bytes)`.
Затем `verify(str(snapshot), str(descriptor), str(key))` ошибочно возвращает
`valid:true, executable:false` во всех трёх случаях. Таким образом, эти примеры
проходят криптографические проверки и достигают недостаточной проверки схем.

## Границы и дополнительные наблюдения

Независимые дополнительные пробы подтвердили неизменность байтов файлов,
состава деревьев, режимов доступа и mtime для положительного примера и отказов
на FIFO, ссылке в пути к snapshot и descriptor внутри export. FIFO дал
`unsafe_path`, ссылка — `input_invalid`, вложенный descriptor — `unsafe_path`.
Во всех полученных отчётах `executable:false`; отчёты ограничены фиксированными
полями и не содержат входных путей или содержимого документов. Неизменность
atime не заявляется.

Проверка кода подтверждает отсутствие вызова core, adapter reconcile/status,
дочерних процессов, сетевых клиентов и операций записи в verifier. Инструменты
создания тестовых данных пишут только в выделенные синтетические каталоги.

Ограничения файлов/байтов и глубины заданы, но полная граничная матрица пока не
доказана 14 тестами. Кроме утечки QE-4, `os.listdir(fd)` выделяет весь список
каталога до проверки количества объектов; глубина JSON проверяется после
`json.loads`. Это ограничивает утверждение «до выделения больших структур»:
нужны потоковый обход каталога с ранним лимитом и точное описание либо проверка
предварительного ограничения JSON. Допустимый объём JSON уже ограничен размером
файла; обход произвольно широкого каталога таким ограничением не покрыт.

Реальная интеграция устанавливает совместимость положительного примера, но не
исчерпывающую совместимость произвольных JS/Python значений. Неподдерживаемые
формы должны явно отказываться. B1–B4 в целом отражены в реализации, однако
строгость B2 и ресурсная часть B4 требуют исправлений выше. Историческая полнота
backup, freeze живых writers, same-UID hostile mutation, B5, production DRP и
право на восстановление не доказаны и не входят в эту приёмку.

Повторная QE должна выполняться после передачи окончательного набора исправлений
с новыми SHA-256; этот отчёт не заявляет их результат и не создаёт машинных gates.

### QE-7: вложенный каталог операции ошибочно принимается

**Блокирует приёмку точного экспортного профиля B2/B4.** На свежем примере
`fixtures.make` создан каталог `operations/unexpected`, затем целиком перенесён
`operations/<rc-id>` в `operations/unexpected/<rc-id>`. После
`fixtures.seal(snapshot, descriptor, key)` verifier вернул `valid:true`,
`operation_count:1`, `executable:false`.

Причина: множество metadata выбирается через `startswith` и `endswith`, ID
извлекается из предпоследнего компонента, а разрешённые каталоги затем выводятся
из самих входных metadata-путей. Не проверено точное равенство пути профилю
`workspace/recognized/.machine-unverified/operations/<id>/metadata.json`.
Это допускает лишнюю структуру даже при правильной закрытости inventory.

Условие закрытия: требовать канонический путь metadata и artifact для каждого
ID; отдельный отрицательный тест должен переносить целую операцию во вложенный
каталог и переиздавать inventory/descriptor, после чего получать фиксированный
отказ без частичного плана. Изменять HMAC не требуется: содержимое receipt при
этом остаётся прежним. До этого исправления итоговая оценка — HOLD только
read-only синтетической приёмки; production-восстановление по-прежнему вне scope.
