# ADR-003 (предложение): offline восстановление непроверенных recognized операций после переноса workspace

**Статус:** proposed, **не реализовано и не принято**. 2026-11-09. Этот документ задаёт следующий ограниченный эксперимент; он не меняет принятые требования, код, тесты или машинные gates parent feature и не устраняет текущий DRP blocker.

## Контекст и граница доказанного

Принятый core `recognized-store.js` сохраняет immutable `artifact.md` и `metadata.json` под `recognized/.machine-unverified/operations/<operation_id>/`. Его канонический request fingerprint включает `operation_id`, `workspace realpath/dev/ino`, source anchor (`entry_id`, путь, SHA-256, размер), точные байты текста и engine. `read/status` сверяют старую identity с **текущей** identity workspace и повторно читают source. Простая копия или восстановление в иной каталог/inode поэтому не является рабочим recognized restore. Текущий CLI имеет только `capabilities/save/status/read`; restore/rebind отсутствует. `present_unverified` означает успешный текущий readback, а не историческое доказательство fsync.

Adapter `recognized_confirm.py` хранит отдельную HMAC квитанцию: owner, workspace identity, runtime identity, sidecar, operation ID и состояние. Его `verify_core` сверяет fingerprint core с этой квитанцией. Старую квитанцию нельзя исправить под новый workspace или проиграть как новое подтверждение. Наличие SHA-256 у старой metadata не доказывает ни подлинность прежнего подтверждения, ни происхождение backup. Ранее проверенный offsite restore `c48c1a01` предшествует новым recognized artifacts; его результат не является проверкой данного сценария.

Цель следующего среза — **операторский offline прототип на синтетическом закрытом backup**. Он должен сохранить исходные байты artifact, логическую source entry и статус `unverified`, явно отделяя старую identity от новой. Он не запускает Hermes/gateway, индекс, live map writers или клиническую проверку. Для применения к живой карте позже потребуется проверенная остановка **всех** writers, включая legacy writers без общего lock; нынешний core lock сам по себе этого не гарантирует.

## Альтернативы

| Вариант | Польза | Цена и риск | Вывод |
| --- | --- | --- | --- |
| A. Переписать старые metadata на новую realpath/dev/ino и сохранить прежние operation IDs | Мало новых файлов и привычные ссылки | Меняет исходное свидетельство, ломает fingerprint и HMAC receipt; создаёт видимость прежнего подтверждения для новых байтов identity. Crash между правками создаёт смешанное состояние. | Отклонить. |
| B. Offline migration в отдельное восстановленное дерево: новые operation IDs через существующий core `save`, immutable mapping и отдельная новая operator attestation | Использует уже проверяемый core `save/status/read`, сохраняет старое дерево и отделяет новое действие от старого подтверждения | Требует самостоятельного валидатора полного backup, durable mapping/reconcile и доказанного владения ключом либо нового подтверждения. Частичная миграция до batch seal не пригодна к активации. | **Рекомендовать только как следующий синтетический прототип.** |
| C. Расширить core специальным restore attestation/alias для старых operation IDs | Может сохранить старые ссылки и напрямую описать смену identity | Новый доверенный путь в core, схема и правила для старых receipts/alias; сложнее ограничить replay, право чтения и сбой между attestation и alias. Нужна отдельная версия контракта и QE. | Отложить; вернуться, если требование сохранения IDs доказано необходимым. |

## Предлагаемое решение B

1. **Закрытый вход.** Оператор предъявляет полный неизменяемый backup как единый объект: его доверенный inventory/manifest, source manifest и raw bytes, recognized операции, adapter receipts и отдельно восстановленный HMAC key material. Новый валидатор проверяет конечный набор и размеры, schema/canonical metadata, регулярные файлы и режимы, отсутствие ссылок/неожиданных или частично записанных объектов, хеши **всех** перечисленных байтов и отсутствие дополнительных объектов. Имена путей из backup служат только адресами для безопасного открытия; они не являются доказательством целостности. При неполном inventory, неизвестной версии или невозможности доказать закрытость набора — отказ всего batch. Ни `read` core на новом пути, ни один SHA файла по отдельности не заменяют эту проверку.
2. **Происхождение.** Для каждой операции валидатор сравнивает старую `realpath/dev/ino` в каноническом tuple core с identity в старой HMAC квитанции, `entry_id`, source path/SHA/bytes, artifact SHA/bytes и engine. Старый HMAC проверяется **исходным** ключом, присутствующим в независимом backup ключа; ключ не выводится из данных. Если ключ потерян, нельзя утверждать, что старое gateway подтверждение доказано. Такой batch остаётся заблокированным до отдельной процедуры нового явного подтверждения с новой квитанцией; миграционный инструмент не сочиняет прежнюю подпись и не превращает SHA в HMAC. Повреждённая или несогласованная квитанция — отказ, а не режим «ключ потерян».
3. **Новая identity и действие.** Перед записью зафиксировать новую `realpath/dev/ino`, сверить source entry и raw bytes в целевом isolated workspace. Сохранить durable migration intent с batch ID, полным проверенным inventory digest, старой и новой identity и детерминированным взаимно однозначным `old_operation_id → new_operation_id` (новый ID отвечает grammar core). Старые metadata, artifacts, receipts и operation IDs неизменны. Новая operator attestation подписывает **новое** действие и ссылается на проверенное старое свидетельство; она не заявляет, что оператор или пользователь подписал его в прошлом. Затем вызвать текущий core `save` с теми же точными UTF-8 bytes, source SHA/bytes, entry и engine под новым ID, проверить `status/read` и хеш байтов. Новый результат остаётся `saved_unverified`, `index_status: not_requested`, `human_verification: not_established`.
4. **Crash и replay.** Для одного target/batch нужен отдельный эксклюзивный lock поверх core lock. Intent и mapping пишутся атомарно с fsync до первого `save`; каждый новый ID детерминирован. После restart сверять intent и каждый новый `status/read` с ожидаемым tuple и байтами. Отсутствие, `incomplete_attempt`, corruption, неоднозначный результат или другой batch в том же target — остановка для оператора; нельзя подобрать ещё один ID или автоматически повторить `save` поверх неизвестного состояния. Batch seal фиксируется только после полного readback всех операций и mapping. Частичный batch остаётся изолированным и не считается готовым restore.
5. **Rollback и дальнейшее использование.** Старое дерево сохраняется неизменным; автоматическое удаление или изменение старых receipts запрещено. До seal target не подключается к gateway, поиску или карте. Откат означает не активировать новый batch и сохранить обе копии для разбора; удаление новой копии требует отдельного операторского решения. Для реального workspace нужны отдельные gate: остановка всех writers, целостность закрытого backup и ключей, контроль единственного target, проверка readback после активации и независимая приёмка. Ничего из этого ADR не разрешает production restore.

## Краткая матрица приёмки будущего прототипа

| Сценарий на синтетике | Ожидаемое доказательство / отказ |
| --- | --- |
| Полный backup, исходный HMAC key, новая path/dev/ino | Старая квитанция валидна для старой identity; новая операция имеет иной ID и точные исходные bytes/source/engine; обе остаются `unverified`. |
| Потерянный key; неверный key; повреждённая квитанция | Различимые причины отказа. Без ключа нет заявления о старом подтверждении; повреждение нельзя маскировать «потерей». |
| Пропуск, extra file, symlink/hardlink, изменённый source/metadata/artifact, незакрытый inventory | Отказ всего batch **до** записи в target, включая случай, когда отдельный известный файл имеет правильный SHA. |
| Crash до intent, после intent, после части core saves и до/после seal | Restart читает тот же mapping/IDs и точные bytes; partial не активируется; ambiguity/incomplete останавливает, без повторного старого receipt. |
| Два оператора или live writer, повтор того же batch, конфликт другого batch | Эксклюзивность доказана либо отказ; replay не создаёт иной ID или новую интерпретацию. Для live writer без freeze — отказ. |
| Откат и проверка границ | Старое дерево цело; target не индексируется, не становится `human_verified`, не публикуется в Hermes автоматически. |

**Следующий шаг:** отдельно спроектировать и проверить на синтетических закрытых fixtures offline inventory verifier + migration intent/reconcile. Лишь после его независимого QE решать, нужен ли restore контракт в core и как проводится controlled activation. Этот ADR не является waiver существующего DRP blocker и не меняет текущие acceptance claims.

## Независимая проверка предложения

См. [challenge](../recognized-recovery-challenge.md): выявлены B1–B5 — корень
доверия backup, допустимые receipt states, общий freeze разных stores, confinement
и durable seal protocol. До их спецификации migration writer остаётся HOLD.
Следующий ограниченный шаг — только read-only verifier синтетических snapshots,
без core save и activation. Это уточнение очередности, не объявление B1–B5 решёнными.
