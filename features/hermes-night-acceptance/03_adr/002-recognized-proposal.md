# ADR и план: подтверждаемое сохранение непроверенного PDF draft

Статус: проект для ночной тестовой итерации, 2026-11-09. Основание: `/tmp/hermes-night-contract-audit.md`, `integrations/hermes-health/{intake_confirm.py,pdf_draft.py,health_plugin.py}`. Код и production не изменены этим документом.

## Контекст и решение

`health_pdf_draft` сегодня сверяет исходный PDF с manifest до и после изолированного извлечения и создаёт приватные `draft.md`/`draft.html` вне карты. `intake_confirm` показывает рабочий образец: подготовка квитанции инструментом, подтверждение только gateway-командой с task-local identity, durable journal и повторное чтение результата. Но это контракт для **оригиналов**, не для распознанного текста. В health-advisor нет обнаруженного `recognized-save` API; `third-brain ingest` принимает уже существующий файл и не даёт точной транзакции recognized + index.

Решение для прототипа: отдельный `draft → proposal → gateway confirm → saved_unverified` поток; индекс запускается **другой** явной операцией и имеет отдельный receipt. Подтверждение означает «сохранить именно эти байты как непроверенную машинную транскрипцию», а не `human_verified` и не клиническое согласие с содержимым. `anchor.verified` означает целостность первоисточника; его нельзя переносить на достоверность PDF text. На всех ответах и фрагментах поиска — `НЕПРОВЕРЕНО`, `human_verification: not_established`, `content_trust: untrusted_document`.

### Альтернативы

| Вариант | Решение |
| --- | --- |
| A. Записать draft прямо из Hermes в `recognized/` и сразу вызвать `third-brain ingest` | Отклонить: модель могла бы инициировать запись, нет общего контракта для Claude, partial/timeout ingest нельзя назвать успешной индексацией. |
| B. Разделить proposal/confirm и создать узкий core `recognized` contract, затем отдельный index receipt | Выбрано для тестовой среды. Core задаёт формат, привязку и чтение для Hermes и Claude; Hermes только проверяет доверенный gateway context и orchestrates. |
| C. Взять существующий `third-brain ingest` как единственное хранилище recognized | Отклонить: поиск/дедупликация patterns не дают стабильного artifact по `(source entry_id, revision)`, byte-exact readback или единственной активной версии. |

## Границы и расположение кода

- **Core health-advisor** (канонический исходник, затем контролируемая сборка/public projection): узкий versioned `recognized save/status/read` контракт и, позднее, `recognized index plan/apply/reconcile`. Он владеет `recognized/` layout, проверкой source anchor/manifest/raw SHA-256, immutable revision, atomic durable write, CAS/idempotency, readback и маркировкой непроверенного статуса. Общий контракт должен работать независимо от Hermes и быть пригоден Claude. Не менять существующее поведение `third-brain` и Claude; новые операции additive и выключены, пока не приняты тестами. Учитывать выявленное отличие core/public `bin/health-advisor.js`; проверить `--capabilities` и совпадение нужных модулей в установленном тестовом runtime, не объявлять parity всего пакета.
- **Hermes plugin**: `pdf_draft.py` добавляет доверенный machine-readable sidecar с `entry_id`, source SHA/bytes, exact `draft.md` SHA/bytes, engine/status и schema, записанный вместе с файлом в приватный каталог. Старые draft без sidecar отвергаются и создаются заново. Новый модуль по образцу `intake_confirm.py` готовит HMAC-protected proposal с owner/workspace/runtime/draft/source binding, TTL, случайным receipt ID и состоянием; `health_plugin.py` открывает **только prepare/status** для модели. `confirm`/`cancel` — отдельные gateway-команды, не методы `HealthTools.call` и не параметры от модели. `health-read` и registry расширяются только после проверки command dispatch и transport acceptance в тестовой среде.
- Не открывать patient workspace, secrets, production Hermes, Docker или реальный gateway в этой итерации. Для реализационных стадий — синтетический workspace, fake gateway context и private temp dirs. Копирование черновика в карту не должно зависеть от отправки `send_file` пользователю.

## Минимальный контракт сохранения

1. `prepare(entry_id, draft_id, expected_draft_sha256)` принимает только идентификаторы и digest, не destination path или текст. Plugin по dirfd/no-follow открывает приватный draft, сверяет `draft.md` с sidecar и возвращает `proposal_id`, digest, source identity, размер, срок, явный статус `prepared_not_saved`. HTML только для просмотра; сохраняемый payload — **точные UTF-8 bytes `draft.md`**, без скрытой переработки. Ограничить размер и отказать malformed UTF-8, NUL, symlink, нечастному каталогу, отсутствующему/несовпадающему sidecar.
2. В proposal навсегда связаны `(workspace dev/ino, case, source entry_id, source SHA-256/bytes, draft SHA-256/bytes, engine, operation id, owner, runtime identity)`. Перед confirm заново открыть draft и исходный raw по manifest; проверить SHA/bytes и неизменность workspace/runtime. Не доверять header draft или полям модели как источнику этой привязки. Если manifest/source/draft изменены, отказ `prepare_again`, без записи. Для source anchor проверить `stampFromManifest`/`resolveAnchor`, но не выдавать integrity за human verification.
3. Подтверждение принимает только opaque proposal ID через уже проверенную gateway command path, требует того же platform/user/chat/profile, запрещает cron и сохраняет момент подтверждения. Запись из модели, текстовой фразы в документе, env или произвольного chat message не считается подтверждением. Если gateway transport не гарантирует этот контекст и не принимает команду, не включать confirm. Смысл команды явно показывает точный draft hash, source ID и `НЕПРОВЕРЕНО`; не называть её медицинской проверкой.
4. Core назначает revision из `operation_id`/content hash по контролируемой схеме и пишет immutable artifact в `recognized/` и metadata `recognized-1`: source binding, exact text digest, engine, status `unverified`, creation/confirmation provenance без персональных данных в публичном ответе. Нет произвольного пути от клиента. Под локальным map-write lock и CAS активной revision: одинаковые operation ID + payload возвращают прежний receipt, тот же ID с иными bytes/metadata — conflict, конкурентная новая revision одного source требует явного expected revision. Не перезаписывать и не удалять прежние revisions молча.
5. Перед вызовом core plugin сохраняет durable `committing` journal. Core завершает atomic file/metadata commit (`fsync` файла, rename, `fsync` каталога) и повторно читает artifact/metadata, сверяя digest и source binding. Только после этого plugin выдаёт `saved_unverified`; в ответе `index_status: not_requested`. Если процесс падает или core возвращает timeout, повторный status/reconcile читает конкретную immutable revision и сравнивает все поля; при недоказанном результате — `reconciliation_required`, без повторного commit вслепую. Если journal save до core не удался, core не вызывается. Сбой journal после успешной core записи требует readback/reconcile; ошибку не маскировать `saved`.
6. Lock обеспечивает сериализацию **только новых writers, использующих тот же core lock** на локальной FS. Manifest CAS и повторная проверка source уменьшают окно гонки, но legacy writers без общего lock не становятся согласованными. При наблюдаемом drift отказ; нельзя заявлять транзакционную согласованность всей карты. Допуск в production требует отдельного анализа всех writer paths.

## Отдельный index retry

Это следующая, независимая стадия после доказанного `saved_unverified`. `index plan` закрепляет source ID, immutable revision, artifact SHA, doc path, chunk count/hash, expected exact records и статус `unverified` в **каждом** pattern/passsage. Core проверяет неизменность revision при apply. Простой `third-brain ingest` с `written/skipped` или `backlinks` по doc_id недостаточен: audit указывает partial import, объединение duplicate/invalid skips, отсутствие `written + skipped == expected`, отсутствие readback всех patterns и возможные варианты metadata под одним doc_id. `--no-mirror` также не доказывает готовность vector индекса.

Нужен узкий core readback/reconcile для конкретного плана: каждый ожидаемый record/chunk найден в brain с точным body/hash, header, source binding и `unverified`; количество и identity совпадают, нет смешения metadata revisions. Receipt может быть `indexed_unverified` только после этой проверки плюс повторное чтение recognized artifact. Timeout/частичный импорт → `index_unknown`, блокировка автоматического повторного apply; сначала reconcile точных expected records, затем retry только недостающих по тому же operation ID при доказанной idempotency. Если core не может безопасно идентифицировать missing/extra records или гарантировать статус каждого search hit, оставить `saved_unverified`, индексный stage `refused_capability_missing`; не притворяться, что нужен лишь повтор команды.

Для пользовательской проверки после `indexed_unverified`: запрос известного синтетического слова/фразы по конкретному source, результат через существующий read-only snapshot search, readback текущего `recognized` файла и сверка digest; hit показывает `НЕПРОВЕРЕНО`. Такой поиск доказывает доступность одного известного фрагмента, **не** полноту индекса. Поиск без hit не доказывает отсутствие данных. Старые third-brain hits без verification metadata нельзя автоматически считать verified. Unindex/rollback и переключение active revision не входят в ночной минимум; не объявлять безопасным обновление индекса поверх старой версии без отдельного контракта ownership/cleanup.

## Малые стадии и приёмка

1. **Контракт/fixtures:** зафиксировать schemas, failure codes и synthetic PDF/draft/source fixtures; проверить permission/path/size, source hash, draft hash и доверенный command context. Gate: старые draft и недостоверный gateway context отказаны.
2. **Core save:** отдельный тест `recognized save/status/read` в чистой карте. Проверить exact bytes, immutable binding, status `unverified`, idempotent replay, conflicting key, concurrent revision CAS, atomic write failure, crash до/после rename и readback после restart. Gate: ни один сбой не возвращает `saved` без доказанного чтения.
3. **Hermes proposal/confirm:** подготовка не меняет карту; confirm с правильным identity сохраняет один artifact; replay возвращает тот же receipt. Проверить истечение TTL, cancel, другой user/chat/profile, cron, runtime/source/draft drift, ошибку journal и crash после core commit. Gate: модельный tool не имеет пути к confirm и ответ никогда не говорит `human_verified`/`indexed`.
4. **Index plan/reconcile:** выполнить на синтетическом brain только при наличии точного core readback. Инъекции partial ingest, duplicate/invalid skip, timeout и metadata variant должны оставить `index_unknown`/refusal, а не успех. Gate: exact expected records и unverified маркировка в каждом hit. Затем известный-source search через Hermes snapshot и readback исходного recognized artifact.
5. **Независимое QE другой моделью:** проверить код и реальные команды тестов отдельно от разработчика; записать доказательства и незакрытые gaps. Если часы/контракт не позволяют stage 4, завершить stage 2–3 с `index_status: not_requested` и явным отказом index, не снижая критерий.

## Условия отказа до внедрения

Нет доверенного gateway command transport; нет поддерживаемого core recognized API в фактически установленном runtime; отсутствует durable readback после crash; source/draft binding можно подменить; legacy writer race наблюдается и не разрешён; нет точного readback/reconcile индексных patterns; search теряет `unverified` статус; plugin/public/core версии расходятся. Любой пункт блокирует соответствующую стадию. Ни один тест на синтетике не разрешает production install или медицинское утверждение о качестве текста.
