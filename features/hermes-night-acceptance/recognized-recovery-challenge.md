# Независимый design challenge ADR-003: recognized recovery

2026-11-09. Reviewer gpt-6-astra; автор proposal — другая модель. Только review будущего дизайна: ADR-003, фактические `recognized-store.js` (`tuple/loadStored/read/save`) и `recognized_confirm.py` (`RecognizedStore`, HMAC, `command/reconcile`). Реализация, тесты, production и текущие parent gates не менялись. Ничего ниже не является реализованным recovery.

**CONDITIONAL GO для дальнейшей спецификации; HOLD на implementation migration до B1–B5.** Выбор новых IDs и сохранение старого дерева лучше согласуется с существующим immutable contract. Отдельные unverified labels, запрет старых receipt replay, отказ при ambiguity и отсутствие automatic activation заданы правильно. Ни один из этих пунктов не снимает текущий DRP blocker.

## Блокирующие пробелы будущего дизайна

**B1 — корень доверия backup пока назван, но не определён.** «Доверенный inventory» и независимо восстановленный key недостаточны как проверяемый контракт. Хеши обнаруживают изменение относительно выбранного inventory, но не подмену inventory вместе с файлами. HMAC доказывает владение общим секретом, а не личное подтверждение человеком, время backup или его полноту; любой обладатель ключа может подписать другой receipt. Нужны explicit trust model, источник доверенного inventory digest/key identity и связь inventory со snapshot/batch. Synthetic fixture может получать expected digest вне восстанавливаемого дерева и заранее известный key ID. Не называть это исторической human-authenticity. Wrong key и изменённый MAC криптографически неразличимы без независимой key identity: таблица не должна обещать точную диагностику причины по одному HMAC mismatch. Lost-key путь оставить отдельным, без fallback из integrity failure.

**B2 — допустимые состояния receipt и согласованность разных stores не определены.** Adapter подписывает не только `saved_unverified`, но также `prepared`, `committing`, `reconciliation_required`, `expired`, `cancelled`. Валидный HMAC + matching artifact не доказывают завершённое gateway подтверждение: например, prepared receipt мог попасть в backup отдельно от позднего core artifact. Задать матрицу receipt-state × artifact-presence × artifact_observed, точное равенство proposal/operation IDs, owner/workspace/sidecar/runtime schema, canonical request hash и source logical path. Для первого прототипа принимать только явно выбранный узкий согласованный класс; prepared/cancelled/expired, orphan core, missing receipt и transient states должны иметь фиксированный отказ/карантин, не автоматическое повышение статуса. Старый TTL не должен превращаться в свежее разрешение save. Новая operator attestation нуждается в отдельной схеме и проверяемом authority, не в самоподписанном утверждении инструмента; старые gateway receipts не импортировать как рабочие новые receipts.

**B3 — закрытый backup требует единой границы freeze для core, adapter и ключей.** Хеширование полного списка после копирования не доказывает согласованный момент across stores. Core lock не охватывает adapter receipt до/после save; legacy writers могут не соблюдать lock. Определить порядок quiesce всех writers, drain in-flight, затем snapshot всех stores и key generation/identity; либо явно ограничить prototype заранее созданной offline fixture без writers. Отдельно описать lock-файлы, staging, `.recognized-pending-*`, prepared receipts и другие штатные служебные объекты: сейчас «нет extra/partial objects» способно отвергать любой обычный полный store без объяснения. Нельзя незаметно удалить их, чтобы backup прошёл. Тест: core artifact и receipt из разных snapshot epochs, ротация/подмена ключа, crash во время snapshot — refusal до target writes.

**B4 — confinement и target ownership должны охватывать весь путь чтения/записи.** Запрет symlink/hardlink в inventory не закрывает aliases ancestors, совпадение source/target/intent/key roots, подмену parent между validation и save и повтор batch в другом target. Уточнить private trusted ancestors, отсутствие nested/overlapping roots, no-follow traversal, owner/modes/nlink и ограничение hostile same-UID. Target должен быть свежим, изолированным, с проверенным source manifest/raw и без чужих operations; lock/intent должны быть закреплены за конкретной target identity. Digest планирования должен включать snapshot identity, полный mapping и target identity; определить canonical encoding, collision refusal и ownership существующего target. Проверить source/target alias, intent внутри source, copied sealed batch на другой inode и повтор с другим target. Проверки пути сами по себе не гарантируют freeze против same UID.

**B5 — durable state machine и граница seal недостаточно конкретны.** «Intent и mapping атомарно» требует одного envelope либо явного commit protocol: два независимых файла/FS нельзя считать одной атомарной транзакцией. Определить состояния validated/planned/applying/sealed, что именно fsync-ится и что хранит attestation; bind seal к inventory, mapping, target identity и точным readback digests. Current core status сообщает observed presence, а не исторический durable commit. После intent crash перед первым save даст absent: консервативный stop допустим, но для полезного resume нужна отдельная явная процедура оператора — не обещать automatic recovery. После части saves verifier не должен импортировать новый opid для failed item или активировать partial batch. Unknown после seal replace/fsync остаётся unknown до проверки; seal не означает подключение gateway. Нужны failure tests каждого перехода, concurrent target claim, mapping tamper, stale seal и падение между последним readback и seal. Cross-storage power-loss atomicity пока не обещать.

## Ограниченный следующий шаг

Сначала дополнить proposal trust/state/freeze/namespace таблицами и спроектировать **read-only verifier** двух synthetic snapshots: полный согласованный positive fixture и adversarial набор B1–B4. Его выход — bounded sanitized validation plan с exact digests, новым mapping и причинами отказа; без `core save`, нового HMAC receipt, индекса или activation. Независимо проверить, что malformed/ambiguous input не выдаёт executable plan. Только затем отдельно рассматривать writer с B5 fault matrix и operator authorization. Этот порядок не изменяет принятую текущую feature и не обещает production recovery.
