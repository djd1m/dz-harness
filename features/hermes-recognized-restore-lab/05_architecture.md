# Архитектура синтетического offline writer

`CLI plan/apply/reconcile → private fd reader + verifier semantics → source-only target preflight → pinned runtime closure → one target lock + atomic intent → bounded Node core CLI save/status/read → exact file readback + fsync barrier → seal`.

Reader повторно исполняет B1–B4 из `recovery_verifier.py`, не принимает прежний JSON report. Export/descriptor/key открываются fd-relative/no-follow с теми же лимитами; verified bytes не подменяются между проверкой и save в модели offline fixture без writers. Root и все ancestors target проверяются fd-relative, directory/file owner/mode/nlink; roots не вложены и не alias. Target source-only создаётся оператором до команды, не заполняется writer из непроверенных путей. Source manifest/raw сверяются с export exact bytes и digest; fsync source files и всех родителей завершается до initial intent.

Runtime adapter берёт закреплённые absolute Node/CLI пути из offline lab config, вычисляет closure identity по алгоритму `recognized_confirm.runtime_identity` включая Node и capabilities и сравнивает с trusted `expected_runtime`. Запускает только installed `recognized-cli.js` actions `capabilities/save/status/read` в bounded process group с timeout и лимитами stdin/stdout/stderr; без shell/env наследования секретов, без network. `status` без текста не заменяет `read` или exact artifact bytes; если CLI `read` несовместим, отказ, не прямой обход core. Перед save text декодируется из verified artifact строгим UTF-8 и после core сравнивается byte-for-byte. Core `read` не возвращает весь tuple: writer независимо строит ожидаемый **новый** 14-field tuple, сверяет его SHA-256 с core `request_sha256` и проверяет exact canonical `metadata.json`, artifact и source. Core создаёт metadata с target identity; старый metadata/HMAC не адаптируется.

Intent/lock размещены в **единственном target-anchored** private control root `<target-realpath>/.restore-lab` на том же filesystem. Перед первым apply target source-only, затем `.restore-lab` становится закрытым исключением профиля. Init создаёт directory и stable lock с fsync; конкурент, увидев незавершённый init, отказывает. Stable lock inode не заменяется и не удаляется; immutable claim создаётся до initial intent и препятствует новому batch после crash. Lock serializes cooperative processes; claim/intent identity проверяется под ним до любого write. Все atomic replacements — на том же local filesystem с file+directory fsync. После неизвестного fsync только explicit reopen/reconcile с повторным file+parent fsync может принять единственную valid версию; missing intent при claim или leftover temp — held. Неизвестный результат любого fsync, subprocess timeout или lock-loss даёт fail-stop. `reconcile` никогда не вызывает save; новый `apply` после принятого envelope запускает только planned. Для `attempting+present` reconcile делает полный barrier: оба core files, operation directory, operations parent, `.machine-unverified`, recognized, все target source files/dirs и target root. Проверять точные bytes до и после barrier; изменение — held. Barrier не «доказывает» предыдущий commit, он устанавливает текущую durable точку для synthetic local FS. Core `.recognized-write/.dz` учитывается как разрешённый scaffold pinned runtime, но оставшийся `store.lock`/staging — held. После seal никакого connect/import/receipt API.

Выход CLI ограничен fixed codes/digests/counts/states, без текста, абсолютных путей, owner, key/MAC. Fault injection допускается только в тестах, не в пользовательских CLI arguments. Интеграция работает с offline pinned image и синтетическим PDF; отсутствие runtime — failure. Same-UID hostile actor, network FS, production freeze и внешняя authority не доказаны.
