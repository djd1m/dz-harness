# QCSD challenge: operator-only recognized index lab

2026-11-09. Read-only review `features/hermes-recognized-index-lab` в public checkout, плюс shipped third-brain engines и harness-cli/core source. Код index не изменялся. Единственная запись — этот отчёт. Проверки runtime в рамках этого review не запускались.

**CONDITIONAL GO для ограниченного synthetic lab после B1–B4; не production/index readiness signoff.** Разделение core artifact и индекса, прямой JS API с machine-unverified, отсутствие save/intake при retry и честный отказ от active revision/rollback — правильные границы.

## B1 — `recall --all` не даёт строгого доказательства доступного backend

`packages/harness-cli/src/cli.ts:5296` действительно имеет отдельную all-ветку до query limit, читает весь `loadStorePatternsSync` и при `--json` выводит массив без обычного `--limit` slice. Это положительное source evidence, но не доказательство конкретного установленного binary/backend.

Критично: `packages/harness-core/src/patterns.ts:1125` реализует `loadStorePatternsSync` как try/catch, где **любая ошибка возвращает []**. Поэтому exit0 JSON[] может означать ошибку хранилища, а не пустой brain. Дополнительно `third-brain/engine/search.js::dzJson` превращает пустой stdout и любой JSON НЕ-массив в `[]`. План прямо предлагает эту функцию; её результат недостаточен для классификации `none` перед записью.

Поправка: не использовать dzJson как строгий oracle. Через existing `runDz` получать raw результат и отвергать spawnError, nonzero, timeout, empty, nonarray, unknown record shape, output/record limits. Для graceful backend [] нужен отдельный проверяемый health/provenance gate конкретного pinned runtime/backend; простой fixture >10 records этого не решает. В минимальном lab можно требовать заранее созданный synthetic canary/known inventory и считать отсутствие свидетеля `readback_unproven`, чётко ограничив claim этой fixture; это не универсальная диагностика частичной corruption. Если независимое доказательство недоступно — блокировать apply, как ADR уже обещает.

Тесты: fake stdout empty/{} /{"patterns":[]} /null; actual read-down/corrupt backend при exit0; `--all --json` fixture выше обычного limit с независимым ожидаемым count; overflow maxBuffer/timeout — никогда none/complete. Проверять именно binary, backend и modules, которые затем вызываются apply, не исходник в другом checkout.

## B2 — Exact set не должен стирать duplicates и malformed variants

Сравнение через Set(pattern) скроет два одинаковых records. `headerOf()` молча возвращает null при неизвестной/битой версии header; фильтрация только успешно распарсенных headers может не заметить extra record, который всё ещё относится к doc_id. Сравнение только hash/body пропустит другой domain/type/reward; importer dedup keyed by exact pattern, поэтому запись с тем же pattern в чужом domain способна заблокировать импорт правильной записи.

Поправка: сравнивать multiset и полную перечисленную схему expected records. Для каждого expected pattern ровно один record с точными domain/type/reward и строкой pattern; ts разрешённо не входит в identity. Duplicate exact records — conflict, не complete. Неизвестные/неразбираемые records, которые нельзя безопасно исключить из области doc_id, должны давать unproven/refusal, а не исчезать из сравнения. Чужие обычные records без этого doc_id допустимы только при ясном discriminator.

Тесты: duplicate одинакового pattern; правильный pattern+неправильный domain/type/reward; тот же doc_id с другим case/date/anchor/header/body; malformed/unknown-version header с нужным doc_id; source с CRLF, Unicode, blank separators — expected strings должны приходить из того же buildRecords, не самодельной реконструкции.

## B3 — Partial retry не является транзакцией; последняя проверка не устраняет гонку

Existing ingest lock охватывает bridge, но не wrapper preflight→ingest→postflight. Два wrapper могут пройти preflight на одном состоянии; чужой writer может добавить conflicting variant между проверкой и ingest. Postflight обязан отказать, но запись уже могла произойти. Single-writer convention это честная граница synthetic lab, не техническая гарантия exact subset.

Кроме того, документ говорит «после timeout обязательно readback», но одновременно «timeout никогда indexed». Нужно выбрать: при timeout и полном валидном postflight результат либо `indexed_at_check_time` как новое наблюдение, либо `index_unknown` до отдельного reconcile. Нельзя разные ветки случайно трактовать один исход по-разному. Консервативный plan уже обещает второй вариант — сохранить его.

Тесты: barrier вставляет extra variant после preflight; результат не успех и не false rollback, уже внесённые records не удаляются. Timeout после полной записи → unknown по выбранному контракту; отдельный reconcile может подтвердить complete. Partial exact subset→повтор того же deterministic batch→нет duplicates; no auto retry. Ни missing/partial/timeout/drift не вызывают core save, intake или новый operation_id.

## B4 — Sentinel не доказывает отсутствие production data

Owned regular marker + --lab-root предотвращает ошибочный запуск без маркера, но оператор может пометить любую настоящую карту. Это прямо не криптографическая авторизация — правильно; нельзя писать «CLI никогда не принимает production workspace» как безусловную гарантию. Пустой/произвольный lab-root `/` или `/home` формально делает confinement бесполезным.

Поправка: explicit ограничение на synthetic temporary fixture root, marker schema/nonce/version, realpath equality/binding к fixture, owned private directory; reject symlinks marker/workspace/brain/operations и marker hardlink если заявляется собственный файл. Программа не создаёт marker, не разрешает общий home/root как lab-root; однако даже с этим claim остаётся «защита от случайного запуска в непомеченной карте», а не PHI detector. Отдельно запрет `.health-brain` alias на shared brain до read (search сам строит lexical brain path; writer защищается позже).

Тесты: marker missing/wrong schema/symlink; workspace outside/root-equal/alias; brain symlink shared/outside; permissive marker mode; real temporary fixture положительный контроль. Проверять отказ до spawn/read source, когда он относится к sentinel confinement.

## C1 — Direct API и неизменяемый artifact

Source подтверждает: CLI KINDS = consultation/trend/synthesis/conclusion, тогда как write.ingest API принимает nonempty whitespace-free kind. Поэтому direct API machine-unverified допустим для этого lab; main CLI whitelist расширять не нужно. Но wrapper должен сам фиксировать kind, не брать его из request, и проверять полученные expected headers. Нет подмены клиническим kind при fallback.

`buildRecords` и `write.ingest` должны быть из одной pinned package tree. Ingest заново читает immutable artifact по path; между core validation и чтением возможен noncooperating change. После ingest обязательно новый core read и exact comparison; при drift — unknown/refusal, не rollback. Никаких prefix-label copies: статус несут header и presentation; artifact bytes остаются теми, которые core подтвердил.

## C2 — `search-known` не доказывает, что generic search безопасен для unverified

Проверять returned hit против конкретного expected pattern/header, включая case/date/chunk count/anchor list и body, затем current core provenance. Label НЕПРОВЕРЕНО ставится wrapper, не считается гарантийной характеристикой generic third-brain или Hermes search. Generic hidden path policy не расширять. Полезен отрицательный тест старого hit без machine-unverified: отказ/пропуск без promotion в verified.

## C3 — Evidence и limits перед implementation

Указать численные bounds plan/chunk count/output bytes/readback records/timeout и включить их превышение в typed refusal. Health/core capabilities не подтверждают third-brain exact-readback автоматически: это отдельная capability/fixture gate, привязанная к installed runtime identity. Source-known query может ранжировать непредвиденный chunk; no hit означает лишь no hit, не no stored data.

**Минимум до GO:** закрыть fail-open readback B1, multiset/full-record B2, согласовать timeout/reconcile и single-writer boundary B3, уточнить sentinel claim B4. Затем real synthetic integration с >обычного limit, partial retry/dedup и exact immutable core read. Пока эти условия не доказаны, оставлять saved_unverified/index not_requested и capability refusal вместо правдоподобного index receipt.
